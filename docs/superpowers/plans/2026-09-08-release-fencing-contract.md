## Decision

Keep the existing container row, provision claim fields, pending-update row, and EFS recovery guard. Extend their contract: the provision claim becomes the shared owner mutation lease for provisioning and task-definition operations; the update row remains the durable release journal. An owner pointer to that update prevents generic recovery from stealing a partially activated release. The existing persistent EFS guard serializes the actual file/service mutation with assignment and claim changes. A conditional database check followed later by a file write is not a fence.

Do not implement an automatically expiring second owner lock, a second rollout table, or a new rollout orchestrator. Extend `update_service._apply_claimed_update` and its existing recovery pass. Do not expose release assignment until all relevant writers and lifecycle entries honor this contract.

There is one deliberate availability limit: an ambiguous ECS mutation after a crashed executor is not automatically recoverable merely because a lease is old. The existing ECS calls have no conditional owner-generation argument. The correct small implementation retains the owner reservation and reports recovery needed when it cannot establish that an earlier command can no longer arrive. It must not claim that a last-minute heartbeat or immutable target ARN solves an old `desiredCount=0` arriving after a successor's start.

## Exact storage and ownership

Container row additions:

| Field | Meaning and writer |
| --- | --- |
| `desired_release_id` | Durable explicit assignment, set only by release assignment/finalized cancellation. Absence retains the environment's legacy default behavior. Do not infer it from a running task or write it for every legacy owner. |
| `active_release_id` | Last release confirmed by exact target observation and acceptance. Remains the old value during preparation, stop, activation and validation. May be absent for an unassigned legacy owner. It never substitutes for the assigned target. |
| `release_revision` | Monotonic integer; absence means 0 only for comparisons. Increment on assignment/reservation, successful activation finalization, or explicit cancellation/repair that changes release state. Never reset when clearing assignment; this prevents absent→assigned→absent ABA from authorizing an old render. |
| `release_update_id` | Stable pointer to the nonterminal release/task-definition update owning the container. Not a second lease and has no TTL. Remains set across worker claim takeover and on uncertain/post-activation failure. Ordinary provision/wake/resize/reapply cannot bypass it. |

Reuse `provision_claim_id`, `provision_attempt_token`, `provision_claimed_at` as the one owner mutation lease. For an update operation, set claim and attempt equal to its `apply_claim_id`; keep `provision_execution_name` absent, because this is not an SFN provision. Do not set container status to provisioning just to stage a running owner's release. New narrow claim helpers must distinguish operation ownership explicitly by `release_update_id`/the claimed update, not infer that any claim means an SFN execution. Existing startup/dispatch classification must check that pointer before considering SFN recovery.

Non-release size/base refresh uses the same existing owner claim and `release_update_id` pointer for its mutation, without changing desired/active release IDs. If it already has a pending-update row, connect both claims atomically; a direct resize uses the existing update journal synchronously to retain its return-ARN contract. Do not create a second worker for it. Direct wake/stop operations enter the same guard and owner-claim exclusion boundary and honor a release reservation; a reserved release's worker issues its own stop/start through internal helpers with its token. An ordinary direct wake/stop retains its owner claim if its ECS outcome is uncertain, so assignment cannot proceed; it does not manufacture a terminal success or clear the claim from a finally block. Preserve an emergency stop's ability to stop the runtime, but mark/retain release recovery state and prevent automatic restart; do not treat an emergency stop as release success or silently discard it.

Update row additions for `release` operations, alongside existing `apply_claim_id`, heartbeat and `target_task_definition_arn`:

- `target_release_id`, `release_revision`: immutable target and assignment generation.
- `phase`: `reserved`, `prepared`, `stop_requested`, `drained`, `staged`, `activating`, `activated`, `start_requested`, `validating`, `healthy`, or `needs_recovery`.
- `prior_release_id` (absent is legacy), `prior_desired_release_id` (omission records prior absence), `prior_task_definition_arn`, `prior_desired_count`, `target_desired_count`: rollback/reference facts and the intended post-update count, captured once from verified owner state and authorized intent.
- `staged_config_sha256`, `prior_config_sha256`: exact target and retained final post-drain source/rollback bytes. The final source is the prior config; do not store a duplicate source hash. A preliminary source hash is an in-memory comparison aid only.
- Owner-local names derived from validated `update_id`: `openclaw.json.staged.<update_id>` and `openclaw.json.before.<update_id>`. Derive these; do not accept arbitrary paths or store duplicate path metadata. Never put config bytes/secrets in DynamoDB.
- `effect_kind`, `effect_claim_id`, `effect_executor_id` only while a remote mutation is unresolved. Kind is narrowly `stop` or `start` (and task-definition update for reused size/base operations); arguments come from immutable target/count fields. Executor is an existing backend/runner identity, never a process-local PID assumed globally unique. Successful response clears the intent in the same journal checkpoint that advances the phase. Missing outcome remains visible as `needs_recovery`.

No candidate release record is populated by this report. A real release record must resolve an approved immutable image/digest, schema artifact/provenance, upstream version and carried-fork identity. `v2026.9.3` or its upstream commit alone is not an extended-image release. Do not derive upstream version by parsing a digest suffix.

Candidate qualification must also verify that its actual config writer/boot recovery interoperates with the existing sidecar/guard protocol. The local helper describes the pinned runtime, not proof that a future candidate preserves it. An incompatible or unverified protocol blocks activation; do not rewrite the marker or remove an occupied lock to make the candidate start.

Add all four container release fields to preserved fields. Pin every one to the observed value, including `attribute_not_exists` for absence, in the whole-item `upsert` CAS; a scoped update helper must not overwrite them. Reject caller-provided release fields in generic `upsert`, `update_fields`, and `update_container_leased`, following the existing gate-owned restriction. Use the narrow transactional helpers for changes. A superseded generation/claim is an abort, not a reread-and-adopt retry by the old worker.

## CAS operations and lock order

Notation: `C` is the container row; `U` is its selected update; `r` is expected release revision; `k` is the current worker token. Conditions include the exact owner and existing container identity; never allow a deleted/recreated row to satisfy an old operation through optional generation clauses.

1. **Reserve and assign:** inside the existing owner recovery guard, `TransactWriteItems` claims `U` from pending/scheduled and updates `C` together. Require `C.release_revision=r` (or absent if expected 0), expected prior desired/active values, no `release_update_id`, and no provision claim. A stale provision claim is still a claim: resolve its existing executor first. Set desired target, revision `r+1`, `release_update_id=U.id`, owner claim/attempt `k`, and `U.apply_claim_id=k`, phase `reserved`, immutable target/prior facts and revision `r+1`. Failure writes neither assignment nor update claim. Scheduling/queuing alone does not change desired state.
2. **Checkpoint:** transaction condition on `C.release_update_id=U.id`, revision and desired target unchanged, exact owner claim **and attempt** equal `k`; condition on `U.status=applying`, `apply_claim_id=k`, expected phase and immutable target. Advance phase/metadata and refresh both timestamps together. Claim-token mismatch aborts immediately. Do not use the current optional “attempt absent also passes” condition on the explicit release path.
3. **Set target:** extend existing `set_apply_target` semantics with those container/phase conditions. ARN is absent or exactly equal to the proposed ARN. After persistence, every retry uses that ARN; an orphan register before persistence is harmless and must never be deployed by the losing worker. Stage metadata becomes immutable at `staged`; before that it may be rerendered under the same claim after the final drain read.
4. **Provision claim/takeover/attempt:** existing provision helpers require `attribute_not_exists(release_update_id)` for ordinary callers. Also fix the current status-only claim branches: `stopped` or `error` does not authorize overwriting another operation's present claim. A fresh acquisition requires no claim; reclaim requires the exact observed prior claim/attempt plus the existing executor-recovery conditions. A present claim with ambiguous remote effects is not ordinarily reclaimable. The old unconditional takeover must not steal a release operation. Claim/attempt changes that could invalidate an in-flight config/service writer enter the same recovery guard before their DDB CAS. Provisioning of an already assigned, stable owner also pins release revision and resolved release throughout, with exact attempt comparisons at effect boundaries. Size/base update reservation uses the same two-row operation with unchanged desired/active IDs; completion clears its pointer/claim under both tokens without claiming a new active release.
5. **Update takeover:** acquire the same recovery guard first, then transactionally replace both owner claim/attempt and update claim only if both still match the previously observed pair, both identify this same update/revision, heartbeat is stale, and no unresolved external effect prevents takeover. Preserve phase, target, source/target hashes and assignment. No new release may supersede this journal. If the guard is held by a live/paused writer, time out; never unlink the guard or declare it dead based on DDB age.
6. **Finish:** after acceptance, transactionally set `active_release_id=target`, increment revision, clear `release_update_id` and the update-owned provision lease fields, and set `U.status=applied`, `phase=healthy`. Require both tokens, target, revision, `phase=validating` and the health evidence's exact task definition/digest. A second worker's finish must fail. Never release the owner lease through the ordinary health poller before this transaction.

Lock order is always: existing process-local lock keyed on canonical `openclaw.json.lock` → existing persistent `.isol8-guard` → existing OpenClaw sidecar **when reading/writing active config** → DDB condition/checkpoint → atomic file operation. Service mutation needs the first two, not the OpenClaw sidecar. Assignment/takeover needs the first two and its DDB transaction. No network data gathering occurs while the active sidecar is held.

Refactor the existing lock context's internals just enough to allow guard-held callers to acquire the sidecar without reacquiring/releasing the process-scoped fcntl guard. Do not nest `openclaw_config_recovery_guard` around `openclaw_config_sidecar_lock` as currently written: nested fcntl opens/closes can accidentally release a process's lock. Keep the protected DDB/check/file or DDB/check/ECS/record block on one worker thread; cancellation of an awaiting coroutine must not release its locks while `to_thread` continues. A thread completing after cancellation still records its resolved effect under its original token before releasing the guard.

Do not hold the recovery guard during drain polling, task boot, gateway waiting, or smoke tests: the new task's boot recovery needs it. Commit an expected phase before releasing it, and recheck that phase under the guard at the next effect. This prevents an old worker that resumes after takeover from reissuing a stop in `validating`.

## Safe assignment → activation order

1. Complete shared-backend rollout and verify old backend/provision executors lacking these fences are drained **before enabling assignment**. Local code/tests alone do not establish this. Verify the exact owner/service, candidate artifact/schema, prior task definition/image, and available rollback/backup prerequisites. The first production-affecting rollout/assignment remains approval-gated by the submitted goal; this step cannot be performed by assuming the founder locator is authority.
2. Reserve and assign atomically as above. Ordinary owner config changes are retryably unavailable while `release_update_id` exists. They must not acknowledge an applied config change they dropped. New desired assignment is now durable, but no image/config activation has occurred; active release remains old. Lifecycle callers seeing desired != active with a reservation resume/defer to this update, never independently provision the target.
3. Prepare target config in memory or the update-local provisional stage, with an explicit target release and schema, and register the candidate task definition with `_register_only=True`. Capture/persist the ARN before any ECS deployment. This preliminary render must not mutate `openclaw.json`, trust stores, device keys, identity files, or another active runtime file. Split the gathering/rendering portion of `write_user_configs` from its existing provisioning side effects; adding only `config_path` to that side-effectful method is insufficient.
4. Snapshot any pre-stop ephemeral state required by the accepted backup plan, persist the stop intent, issue desired zero under the guard, and checkpoint the successful response. Release the guard and strictly await drain. `False`, timeout, access/describe failures and ambiguous service/task identity all stop the transaction. A service count of zero is not sufficient. Enumerate relevant service tasks with pagination, include tasks captured before stop, and require their `lastStatus=STOPPED`; do not use service-not-found alone as positive proof that a just-deleted task exited. Retain this evidence in the release record/operational ledger, without secret payloads.
5. After drain, acquire active lock, verify claims/revision/phase and re-read the final old config. The old runtime could have changed it after the preliminary render; compare its hash and rebuild/preserve from this final snapshot when necessary. Render, prune restored keys with **target** schema, merge the update's target config patch in memory, and run `gate_config(..., schema_id=target.schema_id, enforce=True)` on the completed document. Do not use live `reapply_owner_config`'s write-then-restore sequence. Retain final prior bytes in the update-local backup, write final target bytes with tempfile + atomic rename, and persist `staged` plus exact hashes. Use normal safe file permissions/ownership and flush/fsync where durability is required. A schema/build/storage failure leaves old active bytes intact and service stopped.
6. Under the same canonical active lock, recheck the persisted target/hash/schema and the drained/reserved state. Persist `activating` before replacing the file. Atomically replace active config from a copy of the stage, preserving the stage for recovery; then checkpoint `activated`. The old process has exited and ordinary backend writers remain excluded. The retained rollback config must not be the hot patcher's rolling `.bak`, which subsequent writes can replace.
7. Persist `start_requested` plus effect identity, then update ECS using the persisted target ARN and `target_desired_count`, without `forceNewDeployment`. Starting is contingent on confirmed activation; it cannot race a separately dispatched provision. After the call resolves, persist `validating` and clear its effect intent **before** releasing the guard so boot recovery can run. Disable or otherwise prove safe automatic ECS rollback for a cross-schema release: rolling back just the image to 8.1 while target config remains active is not an acceptable recovery mechanism. Keep SINGLE_WRITER deployment settings.
8. Use a bounded, strict variant of the existing foreground waiter that returns explicit success or raises; require expected target ARN on PRIMARY and actual running task, expected digest, gateway availability, runtime config acceptance, and the requested workload smoke. It must not silently return on error/status change, perform an unapproved cost escalation, release the shared lease, or start ordinary post-provision user-visible work before the release's acceptance boundary. Reuse underlying observation helpers; do not duplicate a second health poller.
9. Commit healthy/applied and active assignment together under both claims. Ordinary hot writers now resolve the active candidate schema. Desired remains the candidate so subsequent size/refresh/reprovision retains it. The stage hash is activation evidence, not an eternal checksum: the live runtime may legitimately rewrite config during boot or later use.

For an intentionally stopped owner, do not wake it merely to label an image change healthy. Keep the update prepared/staged and active release unchanged until an authorized ordinary wake executes activation/start/acceptance through the same journal. A founder release may explicitly request start in its approval package. A size-only change on a stopped owner may truthfully finish “task definition prepared for next start” without changing `active_release_id` or claiming a runtime test.

## Active writers and stale render rejection

At the start of an ordinary full render or schema-sensitive patch, capture `(owner identity, release_revision, active_release_id, provision claim/attempt if any)` with a strongly consistent read. Capture before assembling version-sensitive provider/plugin blocks, and thread that context to the final writer; capturing it only inside `_locked_rmw` after a caller already generated an old-version block is too late. Resolve active schema from this context; do not pass desired schema to a running task. A pending assignment with no active candidate is not a reason to guess the schema.

At the final canonical lock, reread/check that context, require no release reservation for ordinary writes, then validate and write inside the protected section. If the revision/active release/claim changed, reject and let the operation rerender from current inputs; do not retain the old dict and relabel it with the new schema. An owner whose release is assigned but whose metadata cannot be resolved fails closed. DDB unavailable also fails closed at this boundary.

`_locked_rmw` reads current config under lock and can apply an ordinary patch to that current document, but schema-sensitive patches assembled outside the lock still carry their captured context. `write_openclaw_config` must validate inside this same fence and switch from direct `write_text` to the existing tempfile/rename pattern. `reapply_owner_config` must produce its preserved/pruned merged document before its one final active write. No brief generator-only intermediate active document is allowed.

The revision fence closes the concrete race: renderer A starts on revision 0; assignment/activation changes revisions while A gathers inputs; A finally gets the lock and sees a mismatch/reservation, so it writes nothing. It also closes a writer that checked DDB then paused: assignment/takeover cannot move the revision until that writer exits the existing guard. Runtime writers do not understand DDB; positive old-task drain, rather than a database lease, excludes them at schema activation.

## Crash, takeover and recovery contract

| Interruption | Allowed recovery |
| --- | --- |
| Before reservation commits | No assignment occurred. Retry the transaction. |
| After reservation, before target persistence | Same update can resume; re-register if needed. Never deploy an unpersisted ARN. |
| Preliminary render or drain wait | Claim takeover may resume only after acquiring the existing guard and checking both claims/phase. Regenerate preliminary config as needed; final stage is based on post-drain bytes. |
| Guard held by paused/stale writer | Wait/timeout. DDB heartbeat age is not authority to remove or bypass the lock. |
| `staged`, before activation | Verify stage and prior hashes, recheck actual drain, then activate. Missing/corrupt stage is rerenderable only before immutable staged metadata is committed or by a deliberate new staged attempt with a fenced metadata revision; never silently replace expected bytes. |
| `activating`, process died | Under guard, compare active bytes with recorded prior and stage hashes. Target hash means rename landed; prior hash means activation can be retried after drain verification. Neither match, or missing required prior/stage bytes, means `needs_recovery`, no start. This is a local file/DDB gap with deterministic evidence, not a reason to guess. |
| `activated`, before start | Verify hash and target, then start the persisted ARN. Ordinary provision remains blocked. |
| Start completed and phase is `validating` | Resume read-only target/health/acceptance checks. Never register a new target or use force redeploy. Live config may now have valid runtime writes, so do not overwrite it just because its hash differs from initial stage. |
| TCP health succeeds, worker dies before finish | Recheck exact target/acceptance and atomically finish under new claims. No repeated config activation. |
| Post-activation boot failure | Retain reservation and desired/old-active distinction; mark recovery needed, leave stopped when safe. Never terminal-fail-and-release into generic reprovision. Restore image+config only through an explicit state-aware recovery step after drain and the goal's backup/new-work rules. |
| Pending ECS intent without conclusive outcome | Recovery is read-only and reservation remains. Do not automatically advance to an incompatible later stop/start/rollback phase. |

An exact target ARN makes repeated **same-target deployment** convergent; it does not fence desired counts or a later release. Every synchronous service effect must record intent before sending, retain the existing guard until its outcome is known and recorded, and refuse stale phase/token execution. If the executor dies with the request outcome unknown, simply killing its process or seeing the service at zero once is not proof that a delayed remote request cannot still complete. The minimal correct default is `needs_recovery` and no automatic takeover into conflicting mutations. Any more available recovery policy needs a documented, verified settlement/previous-executor termination mechanism; that proof is absent from the inspected code and is a release gate, not an implementer's silent timeout assumption.

Existing worker expiry must not clear `release_update_id`, and unresolved journal rows must not receive terminal TTL. Normal failure before any remote/config activation can be explicitly cancelled under both claims by restoring the prior desired assignment and incrementing revision. A cancellation does not automatically restart an owner already stopped; restoring a previous runtime is a separate recorded action. A failed assigned target must never fall back to global default as “recovery.”

## Compatibility and no-AP boundaries

| State / request | Required behavior |
| --- | --- |
| Unassigned legacy owner, no release operation | Preserve current 8.1 default resolution and omitted-schema selector audit/degrade behavior. No eager assignment/backfill and no global image-pin change. Concurrency guards may add retryable contention; they do not select a new release. |
| Explicit candidate unknown, schema missing/corrupt, image unqualified | Reject before assignment/reservation where detectable. No default release, strip-key, legacy schema, or active-config fallback. |
| Assigned and stable, size-only/base refresh | Base supplies structure; explicitly overlay the assigned image, retaining owner environment/secrets, role, AP and proper size. Verify resolved desired == confirmed active and the observed image is compatible. Do not rerender or activate another schema just for size. |
| Assigned desired != active, or observed image differs | This is release reconciliation. A size/restart call must defer/resume the existing journal, not quietly turn itself into an image migration. Reject missing journal/inconsistent metadata for operator repair. |
| Assigned stable stopped reprovision with AP | Strictly prove prior task drained before full config replacement; resolve one release for config and task definition, propagate failures, and use the shared lease/final write fence. |
| Assigned stopped service without AP | Fail before rendering/overwriting active config or calling start. Existing no-AP fallback starts the old revision and therefore cannot prove candidate/config coherence. Read-only inspection of the task-definition mount can guide a later explicit AP-repair operation; do not infer and silently persist a different AP. |
| Unassigned legacy stopped service without AP | Retain the historical simple-start fallback only for a request with no explicit release/image migration. Branch before target config regeneration: preserve existing active bytes and existing task definition. This is a compatibility fallback, not candidate qualification. |
| Fresh explicitly assigned owner | Candidate must already be registered/qualified; create service at zero with exact target, generate+strictly validate before activation/start, and finish active only after acceptance. The founder migration itself must reject a missing owner/container row rather than accidentally creating a new owner through this path. |

Do not allow free-form `new_image` to mutate an explicitly assigned owner unless it resolves to the immutable release selected by the journal. A fleet image update must exclude assigned owners or resolve their assignment; it must not override it. Digest comparisons must account for the exact registered/running image identity, not `rpartition(':')`, which turns a digest into meaningless version text.

## Dual-schema API alignment

The independently planned API is compatible and should win over the inventory's earlier mandatory-selector sketch:

- `schema_id` omitted retains existing legacy schema lookup and audit/degrade semantics.
- An explicit approved `schema_id` selects only that artifact and fails closed on unknown, missing, corrupt or invalid provenance. It never silently selects the default schema.
- Selection and validation mode remain separate. Explicit selection does not itself mean reject every schema validation error in audit mode; **staged generation and activation explicitly pass `enforce=True`**. The explicit release path must propagate selection/load/validation failures rather than catch them as a legacy regeneration fallback.
- Ordinary hot patches use active schema; staged merge/prune/gate uses target schema. Legacy unassigned callers omit the selector. A release registry can describe legacy observed runtime for migration evidence without forcing every existing owner onto the strict explicit-selector behavior.

Two conflicts to prevent: (1) implementing every resolved default release as an explicit schema selection would change legacy missing-artifact/audit behavior; (2) changing desired assignment before establishing the owner reservation would allow an ordinary reprovision to read target image while still using active old config. Reserve+assign is one transaction under the existing writer guard.
