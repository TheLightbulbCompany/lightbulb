## 2. What a joined agent can read and write today

One tool spec for the engine's MCP server and the hosted MCP (`network_tools.json`; cli `src/mcp/tools.json`). Network tools always; workspace tools only while the computer is signed in (`lightbulb login`), acting in the browser's active workspace (#4413).

| Tool | Reads | Writes | Needs sign-in |
|---|---|---|---|
| `find_sessions` | sessions this computer can message (own first, then teammates'), search + limit | — | no |
| `send_message` | — | text to a session (`session_id`), a room (`room_id`) or a person; `reply_to`; returns a receipt; refuses `*`, `person/*`, repo-wide | room/person targets: yes |
| `message_receipt` | one receipt's state | — | no |
| `check_inbox` | waiting messages for this session (wait up to 30 s) | marks taken | no |
| `wake_me` | — | registers a webhook for a hosted bot (hosted MCP only) | yes (apps page) |
| `find_rooms` | the workspace's rooms | — | yes |
| `read_messages` | a room's messages | — | yes |
| `find_tasks` / `read_task` | the Paperclip task board | — | yes |
| `update_task` | — | task fields / comments | yes |
| `use_browser` | — | drives the workspace's cloud browser | yes |

Not available to a network session: workspace memory (no tool, no endpoint; see §3), another session's transcript, files, the agent's own conversation on another computer. The engine never has a memory of its own: `state.db` keeps message rows for receipts and loop limits, and deletes text once read.

## 4. Skills, session sharing, approvals (facts)

- **Skills.** A Lightbulb agent's skills are the Hermes skills index: our `lightbulb` and `paperclip` skills plus 58 bundled Hermes skills from the image (`/opt/hermes-skills`), each description cut to 60 chars, body loaded with `skill_view` on demand. The Skills tab "browses and enables the skills your workspace ships with". An agent can be asked to "turn a workflow into a skill" and saves it to its own workspace (`skills-and-automations.md`); the review fork can write skills (`turn.py:3989`). **Nothing turns a session, trace or solved task into a skill on its own**, and no skill crosses from one agent to another or from a laptop session to the workspace (grep for promote/distill found only the Beacon note). The marketplace is for hiring agents (curated `atlas`, `friday` with SOUL/IDENTITY/AGENTS.md and manifests), not for skills. Credentials ship as rail skills (shopify, instagram, vercel `SKILL.md` + `token.sh`).
- **Session sharing** (Mac app only; the `lightbulb` plugin and the engine do not share sessions). One link per session, audience `workspace` or `anyone`; "anyone" links show the live terminal view-only with no sign-in, **20 concurrent viewers** (`MAX_LINK_VIEWERS`), 120 seats per ten minutes; sessions with no terminal (Claude app, Codex app, IDE, SDK) are never public. **Pick up** (members, Claude only; `session_pickup` refuses other providers) and **Continue** (`lightbulb continue '<link>'`, a redacted copy of a Claude Code session into the taker's own workspace, off by default). Codex can be watched and typed into, not picked up. Events `share_link_created`, `share_link_opened` (signed-in only), `session_picked_up`. (docs/marketing/06-referrals-and-loops.md)
- **Approvals.** In the workspace: plans, spend and hires arrive as approval cards in the room ("Needs you"); the 14 Oct policy (docs/marketing/24) says who decides what and that a rejection must carry a comment. On the network: nothing is held; the only prompt is a permission request the Lightbulb app files (`held/approve/decline`). The 24 Oct "first message from a stranger is held, native Allow/Decline" (AgentRelay note row 7) was superseded by the 27 Oct flat ruling; `network_member.py` still carries `HOLD_*` code for the app-filed prompts.

## 6. Gaps that matter against a "memory for coding agents" product (no solutions)

1. A network session (Claude Code, Codex, Cursor, Grok CLI, OpenCode on a laptop) has no memory from Lightbulb at all: it cannot read or write the workspace memory, and the engine keeps nothing but message rows. The only "memory" a laptop agent gets is a message someone sent it.
2. The workspace memory is written only from Hermes turns in rooms and DMs. What a coding session did (commands, edits, corrections, what worked) never enters it, even for a workspace member's own laptop.
3. There is no capture of the session itself. Hooks report presence, "doing" and hand over mail; they do not record prompts, tool calls or edits, locally or anywhere. Beacon's entire product rests on that capture.
4. Memory is facts extracted by AgentCore's generic strategy, not reviewed lessons with a kind (workflow, correction, gotcha, convention), evidence or provenance. A person can confirm, share or delete, but cannot write, edit or see where a fact came from.
5. Nothing becomes a skill without a person asking an agent to write one; nothing moves a skill between agents, from a laptop to the workspace, or between teammates.
6. Memory is one workspace, one pool: no per-project or per-repo scope, no cross-workspace or personal portable memory; a solo network user (no workspace) has none.
7. The recall path is single-shot and lossy: five records per turn, query polluted by routing JSON, duplicates in storage, no ranking by recency or confirmation, no "context for this task" view.
8. No measurement: nothing records memory hits, misses, cost per workspace or whether a recalled fact was used; the only cost signal anywhere is inference through the openrouter-gate, and network messages carry no cost at all.
9. The security boundary between members' private memory is IAM plus "product boundary, not security boundary"; the backend-mediated hard boundary from the design is open.
10. Session sharing (the one place a teammate sees a laptop session) is Mac-app only, Claude-only for pick-up, 20 viewers, and never public for app/IDE sessions; it is a live view, not a record.
11. The stated plan of record is to integrate Beacon's telemetry rather than build it (§4 of the 21 Oct note), and to defer "session into a team skill" until spend and admin work show pull. That ordering predates the 26–27 Oct messaging repositioning and Beacon's own pivot to memory.
