# Security of agent-to-agent networks: primary-source findings (1 Nov 2026)

Quotes are verbatim from the fetched pages unless marked paraphrase. `[secondary]` = not an owning source.

## What matters for a cross-vendor agent network (summary)
- A2A authenticates the *calling client* (HTTP-layer credentials) and leaves "who is the human behind this" to the implementer. Its own text: "Identity information is handled at the protocol layer, not within A2A semantics." Nothing in A2A carries an originating principal across hops.
- A2A itself warns that in-band credential exchange "can allow credentials to be passed across chains of multiple A2A agents", and that `auth-required` is not authorization.
- Agent Cards can be JWS-signed, but verification is only SHOULD, and a signature proves who published the card, not who is asking.
- MCP's rule is the opposite of pass-through: tokens must be audience-bound and a server "MUST NOT accept or transit any other tokens." A hop must mint its own token, not forward the caller's.
- The standards that carry a chain (RFC 8693 `act`, ID-JAG `act`) say prior actors "are informational only" for access control. The delegation trail exists in the token but policy ignores it by design.
- OWASP names your exact incident class: ASI03 "Cross-Agent Trust Exploitation (Confused Deputy)" and "Synthetic Identity Injection". Its fix: re-verify every privileged step against the original user's intent, bind tokens to a signed intent (subject, audience, purpose, session).
- Measured: cross-agent injection spreads. Prompt Infection: self-replication works through a chain of agents; a 2026 worm paper reports 63% aggregate ASR; a 2026 multi-agent paper reports message signing + provenance cut inter-agent injection 91%.
- Identity products (Entra Agent ID, Okta XAA) attest *which agent/app and which user within one enterprise trust domain*. None attest that a message between two people's agents reflects that person's real request. SPIFFE explicitly does not prove the caller is not hijacked.
- Real incidents show one pattern: a token or tool with broad reach plus attacker-controlled text, and no check tying the action to the human's intent.

## 1. Google A2A protocol (spec at a2a-protocol.org/latest/specification)
- Identity is out of band: "Identity information is handled at the protocol layer, not within A2A semantics." (s7) [spec](https://a2a-protocol.org/latest/specification/)
- Transport: "Production deployments MUST use encrypted communication (HTTPS for HTTP-based bindings, TLS for gRPC)." (s7.1) [spec](https://a2a-protocol.org/latest/specification/)
- Server duties: "MUST authenticate every incoming request based on the provided credentials and its declared authentication requirements." (s7.4); "Once authenticated, the A2A Server authorizes requests based on the authenticated identity and its own policies." (s7.5). Authorization policy is the server's own; the spec defines no policy model. [spec](https://a2a-protocol.org/latest/specification/)
- Servers "MUST NOT reveal the existence of resources the client is not authorized to access" (s3.3.2); ListTasks "MUST return only tasks visible to the authenticated client" (s3.1.4). Scoping is per authenticated *client*, not per end user. [spec](https://a2a-protocol.org/latest/specification/)
- s13.1: "Implementations MUST ensure appropriate scope limitation based on the authenticated caller's authorization boundaries." and "Authorization checks MUST occur before any database queries or operations that could leak information". [spec](https://a2a-protocol.org/latest/specification/)
- Task states include `TASK_STATE_AUTH_REQUIRED` ("authentication is required to proceed. This is an interrupted state") and `TASK_STATE_REJECTED` ("the agent has decided to not perform the task"), plus INPUT_REQUIRED, COMPLETED, CANCELED, FAILED. [spec s4.1.3](https://a2a-protocol.org/latest/specification/)
- In-task authorization (s7.6): "A2A provides the capability for agents to delegate the fulfillment of this authorization to the client". s7.6.3: "In-band credential exchange can allow credentials to be passed across chains of multiple A2A agents". s7.6.4: "The A2A protocol does not define the scope, representation, validity, or revocation semantics"; "Agents MUST NOT treat the `TASK_STATE_AUTH_REQUIRED` state transition, by itself, as authorization"; it "MUST NOT be assumed to authorize subsequent messages on the Task". [spec](https://a2a-protocol.org/latest/specification/)
- Agent Card: "A JSON metadata document published by an A2A Server, describing its identity, capabilities". Clients "SHOULD validate capability support by examining the Agent Card" (s3.3.4). [spec](https://a2a-protocol.org/latest/specification/)
- Card signing (s8.4): "Agent Cards MAY be digitally signed using JSON Web Signature (JWS)", canonicalized with JCS; "Clients SHOULD verify at least one signature before trusting an Agent Card"; "Expired or revoked keys MUST NOT be used for verification"; keys "SHOULD be retrieved over secure channels (HTTPS)". Signing is optional and verification is SHOULD. Trust anchor for the signer's key is not defined in what I read. [spec](https://a2a-protocol.org/latest/specification/)
- Extended card (s3.1.11, s13.3): the call "MUST require authentication", "MAY return different details based on client authentication level"; "Extended cards SHOULD NOT include sensitive information that could be exploited if leaked"; only available if the public card declares `capabilities.extendedAgentCard`. [spec](https://a2a-protocol.org/latest/specification/)
- Left to implementers: how the credential is issued, what the end user is, delegation semantics, revocation, and what the receiving agent's LLM does with message content. The only security instruction about that is s1.1: "relying on standard web security practices". [spec](https://a2a-protocol.org/latest/specification/)
- I did not find an A2A field for "on behalf of user X" in the sections read (fetch covered chars 0-256k of 256k but via a summarizer; absence is not proven).

## 2. MCP authorization, token rules, ID-JAG
- Authorization is optional: "Authorization is **OPTIONAL** for MCP implementations." STDIO "SHOULD NOT" use it. [MCP authorization (draft)](https://modelcontextprotocol.io/specification/draft/basic/authorization)
- Audience: "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience, according to RFC 8707". The `resource` parameter "MUST be included in both authorization requests and token requests" and "MUST identify the MCP server that the client intends to use the token with." [MCP authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization)
- No pass-through: "MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server." "MCP servers **MUST** only accept tokens that are valid for use with their own resources." "MCP servers **MUST NOT** accept or transit any other tokens." [MCP authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization)
- Token passthrough is "an anti-pattern"; risks listed: security control circumvention, accountability gaps ("downstream Resource Server's logs may show requests that appear to come from a different source"), trust boundary issues. Mitigation: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." [Security best practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Confused deputy in MCP is specifically the OAuth-proxy case: static client ID + dynamic client registration + consent cookie + no per-client consent. Mitigation: "MCP proxy servers **MUST** implement per-client consent". It is about OAuth consent, not about LLM-mediated delegation. [Security best practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Scope minimization section: stolen broad tokens give "lateral data access, privilege chaining". [Security best practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Enterprise-Managed Authorization is an official extension `io.modelcontextprotocol/enterprise-managed-authorization`, normative text in github.com/modelcontextprotocol/ext-auth. I read only the docs page summary via search; the IdP issues an ID-JAG, the MCP server's AS trades it for an access token, no user redirect. [ext docs](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization) (search-result summary; spec file not opened)
- ID-JAG carries (IETF draft-ietf-oauth-identity-assertion-authz-grant): `iss` (IdP), `sub` (end user, in IdP-chosen namespace for the target), optional `sub_id`, `aud` (the resource AS, exact match), `client_id` (client's id at the resource AS), `jti`/`exp`/`iat`, optional `resource`, `scope`, `authorization_details`, and optional `act`, `tenant`, `aud_tenant`, `auth_time`, `acr`, `amr`, `email`, `aud_sub`. Header `typ` MUST be `oauth-id-jag+jwt`. Built on RFC 8693 + RFC 7523. [IETF draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/)
- What it does not carry: it is one hop (client -> IdP -> resource AS). It asserts which user and which client; it does not assert what the user asked for. Safeguards read: RAS "MUST reject a request that has neither client authentication nor a sender-constrained ID-JAG"; RAS may enforce single use via `jti`; tenant isolation of subjects. Section 9 was cut off in my fetch. [IETF draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/)
- Both parties must share one IdP the target already trusts for SSO. A cross-company or person-to-person agent network has no such IdP. (my inference from the abstract: "an identity provider that the target system already trusts for single sign-on")

## 3. Multi-hop delegation, RFC 8693, originating principal
- Delegation vs impersonation (s1.1): "When principal A impersonates principal B, A is given all the rights that B has within some defined rights context." "With delegation semantics, principal A still has its own identity separate from B." [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)
- Chain: "The outermost act claim represents the current actor while nested act claims represent prior actors." (s4.1) [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)
- The loss of the originating principal is built into policy: prior actors "are informational only" and "are not to be considered in access control decisions." (s4.1) [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)
- `may_act` "makes a statement that one party is authorized to become the actor" (s4.4): a pre-authorization of who may act for the subject. [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)
- WSO2's individual draft (draft-oauth-ai-agents-on-behalf-of-user-02, Informational): `act` REQUIRED with `sub`; chain is flat: user, client (`azp`), one agent. It "does not address" agent-to-agent chains; a resource server "can be ... another agent" but no re-delegation. Not adopted by the WG as far as I could see. [IETF draft](https://www.ietf.org/archive/id/draft-oauth-ai-agents-on-behalf-of-user-02.html)
- OWASP calls this out as an attack, not just a gap: "A compromised low-privilege agent can relay valid-looking instructions to a high-privilege agent, which executes them without re-checking the original user's intent". [OWASP ASI](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) (text read from the PDF it links)
- I found no primary source that uses the phrase "originating principal". Treat that as my term for the property above.

## 4. Cross-agent prompt injection
- Prompt Infection (Lee, Tiwari, arXiv 2410.07283): malicious prompts "self-replicate across interconnected agents, behaving much like a computer virus"; harms: data theft, scams, malware, content manipulation. Data theft needs at least three agents with distinct roles (document reader, CSV/db, web/email) cooperating. [arXiv PDF](https://arxiv.org/pdf/2410.07283)
- Measured: self-replicating beat non-replicating by 13.92% on GPT-4o and 209% on GPT-3.5 (global messaging); success about 20% lower under local messaging because it fails when one agent isn't compromised; replication is "the only scalable method for compromising more than two agents" in local-messaging scenarios. [arXiv PDF](https://arxiv.org/pdf/2410.07283)
- Stronger model != safer: GPT-4o ignored 66% (self-rep) / 54% (non-rep) attacks vs GPT-3.5's 9% / 20%, but once compromised executes the malicious tasks better. [arXiv PDF](https://arxiv.org/pdf/2410.07283)
- Social simulation: full infection of 10 and 20 agent populations at about 47% and 31.5% of total turns; 30/40/50 agents at about 23.3/24.2/21.4% of turns (logistic growth). [arXiv PDF](https://arxiv.org/pdf/2410.07283)
- Defense: "LLM Tagging" (prepend a marker naming the origin of each agent response) alone cuts ASR by only 5%; Marking alone "still permits 76% of attacks" (authors then built a counterattack that neutralized marking); Marking + Tagging blocked all attacks, Instruction Defense + Tagging left 3%, Sandwich + Tagging 16%. Authors say no defense works in isolation. [arXiv PDF](https://arxiv.org/pdf/2410.07283)
- Ferrag et al. survey (arXiv 2506.23260v2): threat matrix lists, for A2A: Agent Discovery Spoofing (workflow hijacking; mitigation "Signed discovery responses; authenticated peer discovery"), Rogue Agent Registration ("Agent whitelisting; strict onboarding"), Cross-Agent Prompt Injection ("Cascading malicious actions across agents"; "Input isolation; per-agent validation"), Credential theft/proxy abuse ("Token audience binding; explicit delegation checks"). It is a survey; it adds taxonomy, not measurements of its own for A2A. [arXiv PDF](https://arxiv.org/pdf/2506.23260)
- 2026: AgentWorm (arXiv 2603.15727; the search snippet called it "ClawWorm"): self-replicating worm against OpenClaw (40,000+ instances); one message starts an autonomous cycle that rewrites the victim's config and spreads to peers; 63% aggregate ASR across 5 LLM backends, 3 infection vectors; "the controls capable of stopping the infection loop were not enabled in any observed deployment." Cross-framework test on Hermes Agent. [arXiv abstract](https://arxiv.org/abs/2603.15727)
- 2026: Paul & Nandy, "Beyond Single-Model Injection" (arXiv 2609.22949): 14 vectors incl. 4 inter-agent message-passing; 6-agent system: 31.2% injection success undefended to 4.2% with four architectural defenses; message signing with provenance cut inter-agent injection 91%; privilege-scoped tools eliminated privilege escalation; anomaly detection caught 84% of cascading attempts; 67% of agents had a scope violation despite system-prompt guardrails. Author-run lab numbers on their own system. [arXiv abstract](https://arxiv.org/abs/2609.22949)

## 5. OWASP Top 10 for Agentic Applications 2026 (ASI)
List (from the PDF): ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain, ASI05 Unexpected Code Execution, ASI06 Memory & Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents. [OWASP PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- ASI03: "exploits dynamic trust and delegation in agents to escalate access and bypass controls by manipulating delegation chains, role inheritance, control flows, and agent context". "Agent-to-agent trust or inherited credentials can be exploited to escalate access, hijack privileges, or execute unauthorized actions." "Without a distinct, governed identity of its own, an agent operates in an attribution gap that makes enforcing true least privilege impossible." Maps to T3 Privilege Compromise (Agentic Threats & Mitigations guide). [OWASP PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- ASI03 examples: Un-scoped Privilege Inheritance; Memory-Based Privilege Retention; Cross-Agent Trust Exploitation (Confused Deputy); TOCTOU in agent workflows; Synthetic Identity Injection ("unverified descriptors (e.g., 'Admin Helper') to gain inherited trust"); Forged Agent Persona (fake agent in an A2A registry with a forged card); Identity Sharing ("allows other users to leverage that identity implicitly by invoking its tools as that identity") - this last is close to the Friday/Aden shape. [OWASP PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- ASI03 mitigations: task-scoped time-bound permissions; per-action authorization via a policy engine; human approval for privilege escalation; "Define Intent: Bind OAuth tokens to a signed intent that includes subject, audience, purpose, and session. Reject any token use where the bound intent doesn't match the current request."; "Prevent privilege inheritance across agents unless the original intent is re-validated." [OWASP PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- ASI07: "Weak inter-agent controls for authentication, integrity, confidentiality, or authorization let attackers intercept, manipulate, spoof, or block messages." Examples: replay on trust chains; "protocol downgrade and descriptor forgery, causing authority confusion"; "A2A registration spoofing: An attacker registers a fake peer agent in the discovery service using a cloned schema". Mitigations: mutual auth with per-agent credentials; "Digitally sign messages, hash both payload and context"; nonces/session ids/timestamps tied to task windows; "bind protocol authentication to agent identity". Maps to T12 Agent Communication Poisoning and T16 Insecure Inter-Agent Protocol Abuse. [OWASP PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- ASI08 (cascading failures), ASI09 (human-agent trust), ASI10 (rogue agents): titles confirmed, text not extracted by me.

## 6. Incidents
- Salesloft Drift (GTIG, 26 Aug 2025, updated 28 Aug): UNC6395 used stolen OAuth tokens of the Drift third-party app to export Salesforce data from many orgs (8-18 Aug), searching for AWS keys (AKIA), passwords, Snowflake tokens. Aug 9: Drift Email tokens used to read a few Google Workspace mailboxes. Salesloft and Salesforce revoked all Drift tokens 20 Aug. How tokens were first stolen: not stated in that post. Missing control: long-lived broad-scope bearer tokens held by an intermediary, no IP restriction ("IP Relaxation" advice), no sender-constraint. GTIG: "treat any and all authentication tokens stored in or connected to the Drift platform as potentially compromised." [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift)
- EchoLeak, CVE-2025-32711 (M365 Copilot): NVD: "Ai command injection in M365 Copilot allows an unauthorized attacker to disclose information over a network." CWE-74; CVSS 9.3 (Microsoft) / 7.5 (NVD); published 2025-06-11. Chain per the academic paper abstract: crafted email evades the XPIA classifier; reference-style Markdown evades link redaction; auto-fetched images carry data; a Teams proxy allowed by the CSP is the exfil path. Missing controls: the paper recommends prompt partitioning, provenance-based access control, strict CSP, least privilege. Aim Security's own blog returned 403 and the MSRC page did not render. [NVD API](https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2025-32711), [arXiv 2509.10540](https://arxiv.org/abs/2509.10540)
- ServiceNow Now Assist second-order injection (AppOmni): a low-privileged user put a prompt in a ticket field; when an admin invoked a reader agent, it discovered and delegated to a "Record Management" agent, which copied a ticket the attacker could not read into one they could, under the *admin's* privileges, with prompt-injection protection enabled. Defaults enabling it: agents on the same virtual-agent team and "marked as being discoverable by default when published"; agents run with the initiating user's privileges. ServiceNow "confirmed the behaviors were intended" and updated documentation. Missing control: no binding of delegated action to the original requester's intent; agent-to-agent discovery open by default. [AppOmni](https://appomni.com/ao-labs/ai-agent-to-agent-discovery-prompt-injection/)
- GitHub MCP private-repo leak (Invariant Labs, May 2025): attacker's issue in a public repo; user asks agent to review open issues; agent pulls private repo data into context and posts it in a public PR. Missing control per Invariant: granular permissions (e.g. one repo per session); confirmation prompts failed because users pick "Always Allow". Pattern named "toxic agent flow". [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)
- 2026 incidents: none verified by me. AgentWorm (section 4) is a lab result, not an in-the-wild incident.

## 7. Agent identity frameworks (what is actually attested)
- Entra Agent ID: agent identities are Entra accounts distinguishing "operations performed by AI agents from operations performed by workforce, customer, or workload identities"; agents can act autonomously or with "Delegated access... on behalf of human users"; and "Authenticate incoming messages: Agents can accept requests from other clients, users, and agents... secured using access tokens issued by Microsoft Entra ID, allowing the agent to reliably identify the caller". A creator is recorded as "sponsor". It attests tenant-managed identity of the agent and, with OBO, the user token; it does not attest the content or intent of a message. [Microsoft Learn](https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/what-is-agent-id)
- Entra OBO flow: user token Tc must have `aud` equal to the agent blueprint; blueprint obtains T1 with its credential; agent identity does the OBO exchange; Entra validates both. Agents "aren't supported for interactive (`/authorize`) flows", so child agents inherit pre-authorized permissions via the blueprint; "inheritance works only within tenant boundaries". Doc page does not describe agent-to-agent re-delegation chains. [Microsoft Learn](https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-on-behalf-of-oauth-flow)
- Okta (Cross App Access for AI agents): agent exchanges its ID token for an access token at the resource app via ID-JAG, governed by "administrator-defined policies" instead of user consent. The support article says little about what is attested (agent ownership/ID-JAG contents not described there). Datadog's doc shows the resulting token is the initiating user's. [Okta support](https://support.okta.com/help/s/article/understanding-cross-app-access-with-okta-for-ai-agents) ; Datadog and Auth0 doc pages [secondary, seen only via search summary]
- SPIFFE: "A SPIFFE ID is a string that uniquely and specifically identifies a workload"; an SVID "is considered valid if it has been signed by an authority within the SPIFFE ID's trust domain". "it is _assumed_ that a workload is sufficiently well isolated from other workloads" and the robustness of isolation is "beyond the scope of SPIFFE". JWT-SVIDs are replayable ("tokens are susceptible to replay attacks"). So it attests workload identity within a trust domain, not the integrity of what the workload's LLM was told. SPIRE node/workload attestor details not read. [SPIFFE concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/)
