## The meta-finding the spec never states out loud

**Hermes is a single-tenant, single-host, local-first daemon that Isol8 wants to run as a multi-tenant, network-exposed, NFS-backed, frequently-redeployed managed service — and almost every one of its convenient local-first behaviors becomes a *hazard* under that inversion.** The spec treats Hermes as "OpenClaw with a different wire protocol." It is architecturally the opposite shape: outbound-by-default, host-credential-foraging, in-memory run state, flock-on-disk locking, off-by-default inbound surface. The eight items below are each a specific manifestation of that single mismatch, and the spec's §10 effort table prices *none* of them as net-new work.

## Top 8 unknown-unknowns (evidence + severity)

### 1. `/v1/runs` state is 100% volatile in-process Python — and the SQLite single-writer fix the spec relies on *guarantees* runs get orphaned. [SEVERITY: CRITICAL — CONFIRMED, and I escalate it]

All run lifecycle state lives in plain instance dicts on the adapter: `_run_streams`, `_active_run_agents`, `_active_run_tasks`, `_run_statuses`, `_run_approval_sessions` (`gateway/platforms/api_server.py:658-671`, read this pass). No DB row, no requeue, no recovery for the `/v1/runs` path — only `/v1/responses` (`ResponseStore`) and `SessionDB` persist.

**Where I go further than the interim report (A15):** the report lists this as a standalone risk. The sharper finding is that it *collides head-on with the spec's own EFS-safety remediation*. The spec mandates single-writer `maxPercent=100` redeploys (§6/§7) to avoid SQLite corruption — which means **every config push, image bump, key rotation, or runtime-switch is a hard task replacement that silently drops every in-flight run with no terminal frame ever emitted.** The two load-bearing mitigations (single-writer ECS + in-memory runs) are mutually antagonistic. Any redeploy = guaranteed orphaned runs. The backend must drain runs before any deploy, AND the client watchdog must treat "no terminal event, ever" as a first-class state (not a timeout to retry into a 404). The spec budgets neither.

### 2. The gateway's own boot/singleton lock is `fcntl.flock` on EFS — the single primitive the entire single-writer corruption story rests on is the one Isol8 documented as a no-op on NFS. [SEVERITY: CRITICAL — CONFIRMED]

`acquire_gateway_runtime_lock()` locks `gateway.lock` via `fcntl.flock(handle.fileno(), LOCK_EX | LOCK_NB)` (`gateway/status.py:329`, read this pass), and that lock file path resolves to `get_hermes_home() / "gateway.lock"` (`gateway/status.py:50-55`) — i.e. on EFS under the spec's `HERMES_HOME → EFS access point` layout. CLAUDE.md is explicit: Isol8 uses `fcntl.lockf` *because* `flock` is "incompatible with NFS." So the daemon's "only one gateway per home" guard can **fail-open** on EFS: if two ECS tasks ever share the access point (the exact scenario `maxPercent=100` exists to prevent, but which any console-driven or partial deploy can re-create), both believe they hold the lock and both run — corrupting `state.db`/`kanban.db`. The spec's §7 WAL note covers the *databases* but never notices that the *lock guarding them* is itself NFS-unreliable. The single-writer story has a hole at its foundation. (The token-scoped locks at `status.py:63-69` are deliberately machine-local under `XDG_STATE_HOME` and are fine — it is specifically `gateway.lock` that is on EFS.)

### 3. api_server is OFF by default and silently no-binds — a Hermes container can boot, pass `/health` internally, and have **zero** Isol8-reachable port. [SEVERITY: HIGH — CONFIRMED]

`Platform.API_SERVER` is only constructed if explicitly enabled in config; `gateway/run.py:5522-5527` builds `APIServerAdapter(config)` only when the platform is enabled, and the shipped example config leaves the whole `platforms:` block commented out. Then the adapter `return False`s (does not bind) when `is_network_accessible(self._host) and not self._api_key` (`api_server.py:3433-3441`, read this pass). So three EFS/env preconditions must ALL be satisfied at provision time — `platforms.api_server.enabled: true` (in EFS `config.yaml`), `API_SERVER_HOST=0.0.0.0` (or task IP), and `API_SERVER_KEY` (≥8 chars, non-placeholder) — or the only inbound surface never comes up. The spec §3/§7 calls out only the *key*. A missing host or a forgotten `enabled` flag produces a container that looks healthy (the daemon is up, outbound bot loops run) but is silently unreachable by the backend — a failure mode with no error, just a dial timeout. This is the kind of thing that passes the first dev test (because someone set it by hand) and breaks the automated provisioner.

### 4. Hermes forages host-ambient credentials AND writes rotated tokens back to host files — a cross-tenant-bleed primitive that must be *actively disabled*, not merely "not used." [SEVERITY: HIGH — CONFIRMED, and I sharpen the write-back half]

`agent/credential_sources.py:4-13` (read this pass) enumerates the seed sources: `env:<VAR>`, `~/.claude/.credentials.json`, `~/.hermes/.anthropic_oauth.json`, `~/.qwen/oauth_creds.json`, `auth.json` device-code providers, `gh auth token`, custom-provider config. The interim report (A4) captures the *read* side. The part that would actually blindside an engineer is the **write-back**: on refresh, the pool calls `_write_claude_code_credentials(...)` to keep `~/.claude/.credentials.json` "in sync so other profiles see the latest tokens" (`agent/credential_pool.py:767-773` and again at `848-874`, read this pass). So a Hermes container that ever sees a host `~/.claude` will *mutate* it. The spec's clean "container-owns, no write-back, DDB=seed" (Q3) is true **only** for the `providers.openai-codex` path — the credential-pool path forages and writes back. In a shared base image or a misconfigured HOME this is a credential-bleed surface. The port must ship the image with these paths absent and the pool host-foraging suppressed — unbudgeted hardening, and a security-review finding waiting to happen. **Divergence from spec:** the spec's entire §3 auth model is about the backend↔container hop and says *nothing* about where Hermes sources credentials on the host filesystem, which is the real hosted-multi-tenant risk.

### 5. `/api/jobs*` is a full cron CRUD + trigger surface mounted on the same port, gated by the *same single bearer* as chat. [SEVERITY: MEDIUM-HIGH — CONFIRMED]

The route table mounts 8 cron routes — `GET/POST /api/jobs`, `GET/PATCH/DELETE /api/jobs/{id}`, `POST .../pause|resume|run` (`api_server.py:3410-3417`, read this pass) — immediately adjacent to the `/v1/runs` family, all behind the single `_check_auth` bearer. There is no separate auth tier, no per-route scope, no per-tenant scoping anywhere. **Why this is an unknown-unknown and not just "noted":** anyone who holds `API_SERVER_KEY` gets full scheduled-execution control over the user's agent (create a cron job that runs arbitrary `terminal()` on a schedule). That is fine *iff* only the backend ever holds the key — but it dramatically widens the blast radius of a single leaked key (a leaked Bearer is not "read one user's chat," it's "schedule persistent code execution in their container"), and it must be in the threat model the spec doesn't have. The spec's §3 enumerates what auth Hermes *lacks*; it never enumerates what a single key *grants*, which is: everything, including durable cron.

### 6. The webhook adapter is a built-in HMAC-validated inbound + push-back-delivery rail the spec's bespoke ~400-600 LoC npm transport (WS7) never evaluated. [SEVERITY: MEDIUM — CONFIRMED — this is the one place budget can be *returned*]

`gateway/platforms/webhook.py` is a generic aiohttp server whose `send()` routes the agent's reply back to a configured destination — `github_comment`, or any platform/plugin via `_deliver_cross_platform` (`webhook.py:220-263`, read this pass), with delivery config stashed per-`chat_id` at receipt. Combined with the "Plugin Path" (drop a `plugin.yaml` + `adapter.py`, zero core changes — `ADDING_A_PLATFORM.md`), a Paperclip issue→run→comment-back binding could be a webhook route binding (no code) or a small plugin adapter — **not** the spec's implied bespoke npm transport. Crucially, push-back delivery also *sidesteps the SSE-orphan problem entirely* (agent finishes → server POSTs result, no live socket to drop). **Divergence from spec:** the spec's WS7 (1-2 wk) assumes a custom transport with no return address; this rail has a native return address. The spec should evaluate it before committing the budget — the single section where the project might get *cheaper*.

### 7. The image is heavy (Node + npm + Playwright Chromium) and does a per-boot small-file write storm onto EFS via `skills_sync`, with a lazy `uv pip install` re-paid every cold start, on a 0.5-vCPU box never re-validated for a subprocess-spawning Python agent. [SEVERITY: MEDIUM-HIGH — CONFIRMED]

`tools/skills_sync.py` runs on **every** boot (`docker/entrypoint.sh:103-105`, read this pass), syncing bundled skills into `$HERMES_HOME/skills` — i.e. a many-small-file write storm onto EFS at each cold start. This is the exact EFS small-file pain Isol8 already hit with OpenClaw's npx extract (`project_mcp_npx_efs_extract_stall`, `project_openclaw_mcp_npx_efs_extract_stall`). The image bakes Node + npm + `npx playwright install --with-deps chromium` (hundreds of MB) and keeps a hermes-writable `.venv` so `lazy_deps.py` can `uv pip install` optional packages at first use — which is in the *image* layer, lost on restart, re-downloaded over the network each cold start (same trap as `project_openclaw_mcp_cache_crashloop`). And the box: Isol8 already documents OpenClaw CPU-starvation crash-loops on the 0.5-vCPU box (`project_openclaw_mcp_connect_storm_crashloop`); `tini` exists in the Hermes image *specifically because it spawns many subprocesses*. The spec inherits OpenClaw's 512/2048 sizing by assumption (§7 says nothing about CPU/MEM). **Unit-economics risk:** if Hermes needs a bigger box, the $50 flat fee math changes.

### 8. The metering payload carries token integers only — zero USD — and there is no mid-run meter, so `check_budget()`-style pre-flight gating cannot be fed from the run stream. [SEVERITY: MEDIUM-HIGH — CONFIRMED]

The `run.completed` `usage` object is exactly three ints — `input_tokens`, `output_tokens`, `total_tokens` (`api_server.py:3046-3050`) — with no `cost_usd`. Cost *exists* on the agent (`session_estimated_cost_usd`) but is never copied into any api_server wire payload; only the *other* gateway (`tui_gateway`) emits cost, and even that is a local-table estimate that is `None` for self-hosted/OpenRouter routes. Usage is terminal-only — no usage field on `message.delta`/`tool.*`/`reasoning.available` — so there is **no mid-run token meter** to drive a real-time budget cutoff. **Why this is an unknown-unknown:** the spec's §8 says the adapter "must surface token `usage` from the `run.completed` event into `record_usage()`" — phrased as a wiring task, as if the payload were billing-complete. It is not. Isol8 must self-price from tokens + its own table (as it does for Bedrock), handle dual key naming (`input_tokens` vs `prompt_tokens` on the OpenAI-compat path), verify delegated-subagent cost rollup timing, and accept that pre-flight budget gating has no run-stream data source. This is net-new metering work the spec treats as free, and per-call token deltas also persist to a per-session SQLite on EFS — putting billing data on the same WAL/EFS hazard surface as items 1/2.

## Cross-cutting blindside not captured as a single numbered item

**The drift tax is mis-unitized and the lag-vs-security posture is self-contradictory.** Confirmed independently this pass: upstream commit `1a9ef8314 fix(security): require API_SERVER_KEY before dispatching API server work` (verified via `git show`) makes the key mandatory on *every* bind including loopback past `v2026.5.28` — so per-container key-gen + Secrets-Manager + Bearer-injection is **day-one mandatory scope**, not a drift contingency, and the "keyless loopback like OpenClaw" mental model is dead. Each Hermes release is 800-1300 commits (the report's 3-5 days/bump is right; the spec's 1-2 is off by several×). And the spec's "lag 1-2 releases for stability" directly conflicts with staying current on a `fix(security)` stream that ships as 1000-commit supersets you cannot cherry-pick — you cannot do both. I fully endorse the interim report here (A12); flagging it because it compounds every item above (each bump re-audits the auth, run-state, lock, and metering surfaces, all of which are moving).

## Verdict vs the interim report

The interim report's unknown-unknowns list (§4: volatile runs, webhook ingress, credential foraging, flock boot lock, cron CRUD, metering, off-by-default api_server) is **accurate and I confirm every item against source.** My additions/sharpenings:

1. **Items 1+2 are not independent risks — they are mutually antagonistic** (single-writer redeploy *causes* run orphaning). The report lists them separately; the build-blindside is their interaction.
2. **The credential hazard's write-back half** (`_write_claude_code_credentials`) is the part that turns "don't use it" into "must actively disable it in the image" — a security-review finding, not a config note.
3. **The cron-CRUD blast-radius framing**: the real point is what one leaked key *grants* (durable scheduled code exec), not merely that the route exists.
4. The report's effort recalibration to **~14-19 eng-weeks** is, if anything, still optimistic on the maintenance tail given the drift mis-unitization compounds across all eight surfaces.

Nothing here is a kill-shot — the architecture survives. But the spec's "~10-15 wk, OpenClaw-with-a-different-wire-protocol" framing systematically under-prices the single-tenant→multi-tenant inversion, and these eight are where it bites.
