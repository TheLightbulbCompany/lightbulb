# Hermes Runtime Option — Pressure-Test Report

**Date:** 2026-06-17
**Scope:** Adversarial synthesis of the 12 map* + 1 attack* pressure-test agents against the design spec `docs/superpowers/specs/2026-06-16-hermes-runtime-option-design.md`, grounded in `/Users/prasiddhaparthsarthy/Desktop/hermes-agent @ basis-v0.14.0-spec (4c46c35e)` and this repo's `apps/{backend,frontend,infra}`.
**Posture:** Deliberately uncharitable. Every claim cites a `file:line` an agent read.

---

## 1. Bottom line (≤6 sentences)

The spec is **technically careful and mostly survives contact** — its four headline falsifications (one-file auth, Nous-only proxy, dead `_OPENCLAW_RUNTIME_STATE_DIRS`, no `workspace` run field), its auth-hop topology, its SSE non-resumability, and its 4-WS-client consolidation surface all re-confirm against source. But the **biggest crack is architectural and changes the shape of the project**: Hermes has **no first-class multi-agent model at all** — one daemon is one persona/one SOUL, the session-key grammar hardcodes the literal `agent:main`, and the developers' own comment calls one-daemon multi-agent a *future* feature (`map02`; `gateway/run.py:1017-1040`, `gateway/status.py:5-12`). The spec acknowledges "personalities are daemon-global" but then quietly papers a full `Runtime` port (`list_agents`/`create_agent`/`list_sessions(agent_id)`/`export_agent`) over a runtime where `agent_id` **is not a real key** — every notion of "which agent" must move *into the Isol8 backend* as backend-held convention over a single shared daemon, which is materially more backend work than "render the persona into a different on-disk shape." Two further surprises also harden the project: the `run.completed` `usage` payload the metering hook is wired to carries **only three token integers and zero USD cost** (`map12`; `api_server.py:3046-3050`), and pinning *any* Hermes newer than the basis re-arms a mandatory `API_SERVER_KEY` and re-pays a 1000+-commit-per-release audit tax (`map11`/`attack07`). It is **still a ~10-15wk *build*, but the maintenance tail and the backend-side agent-identity layer are under-budgeted** — realistically **~14-19 eng-weeks** once the agent-identity backend layer, the metering self-pricing, the EFS/flock hardening, and the heavier per-bump audit are priced in.

## 3. The multi-agent finding (headline)

**Hermes has no first-class multi-agent model. One daemon = one persona, one SOUL, one session namespace literally hardcoded as `agent:main`.** (`gateway/run.py:1017-1040` — `_parse_session_key` only matches `parts[0]=="agent" and parts[1]=="main"`; `gateway/status.py:5-12` — the devs call one-daemon-multi-agent "a property that **will be useful when we add named profiles (multiple agents running concurrently)**"; `hermes_cli/profiles.py:235-237` — `active_profile` is a single on-disk name.) The only "two agents at once" mechanism is `delegate_task`, which spawns **ephemeral, non-addressable child workers** (`tools/delegate_tool.py:133,153`), the opposite of two persistent peers an orchestrator routes to by name.

**The spec is honest that personalities are daemon-global** (§2 Q5, line 122) and that Friday/Atlas must be simulated via per-call `ephemeral_system_prompt`. What it under-states — and what changes the design — is the **consequence**: the §4 `Runtime` port advertises `list_agents`, `create_agent`, `list_sessions(agent_id)`, `export_agent`, `seed_owner_agents` as facets a Hermes adapter "implements." On the Hermes side **`agent_id` is not a real key.** These facets cannot be *implemented against Hermes*; they degrade to "which persona string + which `session_id` prefix the backend chooses to send." That means:

**Design consequence for §4/§5:**
- The "two interchangeable adapters behind one port" framing holds for the **Transport** facet (chat send / events / approval) but **breaks for the agent-model facets**. `list_agents`/`create_agent`/`list_sessions(agent_id)` must be reframed as **generic-layer, backend-held state** that the Hermes adapter *services from a backend agent registry*, NOT delegates to the daemon. OpenClaw resolves these server-side (`agents.list[]`); Hermes cannot.
- Real net-new backend work the spec doesn't budget: a **per-owner agent registry** (persona text, per-agent skills/MCP/cron mapping, per-agent session-prefix convention, marketplace-agent identity) living in Isol8's own store, re-sent on **every single `/v1/runs`** (the persona is not persisted server-side — `map03:231-256` confirms the gateway rebuilds the agent from history per message). This is closer to "build a thin agent-orchestration layer in the backend" than "render a profile into a different file." Add it to workstream 1/2.
- §5's `seed_owner_agents` for Hermes correctly "does NOT write per-agent identity files" — but it should be explicit that there is **nothing to seed on the Hermes side at all**; seeding is a no-op and the persona lives only in the backend registry. Marketplace deploy (§9) likewise creates no Hermes agent — it adds a backend registry entry + a skills/MCP/config merge.

This is the single finding most likely to move the estimate and re-shape the architecture diagram.

## 4. Newly-surfaced risks / unknown-unknowns (not in the spec)

1. **`/v1/runs` state is fully volatile (A15).** No DB row, no requeue. An ECS task replacement / image deploy / OOM kill silently drops the user's running agent with **no terminal event ever delivered** (`map01`, `api_server.py:658-671`). The spec's single-writer-redeploy posture (needed for SQLite) directly collides with this — every redeploy orphans in-flight runs. Runtime-switch and key-rotation must *drain* runs first or accept silent drops.
2. **The webhook adapter is a missed first-class ingress (A6).** `gateway/platforms/webhook.py` already does HMAC-validated inbound + **push-back delivery** + a zero-core plugin path (`ADDING_A_PLATFORM.md`). The spec's bespoke ~400-600 LoC npm transport (WS7) may be largely unnecessary; a push-back binding also dodges the SSE-orphan problem entirely. This could *reduce* WS7, the one place the report can hand back budget.
3. **Host-ambient credential foraging + write-back (A4).** Hermes's `credential_pool` reads `~/.claude/.credentials.json`, `~/.codex/auth.json`, `~/.qwen/oauth_creds.json`, `gh auth token`, `os.environ` at pool-load (`credential_pool.py:1317-1421`, `credential_sources.py:4-13`) and **writes rotated tokens back to host files** (`credential_pool.py:767-773,848-874`), plus a machine-global shared-Nous store (`auth.py:3520-3579`). In a hosted image this is a cross-tenant-bleed primitive that the port must **actively disable** — unbudgeted hardening.
4. **`/api/jobs*` cron CRUD is exposed under the same single bearer (A1/map01).** Anyone holding `API_SERVER_KEY` gets full cron control (`api_server.py:3410-3417`). Fine if only the backend holds it, but it widens the blast radius of a leaked key and must be in the threat model.
5. **The metering payload carries no cost; cost estimate is `None` for self-hosted models (A11).** Isol8 must self-price. Also: per-call token deltas persist to a per-session SQLite on EFS (`conversation_loop.py:1532-1550`) — billing data on the same WAL/EFS hazard surface.
6. **`gateway.lock` (the singleton boot lock) is `flock`-on-EFS (A8/A14).** This undercuts the single-writer guarantee the SQLite-corruption fix relies on — the lock the whole single-writer story leans on is itself NFS-unreliable (`gateway/status.py:329,416`).
7. **api_server is OFF by default and silently no-binds (A10/A14).** Three EFS/env preconditions (`platforms.api_server.enabled:true`, `API_SERVER_HOST=0.0.0.0`, `API_SERVER_KEY`); the spec calls out only the key. A missing host = silent no-port container that looks healthy.

## 5. Drift verdict (basis vs latest)

**Basis is mislabeled and pinning recent costs more than the spec budgets — but the architecture survives forward.** (`map11`, `attack07`.)

- **The basis is not v0.14.0.** `git describe` = `v2026.5.16-201-g4c46c35e`; HEAD is +201 commits past the real `v2026.5.16` tag. Every cited line offset is a snapshot of an untagged intermediate. Re-pinning to any tag shifts offsets.
- **One HARD invalidation if you pin recent:** upstream `1a9ef8314` makes `API_SERVER_KEY` mandatory on every bind including loopback. The spec's design already binds with a key, so the *architecture* survives — but the per-container key-gen + Secrets-Manager + Bearer-injection is **day-one mandatory scope**, not a drift contingency, and the "keyless loopback like OpenClaw" mental model is dead.
- **Two SOFT risks:** config schema 23→29 (6 migrations; auto-migrates, won't brick, but a hand-written config drifts ~1.2 versions/month); OAuth/credential-pool churned 64 commits on `auth.py` (token sub-shapes not versioned by `AUTH_STORE_VERSION`, which stayed at 1).
- **Genuinely survives:** SSE framing (additive only — `run.completed` gained a `messages` field, ignorable); agent-init signature (accretion); no `Last-Event-ID` added (non-resumability holds at HEAD); all four files exist, no renames.
- **The real cost of pinning recent:** each Hermes release is **800-1300 commits / 1393 files / 12 P0 + 50 P1** (`RELEASE_v0.14.0.md`). "1-2 days/bump" is off by several×; budget **3-5 days/bump**. And lag-1-2-releases (1000-2600 commits behind) conflicts with the steady `fix(security)` stream — you can't both lag for stability and stay current on security when each release is a 1000-commit superset (OpenClaw's point-release cadence lets you cherry-pick; Hermes's does not).
