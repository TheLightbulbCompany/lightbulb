## (a) EFS / cross-process locks / two-writer

### CONFIRM — gateway boot lock is `fcntl.flock` on EFS
`acquire_gateway_runtime_lock()` (`gateway/status.py:421-439`) opens `HERMES_HOME/gateway.lock` (`_get_gateway_lock_path` → `home / _GATEWAY_LOCK_FILENAME`, `status.py:50-55`, default home from `get_hermes_home()`), then `_try_acquire_file_lock` → `fcntl.flock(handle.fileno(), LOCK_EX | LOCK_NB)` (`status.py:329`), released with `fcntl.flock(..., LOCK_UN)` (`status.py:416`). Under the spec's §7 layout `HERMES_HOME` IS the EFS access-point dir, so this is `flock`-on-NFS — the exact primitive CLAUDE.md forbids (Isol8 uses `fcntl.lockf` in `config_patcher.py` *because* `flock` is an NFS no-op). The token-scoped locks are correctly machine-local under `XDG_STATE_HOME`/`HERMES_GATEWAY_LOCK_DIR` (`status.py:63-69`) — those are fine; the load-bearing singleton lock is not. **The single-writer guarantee the SQLite-corruption fix leans on is itself NFS-unreliable.**

### CONFIRM — cron `.tick.lock` is `flock`, and `next_run_at` advances UNDER it (double-fire mechanism is real)
`tick()` opens `HERMES_HOME/cron/.tick.lock` (`_get_lock_paths` → `hermes_home/cron/.tick.lock`, `cron/scheduler.py:141-145`) and acquires `fcntl.flock(lock_fd, LOCK_EX | LOCK_NB)` (`scheduler.py:1691-1692`). Critically, the at-most-once guarantee is implemented by advancing `next_run_at` for every due job *inside* the lock, before any execution (`scheduler.py:1711-1714`: "Advance next_run_at ... FIRST, under the file lock ... This preserves at-most-once semantics"). On EFS with two tasks, `flock` fails open → both ticks see the same `get_due_jobs()`, both call `advance_next_run`, both execute → **every cron job double-fires.** This is not speculative; the at-most-once design is explicitly built on the one primitive that doesn't work on NFS.

### CONFIRM — memory MEMORY.md/USER.md RMW lock is `flock`
`MemoryManager._file_lock` (`tools/memory_tool.py:144-176`) opens `<file>.lock` and uses `fcntl.flock(fd, LOCK_EX)` (`:162`) / `LOCK_UN` (`:169`). Two tasks RMW `memories/MEMORY.md` / `USER.md` (on EFS) can interleave and clobber despite the `os.replace` atomic swap, because the swap is atomic but the read-modify is not serialized across hosts.

### CONFIRM — WAL→DELETE fallback dodges the open-crash, NOT two-writer corruption
`apply_wal_with_fallback` (`hermes_state.py:128-161`) sets `PRAGMA journal_mode=WAL`, catches `OperationalError` matching `_WAL_INCOMPAT_MARKERS`, falls back to `PRAGMA journal_mode=DELETE` (`:160`). The docstring itself only claims DELETE "works on NFS" (`:138-139`) — i.e. it survives the WAL-open crash; it makes **no** two-writer-safety claim. DELETE-mode (rollback journal) still relies on SQLite POSIX byte-range VFS locks, which protect one connection, not a second ECS task opening the same file. This is exactly `project_efs_sqlite_wal_two_task_corruption` for OpenClaw 6.6. Both `state.db` (`hermes_state.py:353`) and `kanban.db` route through this shared helper (`hermes_state.py:148-149` docstring). **Verdict: single-writer `maxPercent=100` is necessary AND insufficient alone — identical posture to OpenClaw, the spec cannot cite "WAL fallback" as the EFS safety story.**

### CONFIRM — billing data itself lands in an EFS SQLite under the same hazard, and Hermes admits the lock failure
Per-call token+cost deltas are written to a session SQLite DB via `agent._session_db.update_token_counts(...)` (`agent/conversation_loop.py:1542-1552`), passing `estimated_cost_usd`, `cost_status`, `cost_source`. The surrounding comment (`conversation_loop.py:1535-1537`) says: "Under concurrent load (cron/kanban), the initial `_ensure_db_session()` may have failed due to SQLite locking. Retry here so per-call token deltas are not silently lost." **Hermes itself documents that concurrent writers hit SQLite lock failures** — billing data lives on the same WAL/EFS corruption surface. This is a reliability concern for any metering design that trusts the session DB.

### NUANCE — RetainDB queue DB is a latent provider-conditional brick (re-confirmed via map07, not re-read this session)
map07 cites `plugins/memory/retaindb/__init__.py:351` opening `retaindb_queue.db` with plain `sqlite3.connect(timeout=30)` and NO journal-mode pragma / no WAL fallback. I did not independently re-open that file this session, so I tag this NUANCE (inherited, not re-verified). If the owner selects the RetainDB memory provider it opens default-journal-mode on EFS and will throw/corrupt. Latent, off the default path.

## (b) Metering — terminal-only, three token ints, NO cost_usd

### CONFIRM — the cited `run.completed.usage` is exactly 3 ints, zero cost
`api_server.py:3046-3050` builds `u = {"input_tokens": getattr(agent,"session_prompt_tokens",0) or 0, "output_tokens": getattr(agent,"session_completion_tokens",0) or 0, "total_tokens": getattr(agent,"session_total_tokens",0) or 0}`. It ships in `run.completed` (`:3073-3079`) and is stored on run status (`:3080-3085`). A repo-wide grep for `cost_usd|cost_status|cost_source|session_estimated_cost` across `gateway/platforms/api_server.py` returns **zero hits** — no api_server wire payload anywhere carries USD. The metering hook the spec wires to is billing-incomplete.

### CONFIRM — cost exists on the agent but is never wired to api_server
`run_agent.py:555-557` initializes `session_estimated_cost_usd = 0.0`, `session_cost_status = "unknown"`, `session_cost_source = "none"`; accumulated at `conversation_loop.py:1520-1523` (only when `cost_result.amount_usd is not None`). The *only* gateway that emits cost is the TUI gateway: `tui_gateway/server.py:1303-1318` calls `estimate_usage_cost(...)` and sets `usage["cost_status"]` (`:1316`) + `usage["cost_usd"]` (`:1318`). The spec's cited entry point (api_server) is the wrong one for money.

### CONFIRM — even where cost exists, it is an estimate that is `None` for self-hosted/OpenRouter
`CostStatus = Literal["actual","estimated","included","unknown"]` (`usage_pricing.py:17`). `estimate_usage_cost` returns `CostResult(amount_usd=None, status="unknown", ...)` at `usage_pricing.py:765` (no pricing entry), `:771`, `:773`, `:777-778`, `:786-787` (missing input/output/cache pricing fields). For open-weight Nous/self-hosted vLLM or an unrecognized base_url, `get_pricing_entry` misses → cost is `None`. **Isol8 must self-price from token counts + its own table, exactly as it does for Bedrock today.**

### CONFIRM — terminal-only, no mid-run meter
Usage is attached only to terminal frames (`run.completed` `:3078`). I confirmed the 3-int shape recurs at the OpenAI-compat sync path (`api_server.py:1323-1327`) using DIFFERENT key names — **`prompt_tokens`/`completion_tokens`/`total_tokens`** — so any hook must handle both namings. Streaming frames carry no usage. There is no token meter mid-run, so Isol8's `check_budget()`-style pre-flight cutoff cannot be fed off the run stream — only a post-hoc terminal reconcile.

### CONFIRM — delegated-subagent cost folds into the parent separately (rollup-timing risk)
`tools/delegate_tool.py:2256-2289`: children accumulate cost independently, summed into `_children_cost_total`, then `parent_agent.session_estimated_cost_usd = current + _children_cost_total` (`:2289`). A naive meter reading only the top-level agent's terminal `usage` may miss or double-count delegated spend depending on whether the rollup has landed before `run.completed`. Worth a live check that parent totals are final at terminal.

## (c) Boot — off-by-default bind, UID mismatch, image weight

### CRACK / DISAGREE WITH INTERIM REPORT — api_server is NOT gated on a config.yaml stanza; the env key alone enables it
The interim report (00-report A10, risk #7, spec-edit #7) says api_server "must be explicitly **enabled** in config (`platforms.api_server.enabled:true`)" and lists writing that stanza to EFS config.yaml as a boot prerequisite. **This overstates the requirement.** `gateway/config.py:1471-1480`: `api_server_enabled = os.getenv("API_SERVER_ENABLED",...)`; `api_server_key = os.getenv("API_SERVER_KEY","")`; then `if api_server_enabled or api_server_key:` → `config.platforms[Platform.API_SERVER].enabled = True`. The `or api_server_key` clause means **setting the `API_SERVER_KEY` task-def env var alone flips the adapter on** — the same env var the spec already requires for auth. No YAML stanza on EFS is needed. `tests/gateway/test_config.py:357` confirms the *default* (no env) is `enabled is False`, and the example config leaves `platforms:` commented (`cli-config.yaml.example:675`), but both are moot because the env path auto-enables. **This is the cleaner provisioning lever and it shrinks the WS4 config-writer friction the report inflated** — the api_server enablement is one env var, not an EFS-config mutation. The boot prerequisite reduces to two env vars (`API_SERVER_KEY` + `API_SERVER_HOST=0.0.0.0`), both task-def, no EFS write.

### CONFIRM — DEFAULT_HOST=127.0.0.1 → silent no-bind without API_SERVER_HOST=0.0.0.0
`DEFAULT_HOST = "127.0.0.1"` (`api_server.py:57`), `self._host = extra.get("host", os.getenv("API_SERVER_HOST", DEFAULT_HOST))` (`:642`). The backend dials in via `discover_ip` to the task IP; a loopback bind is unreachable. So `API_SERVER_HOST=0.0.0.0` (or task IP) is a hard, silent precondition — a missing host yields a healthy-looking container with no Isol8-reachable port. CONFIRMED as a silent failure mode the spec under-calls.

### CONFIRM — network bind refuses without a real key (mandatory, day-one)
`is_network_accessible(self._host) and not self._api_key` → `return False` (`api_server.py:3434-3440`); placeholder key (`has_usable_secret(..., min_length=8)`) → `return False` (`:3444-3455`). `self._api_key = extra.get("key", os.getenv("API_SERVER_KEY",""))` (`:647`). So `API_SERVER_KEY` (≥8 chars, non-placeholder) is mandatory the moment you bind on `0.0.0.0` — day-one scope, not a drift contingency.

### CONFIRM — UID 10000 vs EFS-pinned 1000; chown is best-effort, NOT fatal — and there IS a supported remap lever the interim report under-states
`useradd -u 10000 -m -d /opt/data hermes` (`Dockerfile:21`); `HERMES_HOME=/opt/data` (`:116`); `VOLUME ["/opt/data"]` (`:118`); root→`exec gosu hermes` (`entrypoint.sh:58`). The chown dance: `if [ -n "$HERMES_UID" ] && [ "$HERMES_UID" != "10000" ]; then needs_chown=true` (`entrypoint.sh:30`), then `chown -R hermes:hermes "$HERMES_HOME" 2>/dev/null || echo "Warning: chown failed ... continuing anyway"` (`:40-41`) and the same for `.venv` (`:44`). Two facts the spec/report should fold in: (1) **chown failure is non-fatal** — it logs and continues, so an EFS access point that pins ownership server-side won't brick boot, it'll just leave files owned by the AP UID; (2) the **supported lever is `HERMES_UID=1000`** as a task-def env — `usermod -u "$HERMES_UID" hermes` (`entrypoint.sh:13-15`) remaps the runtime user to match the EFS AP, which is exactly the OpenClaw "work with the AP UID" posture. map10 flagged the 10000-vs-1000 mismatch as an open question but missed that `HERMES_UID=1000` resolves it cleanly. The open question narrows to: validate that running as UID 1000 (matching the AP) + `chown` best-effort no-op behaves correctly, which is a test, not a redesign.

### CONFIRM — per-boot `skills_sync.py` EFS write-storm
`entrypoint.sh:103-105`: `if [ -d "$INSTALL_DIR/skills" ]; then python3 "$INSTALL_DIR/tools/skills_sync.py"; fi`. `$INSTALL_DIR/skills` is baked into the image so the guard is always true → skills_sync runs on **every** cold start, syncing bundled skills into `$HERMES_HOME/skills` (EFS). This is the same many-small-file-on-EFS class as `project_mcp_npx_efs_extract_stall`. Plus `mkdir -p "$HERMES_HOME"/{cron,sessions,logs,...}` every boot (`entrypoint.sh:71`). Per-boot EFS cost is unbudgeted by the spec.

### CONFIRM — heavier image (Chromium+Node) re-pulled per provision; latent `*.md` dockerignore trap
`Dockerfile:17` installs `nodejs npm ... tini`; `:52-55` runs `npm install` + `npx playwright install --with-deps chromium --only-shell` + two more `npm install`s; `:81` `uv sync --frozen ... --extra all --extra messaging`. Chromium + Node + Playwright deps make this far heavier than OpenClaw's extended image → slower cold Fargate pull, and the task def is re-registered every provision (map10/spec §7). The box is 512/2048 in this worktree (per map10 `ecs_manager.py:43-44`) — inherited from OpenClaw with no re-validation for a subprocess-spawning Python agent (`tini -g` exists precisely because "Hermes spawns many subprocesses ... MCP stdio, git, bun", `Dockerfile:13`). Separately: `.dockerignore:24` has `*.md` with **no `!docker/SOUL.md` negation**, while `entrypoint.sh:85` does `cp "$INSTALL_DIR/docker/SOUL.md"`. `docker/SOUL.md` exists in-tree (verified). So `*.md` likely strips it from the build context → SOUL seed fails at boot. Same `feedback_backend_dockerignore_strips_md` footgun; needs a live `docker build` check. Low impact because Isol8's identity-seeding (spec §5) sidesteps SOUL.md.
