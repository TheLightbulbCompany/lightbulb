## Decision

The desired identity is the same owner-scoped native human profile for a verified Lightbulb member and that member's explicitly verified Slack workspace account. A prior web signup is not an inherent requirement: an explicitly authorized Slack-first onboarding policy could create a new member on first verified interaction. Existing members must prove the account link. Preserve Slack `(team_id, user_id)` and installation provenance as transport identity. Do not infer existing-account links from matching names/emails, an installer record, a Slack workspace membership, or shared session keys. Slack installation ownership, human identity linking, native room participation and Paperclip task ownership are separate facts.

The smallest safe slice reuses the existing Slack ingress and installation records, adds a revocable verified member link, and extends the trusted native channel boundary to attach the already-established profile. The inspected upstream APIs do not provide an end-to-end Slack remote-identity-to-profile link with revocation. A UI-only author label or `session.identityLinks` config is insufficient.

## Minimal Lightbulb mapping and trusted attribution — proposal

Use the existing installation as company authority. Add one durable member-link record per `(owner, installation generation, Slack team, Slack user)` pointing to the verified Clerk `(issuer, subject)` and owner-scoped native profile ID, with active/revoked state, verification time/method and revocation revision. Use conditional uniqueness so a Slack tuple cannot race into two members. This can be a distinct row kind in the existing identity-link repository/table if its schema permits; do not couple human identity to a specific agent. Keep team/user separately queryable for checks, and qualify every legacy peer value. Reuse the existing Paperclip member record for Paperclip user/company references; do not maintain a second Paperclip membership list.

For an existing member, link through an explicit, short-lived single-use challenge bound to the logged-in Clerk member, current company, active installation and Slack account proof. One small implementation candidate is a backend-minted nonce redeemed through a Slack-signed private interaction and confirmed in the originating authenticated browser session. Require proof of both ends and fresh membership/role before committing. No name/email matching, install-time automatic human link, client-supplied arbitrary profile ID, or admin self-assertion on behalf of an unverified Slack user. Replayed/expired challenges and conflicting links fail. This candidate flow has not been built or checked against Slack UI limitations. The Slack-first alternative below does not require this existing-account/browser flow for a new person.

For each actor-bearing Slack event, resolve the actor team/user from its verified event shape and distinguish actor from lifecycle-event subject. Validate install owner/generation, canonical member link, current company membership/role and action permission before forwarding any content to the member-only room path. An unlinked person may enter the authorized Slack-first onboarding flow; they must not fall back to the current open policy for these rooms while admission is unresolved. Company audience and actual Slack channel audience must also agree: Slack Connect guests/private channels can create mismatched audiences even within a valid installation. Start with a deliberately selected internal company channel, and withhold private browser history.

Preserve raw Slack body verification. Attach a narrow authenticated backend-to-runtime identity assertion bound to owner, installation generation, team/user, event/message, target session and a short expiry/revocation revision, consumed only at the trusted ingress boundary. The precise assertion/transport is a prototype decision, not an existing supported header. A narrow fork/plugin bridge must resolve the canonical native profile, prepare trusted profile participant facts and use the same profile for persisted user-turn sender and requester context; retain the remote Slack identity in provenance. Reuse native participant/transcript recording and role/session authorization. Do not grant a Slack caller the owner-admin token or route content twice through both Slack and browser chat dispatch.

Before choosing the bridge, prototype both persistent-turn paths and verify run authorization: merely setting a participant profile does not prove native session participation policy was enforced on channel dispatch. Backend membership/role, request admission/budget, session and device permission remain mandatory. Existing auth compatibility risks from the companion report still apply to any service-auth path.

## Slack thread to canonical session — source facts and proposed seam

Upstream already resolves route/account, channel peer, thread and optional runtime/configured binding. Ordinary channel messages retain a channel session; actionable mentions can seed a root thread; room replies retain thread ID. Ordinary DM threads remain the main DM conversation, except Assistant/Agent View threads. A runtime/configured bound session takes precedence; otherwise `resolveThreadSessionKeys` constructs the session and optional parent. U/extensions/slack/src/monitor/message-handler/prepare-routing.ts:142–224. Recorded conversation-session lookup is reused for run targeting (same file:237–273). Bindings carry Slack account, conversation and parent/thread identity (U/extensions/slack/src/conversation-binding-route.ts:94–151). Enterprise `eventScope` disables this binding path in prepare-routing.ts:188, so generic workspace success does not prove enterprise support.

The prepared channel context already carries workspace, native channel, thread, route session, dispatch session and parent (U/extensions/slack/src/monitor/message-handler/prepare.ts:1625–1654). Reuse the runtime-resolved canonical session; Lightbulb's room/deep-link row points to it and stores `(owner, install generation, team, channel, thread/root, agent, canonical key, native session ID)`. Do not guess keys from Slack labels, use thread timestamp without team/channel qualification, or create a second transcript copied from the Slack thread. Bind an existing native session only through a proven native binding write path; discovery of a resolver is not proof of a public write API.

Browser/desktop use the same full session reference and native author profile. Keep Slack origin/delivery metadata so browser viewing does not retarget later replies; explicitly authorize whether browser-authored messages are also delivered into Slack. Native room read audience remains distinct from participants. A channel root being company-readable does not authorize copying private parent context into child threads.

## Paperclip flow — source facts and boundary

The inspected Slack installation/ingress functions route directly to the assigned OpenClaw agent; they do not create Paperclip human membership or an issue per Slack event. The Paperclip provisioning service offers a Better Auth invite/approval member flow (L/apps/backend/core/services/paperclip_provisioning.py:11–31), but the current Clerk membership-created handler explicitly defers that work to first `/container/status` readiness, rather than provisioning in the webhook (L/apps/backend/routers/webhooks.py:331–343). Native Paperclip agent wakes use the backend-synthesized `openclaw_gateway` adapter, service auth and per-issue sessions, with a separate `paperclip:` fallback (L/apps/backend/core/services/paperclip_adapter_config.py:1–40, 53–57). Agent work can call Paperclip through existing skill/tool facilities, but that is not evidence of a first-class Slack-thread→issue mapping.

Proposal: preserve one task/run link when a Slack room requests durable work. Resolve the initiating human through the verified member map and existing Paperclip membership; preserve agent executor identity and service-auth authority separately. A Paperclip service wake is not a human Slack turn. Return its result once to the originating authorized room/thread; do not redirect its issue session into the human transcript or invent a replacement task scheduler.

## Optional Slack-first onboarding — proposal and actual blockers

**Why installation alone does not currently create people:** the install knows its installer, bot and workspace, and installs transport configuration; it neither enumerates eligible humans nor admits them to Clerk/Paperclip or creates native human profiles. Upstream Slack participants are remote identities. Native profile creation is nevertheless available internally: `ensureProfileForEmail` atomically resolves/creates a human profile for a normalized alias (U/src/state/user-profiles.ts:246–296), and trusted-proxy connection admission invokes it (U/src/gateway/server/ws-connection/connect-user-profile.ts:28). No generic `users.create` RPC appears in the inspected method registry. A native human profile is a person record; a model/provider auth profile is a credential/account record and does not establish membership.

**Minimal optional flow:** a company admin deliberately enables an installation-specific eligibility/access policy, chooses the initial member role and allowed Slack audience, and authorizes seat growth within an explicit bound. The first Slack-signed eligible `(team, user)` interaction then idempotently reserves admission, provisions the Lightbulb member and canonical native profile, commits the verified link, and resumes the original event once. This can happen without web signup. It is lazy creation per actual eligible participant, not a workspace-wide import inferred from app install. An existing-account claimant follows verified linking; email can be separately collected/verified where required but never proves that an existing Clerk account is theirs.

**Clerk/source blocker:** current member authority and billing count are Clerk-backed. The inspected `clerk_admin.py` exposes organization listing and invitation creation, not a ready-made Slack-identity user + org-membership provisioning helper (L/apps/backend/core/services/clerk_admin.py:359, 455). The existing invite route requires admin of the exact organization and prevents joining an active personal tenancy (L/apps/backend/routers/orgs.py:51–96). A direct Slack-first implementation must establish a supported Clerk account/membership creation or federated-identity path, with those same tenancy restrictions, before synthesizing an `AuthContext`. Exact Clerk API/tenant capability compatibility was not verified in this local-source assessment. Creating only an OpenClaw profile or a local link row does not satisfy current Lightbulb member authority. A local Slack-only guest principal would be a separate product/auth/billing model, not the minimal version of existing membership.

**Seat/billing blocker:** accepted Clerk members plus pending invitations are billable seats (L/apps/backend/core/services/clerk_admin.py:328); `sync_team_seat_quantity` updates Stripe with `proration_behavior="create_prorations"` (L/apps/backend/core/services/billing_service.py:797–840). Membership-created events call that reconciliation (L/apps/backend/routers/webhooks.py:394–403), and invite creation also schedules it (L/apps/backend/routers/orgs.py:109–119). Therefore even an invitation is not a free inert placeholder. Slack-first eligibility must include explicit organizational authority for seat additions and a bound; this research does not authorize creating accounts, invitations or charges. If admission/seat state is uncertain, keep the interaction pending rather than granting room access.

**Readiness/Paperclip blocker:** webhook-only enrollment will not complete today's deferred Paperclip member setup. Reuse readiness/provisioning from the Slack onboarding workflow rather than requiring the user to visit a page to trigger `/container/status`. The member helper requires an active owner company and member email and skips work when either is unavailable (L/apps/backend/core/services/user_provision.py:882–908), then calls `provision_member` with member and owner email (same file:935–941). A verified email acquisition/identity policy and duplicate-account handling must be demonstrated; do not fabricate email addresses to bypass Better Auth constraints or auto-link by matching them.

**Later web/desktop:** when a Slack-first person signs in, verify possession and bind the resulting Clerk identity to the same canonical person/native profile through a supported linking flow. Do not create a second profile then automatically merge it by email. Preserve prior Slack authorship and current revocation state. Existing-member and Slack-first entry paths converge on the same durable member mapping and room authorization after admission, without making web signup mandatory.

## Official Clerk API follow-up (controller, read-only)

Clerk documents direct programmatic user creation and organization membership creation; the latter does not require an invitation. Thus a separate web signup is not inherently required. The actual tenant's required/enabled identifiers still govern user creation. Email addresses supplied through the backend creation API are verified by default; that is an administrative assertion, not proof Slack verified possession. Do not accidentally bless an unverified address or use it to claim an existing account. Reserved identifiers remain sign-in-capable and exclusive, so they are not harmless placeholders either. See [createUser](https://clerk.com/docs/reference/backend/user/create-user) and [createOrganizationMembership](https://clerk.com/docs/reference/backend/organization/create-organization-membership), checked 2026-09-08.

This narrows the blocker to Lightbulb integration, tenant configuration, verified identity/consent and authorized seat policy—not an absent Clerk membership API. No account, invitation or membership was created, and no auth requirements were weakened. Supported later account linking, Paperclip's email/readiness requirements and bounded billable admission remain unproven.
