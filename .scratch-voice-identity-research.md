# Voice identity research: GPT-Live vs. Hermes agents (2026-10-01)

Scope: why the Live voice ("Lightbulb") and the agents (Hermes) feel like two entities, what upstream
Hermes does, what GPT-Live allows, and options A/B/C. Read-only research; no code changed.

## 0. Root cause of the symptom (our code)

- The voice is a fixed persona named "Lightbulb" that "speaks for the whole team" and "doesn't do the work yourself" (ours:apps/backend/core/services/voice_persona.py:7, :24-28). The Live worker accepts the job as "Lightbulb" (ours:apps/huddle-agent/src/huddle_agent/agent.py:117) with no tools (agent.py:32) and `delegation="client"` (agent.py:84).
- Each delegation is routed to an agent (name → Jev → CEO, ours:apps/backend/core/services/voice_routing.py:22-37), which runs in a call-only Hermes session `agent:{id}:lightbulb:call:{callId}` (ours:apps/backend/core/services/voice_calls.py:443-451; ours:apps/infra/hermes/bridge/turn.py:216-217).
- The agent's reply is streamed back **verbatim** as `append_commentary` (ours:apps/huddle-agent/src/huddle_agent/frames.py:184-191). Attribution exists only as a *thinking* line ("Forge is on it", frames.py:82) and a persona rule ("say who it came from", voice_persona.py:28). Commentary is something the model says "in its own words" (LK:1068-1072; OAI:live-conversations:260 "commentary.append may paraphrase"). So Forge's first-person "you, Aden and me, Forge" is paraphrased by a model whose identity is Lightbulb, and it comes out as Lightbulb claiming to be Forge. The bug is structural: two identities, one mouth, and first-person text crossing between them.
- The voice also has no room facts: the persona carries only the agent roster plus their cards (voice_calls.py:531-535), not the human members. A question like "who's in this room" can only be delegated.

Correction to the brief: "Live stores nothing" is only half true. A call turn is a real Hermes turn. After it, the bridge waits for the memory-provider sync and saves the profile (turn.py:315-317). Our AgentCore memory provider writes every turn's user and assistant text via `CreateEvent` (ours:apps/infra/hermes/plugins/memory/agentcore/__init__.py:11-13, sync_turn at :132-148). So the *delegated* text, including the injected context block, reaches workspace memory. What is lost:
- the voice side of the conversation;
- the room's message history;
- the Hermes session's continuity, because every summon makes a new callId and therefore a new session key (voice_calls.py:631, :450).

Call turns also pass no `conversation_history` (turn.py:270-273), unlike room turns, which pass the room's recent messages (turn.py:2453-2460, built at :1873-1898).

## 1. How upstream Hermes does voice

Hermes has **three** voice designs. Only one of them uses GPT-Live.

### 1a. Desktop "GPT-Live voice chat mode" (`voice.voice_chat_mode: gpt-live`)

**Who is the voice?** A static persona: "You are Hermes, a calm and friendly voice assistant…" (HA@pin:tools/voice_live.py#L48-69). The user can add extra sentences from `voice.gpt_live.instructions` (#L126-128) and pick a voice from `voice.gpt_live.voice`, default `marin` (#L36, #L154). It is **not** built from SOUL.md, the profile or memory: `build_session_config` uses only the persona, the voice and optional history (#L147-159). The persona names the backend as "Hermes agent", which "remember[s] things across sessions" (#L57-59). Voice and agent therefore share one name: there is one entity, and the voice is its mouth.

The community plugin in Hermes's own catalog, `hermes-live-voice`, goes further: "the voice session adopts the active bot's SOUL.md identity and language" (https://github.com/Synero/hermes-live-voice README L37, L113-114; listed in HA@main:plugin-catalog/hermes-live-voice.yaml). Building the persona from SOUL.md is a recognised variant, not something we would be inventing.

**Where do delegations go?** Into the **same chat session the user is in.** Each `session.delegation.created` becomes a normal `prompt.submit` on the open chat with `surface: 'voice-live'` (HA@pin:apps/desktop/src/app/chat/composer/hooks/use-composer-voice.ts#L144-151; doc HA@pin:website/docs/user-guide/features/voice-mode.md#L210). The persisted user row is the user's last words. The recent spoken transcript, up to 6,000 chars, rides the model input only as a per-turn note (HA@pin:tui_gateway/methods_prompt.py#L582-588; HA@pin:tui_gateway/session_notifications.py#L690-692 → `voice_live_turn_note`, HA@pin:tools/voice_live.py#L73-90). Our `TURN_NOTE` is a port of this (ours:voice_calls.py:342-354).

**How do results flow back, and how is one identity kept?**
- Tool progress goes in as `session.thinking.append` ("Hermes is working: <tool>").
- The answer goes in as `session.commentary.append`, sentence-chunked to 1,400 chars because of the 500-token cap.
- When nothing is spoken, a closing thinking line is sent instead.

Sources: HA@pin:apps/desktop/src/app/chat/composer/hooks/use-voice-live-conversation.ts#L347-420 and HA@pin:apps/desktop/src/lib/voice-live.ts#L75-76, #L443-467.

Hermes has no pronoun problem because there is no second identity: the voice is "Hermes" and the backend is "Hermes agent". When the backend says "I", that is the same "I". It is the identical commentary mechanism to ours. Hermes simply never routes one voice to several minds.

**Session continuity.** A new GPT-Live session is **seeded from the chat**: `seedLiveHistory` takes the chat's recent user and assistant text turns, at most 24 messages, 6,000 chars, 1,200 per message (use-composer-voice.ts#L153-160; voice-live.ts#L151-180). They are sent as `session.input` (voice_live.py#L157-158; route HA@pin:hermes_cli/web_routers/audio.py#L177-197).

Every delegated turn is a normal turn of that chat, so it lands in the chat's history and goes through the normal memory and review paths. One voice session is bound to one agent conversation, and the conversation outlives the voice session.

**Multi-agent or group?** None in this mode. It is desktop-only, one chat, one session. It does not run in the CLI or TUI (voice-mode.md#L212).

### 1b. Chained mode (default): STT → normal agent turn → TTS

This covers the CLI, TUI and desktop: record, transcribe, run the turn, speak it (voice-mode.md#L138-142). TTS streams "sentence-by-sentence as it generates text" with any provider (#L168-176). The desktop can call STT and TTS providers directly ("client-direct", #L180-194).

### 1c. Gateway voice: the messaging approach (Telegram, Discord DMs and channels, Discord voice channels)

**Voice messages.** In `/voice on|tts` mode, a voice note is transcribed, the reply is a normal turn, and TTS audio is sent back as a voice bubble (voice-mode.md#L233-297).

**Discord voice channel.**
1. Each user's audio is handled independently.
2. 1.5 s of silence after at least 0.5 s of speech triggers processing.
3. The audio is transcribed with Whisper.
4. It goes through "the full agent pipeline (session, tools, memory)".
5. The reply is spoken back with TTS.

Source: voice-mode.md#L408-416.

How it stays one conversation and one identity:
- The voice input is turned into a `MessageEvent` on **the bound text channel's own session source**: "voice shares the text conversation's session" (HA@pin:gateway/run_voice.py#L225-235, #L274-278).
- Transcripts are posted to the text channel as `[Voice] @user: …`, and the agent's reply is sent as text **and** spoken (run_voice.py#L259-265; voice-mode.md#L418-424).
- The agent itself speaks, in its own TTS voice, so there is no persona layer at all.

**Multiple bots / profiles.** Under multiplexing each profile's bot has its own adapter and its own voice state per (bot, chat): `<profile>:<platform>:<chat_id>` (run_voice.py#L33-49, #L240-241). Several agents can each be a distinct speaker in one channel. Upstream also has an outgoing PCM mixer for Discord voice (HA@main:plugins/platforms/discord/voice_mixer.py).

### 1d. Google Meet plugin (realtime as a mouth)

In `mode='realtime'`, the agent decides what to say (`meet_say`). An OpenAI Realtime session only turns that text into audio: `conversation.item.create` + `response.create` (HA@pin:plugins/google_meet/realtime/openai_client.py#L72-102). The agent is the voice and the speech model is a TTS device.

**Bottom line on Hermes.** The GPT-Live mode avoids the identity split by having one entity and binding delegations into the user's own session. Every multi-party design upstream (Discord VC, voice notes, Meet) uses the cascade: the agent's normal turn in its normal session, transcripts and replies written into the text channel, then TTS. **Hermes has no multi-agent GPT-Live design.**

## 3. Options

Common to every option: we can **write the voice exchange back** to the room. `messaging_repo.create_message(..., dispatch_targets=[], silent=True)` already exists for system lines that must not wake anyone or notify (ours:apps/backend/core/services/messaging.py:3748-3766). Room turns build their history from the room's recent messages (turn.py:1873-1898, :2459). So written-back lines become every agent's context on its next room turn, with no Hermes change. Memory follows automatically from the turn (agentcore plugin sync_turn).

### (A) The voice *is* the agent

What changes:
- **Persona** (`voice_persona.build_persona`): "You are {agent name}". Add a short SOUL.md excerpt, readable from the profile in S3 by the backend (`hermes_profiles`), plus the room facts we already have: human members and agent roster. Per-agent voice: `voice_for(agent_id)` already maps an agent to a stable voice (voice_persona.py:12-15), but its list includes realtime names (`alloy`, `ash`, …) that are not in the GPT-Live table above. Constrain it to the 14 GPT-Live voices.
- **Backend dispatch**: use the agent's **room** session key, `lightbulb_session_key(agent, room)` = `agent:{id}:lightbulb:channel:{room}` (turn.py:1901-1903), instead of `…:call:{callId}` (voice_calls.py:450). Fetch the room history into the call run as `conversation_history`, as room turns do (turn.py:2459).
- **Bridge**: `_run_call` must accept and pass `conversation_history`. The turn lock is already per (agent, session key) (turn.py:2220-2225, :253), so a voice turn and a typed room turn of the same agent serialize. That is correct, but a voice turn can then queue behind a long typed run.
- **Worker**: seed `chat_ctx` from room history so GPT-Live starts with `session.input` (LK:1131-1134). Keep one GPT-Live session per (Live room, agent) across summons, or close it on idle and re-seed: the docs pattern (OAI:live-conversations:494-503).
- **Write-back**: the human utterance and the spoken answer are posted as silent, no-dispatch room messages; the answer is authored by the agent.

Several agents in a room have no clean answer, because one session has one voice and one persona:
- (i) **Persona switching in one session**: same voice for everyone, plus an appended "now speaking as X" each time. It looks like a fix but it is still one person, so the identity problem remains.
- (ii) **One GPT-Live session per agent in the room**: N × $0.05/min, idle included (6 starter agents = $0.30/min = $18/hour per huddle). Floor control between N full-duplex models is unsolved, since every session hears the room. Not viable.
- (iii) **Fallback**: A for DMs and single-agent rooms, today's Lightbulb with better attribution for multi-agent huddles. That keeps two entities exactly where the bug was reported (a group DM with Forge).

**Session continuity**: one Hermes session per room per agent (the room key), so it is continuous with typed chat. GPT-Live is per summon but re-seeded from the room.
**Latency**: unchanged from today for the voice; Hermes turns get slightly longer with history added.
**Cost**: unchanged in 1:1 ($0.05/min). Multi-agent options (i) $0.05/min, (ii) N × $0.05.
**Risks**:
- SOUL.md text is user-editable and goes into the voice persona. It is untrusted content, but it is the user's own.
- GPT-Live still paraphrases, so the agent's wording is softened, though now in the right person.
- Voice turns can wait on the per-session lock behind typed room runs.

**Free from Hermes**: the exact pattern (delegate into the user's own session, seed history, per-turn note), already proven upstream (§1a). The SOUL.md persona variant exists in the community plugin.

### (B) Lightbulb is a real Hermes agent that owns the voice

What changes: a seventh profile, "Lightbulb", provisioned per workspace, with its own SOUL.md and memory. The voice delegates to it, and it delegates to teammates. Teammates are reached by:
- Paperclip issues, which are asynchronous: minutes, not seconds, and wrong for a live answer; or
- direct turns, which means a new bridge seam for agent-to-agent turns.

Their answers are its inputs, and it rewrites them in the third person in its own turn.

**Continuity**: Lightbulb's room session is continuous, and its memory gives it personal history.
**Latency**: worst of the three. GPT-Live → Lightbulb turn → teammate turn → Lightbulb turn → voice is two LLM turns in series: +1–3 s minimum, more with tools. `_TURN_TIMEOUT_S` (18 s) and the 4-step call budget (turn.py:240) get tight.
**Cost**: voice $0.05/min plus an extra Hermes turn per request, plus a seventh agent's provisioning, memory and roster slot.
**Risks**:
- It fixes the pronouns (an LLM rewrites them), but cements "two entities". Lightbulb becomes a real colleague who is *not* Forge, which is the opposite of what the owner says feels wrong.
- It also collides with the roster rules: the CEO is root, Jev routes, and the reply cap is `AGENT_REPLY_CAP`.

**Free from Hermes**: nothing voice-specific; Paperclip coordination already exists.

### (C) Hermes-native cascade: per-person STT → the agent's normal room turn → TTS in the agent's voice

What changes:
- **Worker**: per-person streaming STT already runs (agent.py:130, gpt-4o-mini-transcribe, only while unmuted, :200-211). The summon and turn-taking logic in `huddle.py` stays. Change: a final transcript addressed to agents (wake word, Talk button or name) becomes a **room message** through the normal messaging command path (the `[Voice]` line, as on Discord), so the existing dispatch decides who answers. That dispatch is `select_dispatch_targets` + Jev + listen modes (messaging.py:2623-2652). This also removes `voice_routing`'s parallel copy of the routing.
- **Agent reply**: the agent's reply arrives as a normal room message and run frames (async turn contract). The worker streams its sentences to TTS in **that agent's** voice and publishes the audio, one LiveKit participant/track per agent (or one track with the agent's name in participant attributes).
- **Backend**: a voice flag on the message, so the agent gets the speakable-reply note (port of `VOICE_LIVE_TURN_NOTE`). No call row and no call session per summon; the bill is STT plus TTS minutes.
- **Bridge**: none for the core path: it is a normal room turn on `agent:{id}:lightbulb:channel:{room}`. Optional: emit sentence-complete frames earlier for TTS.
- **Write-back**: automatic. The utterance and the reply *are* room messages, so history and memory are free, and so is the room's read model on web and mobile.

**Session continuity**: one Hermes session per room per agent, the same one as typed chat, and permanent.

**Latency** (estimates, not measured):
- endpointing: Hermes uses 1.5 s silence (voice-mode.md#L413); we can push to about 0.6–0.8 s;
- final STT: about 0.2–0.5 s streaming;
- the agent's time to first sentence: warm, about 1–3 s for a plain answer, plus tool steps;
- TTS first audio: about 0.3–0.5 s;
- so about **2–4 s** to first word for a simple question, versus GPT-Live's instant acknowledgement followed by the same Hermes wait.

The difference is perceived liveness, not time to the real answer. GPT-Live also fills the wait ("Forge is checking") and handles barge-in and backchannel natively. In a cascade we must build barge-in (stop TTS on VAD) and an optional "on it" earcon. A cold workspace stays 54–57 s either way (CLAUDE.md "Agent dispatch"), so pre-wake stays (voice_calls.py:468-477).

**Cost**:
- STT: $0.003/min per *unmuted speaker*, already paid today.
- TTS: only while an agent speaks; gpt-4o-mini-tts about $0.015/min of speech (estimate).
- **Zero idle cost**, versus $0.05/min for every minute a GPT-Live session is open, silence included.
- A 20-minute huddle with 2 minutes of agent speech: about $0.03 TTS, versus $1.00 of GPT-Live per summon-minute. (Today's summons are short, so the real saving depends on usage.)

**Risks**:
- Weaker conversational feel: no backchannel, and the turn-taking is ours.
- Barge-in and echo handling: Hermes pauses listening during TTS (voice-mode.md#L426-428).
- Agents that are chatty in rooms are also chatty in voice; Jev and the reply cap already bound that.
- Voice-flagged messages must stay short, so the turn note matters.

**Free from Hermes**:
- the whole design, proven upstream (Discord VC: one session shared with the text channel, transcripts posted, agent speaks itself; multiplexed bots for several agents);
- STT/TTS provider registries and sentence-streaming TTS (HA@pin:tools/tts_tool.py, tools/tts_streaming.py, agent/tts_registry.py; voice-mode.md#L168-176);
- the voice-surface turn note (HA@pin:tools/voice_live.py#L73-90).

We would use these as reference rather than calling the gateway, because our bridge does not run the Hermes gateway.

## 4. Recommendation

**Make the agent the voice, everywhere, and stop running a second mind.** Concretely: **C for Live huddles and multi-agent rooms, A for 1:1 (DM) calls.** Reject B.

Why:
- Hermes itself never puts a second mind between the user and an agent. Its one-voice-model mode works only because voice and agent share one identity and one session (§1a). Every multi-party design it ships is the cascade into the channel's own session (§1c).
- GPT-Live cannot be several agents: one voice per session, immutable persona, idle billed (§2).
- The room is already the canonical conversation, and room turns already take their history from it. Making voice *write into the room* gives history, memory and cross-surface visibility at once, and removes `voice_routing` and the call-session machinery for huddles.

Phased plan:
1. **Stop the bleeding (small, now).** Turn frames carry the agent name; send the answer as commentary in the third person with a speaker prefix. Change the persona rule from "say who it came from" to "a result is a quote from the named teammate: report it in the third person ('Forge says you, Aden and Forge are here'), never as yourself". Add room facts (human members and agents) to the persona so "who's here" is answered directly. Constrain `voice_for` to GPT-Live voice names.
2. **Write-back (both modes).** Post the spoken request and the spoken answer as silent, no-dispatch room messages: `create_message(dispatch_targets=[], silent=True)` for the human line; the agent's answer as its own message. Run voice turns on the agent's **room** session key with room history passed (`_run_call` gains `conversation_history`).
3. **DM calls = A.** Persona = the agent (name, a SOUL.md excerpt, its voice); delegations go into that DM's room session; GPT-Live is seeded from the DM history via `session.input`. This is the Hermes desktop pattern.
4. **Huddles = C.** Transcripts addressed to agents become `[Voice]` room messages; normal dispatch picks the responder; the worker speaks the agent's reply with streaming TTS in that agent's voice, as its own LiveKit participant; build barge-in. Measure time to first word against today's summon before deciding whether GPT-Live stays as a fallback for single-agent huddles.

Ship 1 and 2 first: they fix the reported bug and the "nothing is remembered" complaint without a new architecture. Decide 3 versus 4 order after measuring.
