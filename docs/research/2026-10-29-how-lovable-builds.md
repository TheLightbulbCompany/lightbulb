# How Lovable makes building and shipping effortless (29 Oct 2026)

The question: how does Lovable keep non-technical users from drowning in infrastructure, especially dev versus prod? All sources fetched 2026-10-29. Tags: **[P]** Lovable's own docs, changelog or blog, with URL; **[S]** secondary; **[U]** unverified. This doc builds on `2026-10-27-small-software-stack-teardown.md` §2 (stack, Cloud, auth, storage, pricing, GitHub) and `2026-10-28-small-software-open-lovable-read.md`, and does not repeat them. Docs root: `https://docs.lovable.dev` (written below as `docs/…`).

## The answer in one paragraph
Lovable has **one database and two views of the code**. The preview always runs the latest code. The published site is a code snapshot that changes only when someone clicks Publish. Both use the same backend and the same data. Lovable shipped real Test and Live databases (Feb 2026), stopped offering them to new projects on 24 Mar 2026, and retired them on 23 Oct 2026. In their place came **drafts**: copies of the code, without a second database. Data safety comes from three rules, not from a staging stage. The agent may only add to the schema, never break it. Code reverts never touch data. Daily database backups can be restored. The words "environment", "staging" and "production" are missing from the glossary. The one place a test/live split survives is payments, and there it is driven by preview versus published.

## 2. Stages: how Lovable handles dev versus prod
- **Today (new projects): one database.** "the preview and your published app share the same backend and data, so changes to your database affect both." Visitors see "a snapshot that only changes when you publish" [P] docs/features/projects/preview. "Every draft uses the same database as your project," and the Database view edits "the same database your published app uses" [P] docs/features/database.
- **Code staging = drafts.** Drafts are "Copies of a project you can build in separately, each with its own chat, preview, and edits" [P] docs/glossary. Accepting a draft "is not publishing"; creating, updating, accepting and deleting a draft cost no credits [P] docs/features/drafts.
- **Test and Live, introduced then retired.** 5 Feb 2026: "separate Test and Live environments with isolated databases." 2 Apr 2026: "As of March 24, 2026, Test and Live environments are no longer available for new Lovable Cloud projects… plan to bring it back in an improved form" [P] docs/changelog. Retirement page: "Test and Live is replaced by drafts… Drafts don't provide a second database"; the switcher was removed from the Database view on 23 Oct 2026, and detached Test databases are deleted on 1 Dec 2026 [P] docs/features/environments. While it ran, publish carried "the database schema, storage bucket definitions, row-level security (RLS) policies, and edge functions" from Test to Live, but "It does not carry data… Do not rely on publishing to migrate data" [P] same page. No reason is given beyond "moving development and production environments in a different direction" [P] same page. My read is that two databases confused users whose data lived in the wrong one [U].
- **Migrations: only safe changes, by default.** From 7 Oct 2026, Cloud records every schema change as a Drizzle SQL file under `drizzle/migrations/`, and "refuses changes that could break your published app, such as dropping or renaming a table or column" [P] docs/changelog. Instead it adds: "adding a new column and copying the data over". Breaking changes need **Execute backward incompatible database migrations**, which defaults to Never allow; with Ask each time, "Lovable shows you the SQL and asks for your approval" [P] docs/features/database. A publish can still fail when a change conflicts with live data; the fix is **Ask the assistant to help**, and "Lovable confirms with you before changing anything" [P] docs/features/publish.
- **Code apply, data never rolls back.** "There is no save button"; reverting "does not restore or roll back your database data"; edge functions are redeployed to match; the live version carries a "Published" badge [P] docs/features/projects/history. Reverting does not change the live site: "Your published site does not change until you publish" [P] docs/changelog (28 Jul 2026).
- **Data recovery = daily backups.** Since 18 May 2026 a user can restore "to any of its recent daily backups" without support; a restore is permanent and drops data written after the backup [P] docs/changelog.
- **Does the user see "environment"?** No. The glossary has no entry for environment, staging or production; the word appears only in "Build secrets… environment variables" [P] docs/glossary. The one surviving test/live split is **Payments**. The preview runs in test mode ("Checkout only accepts test card numbers"), the published app runs live, and "products and prices created through Lovable sync automatically from your test environment" to live on publish. A "test mode banner" shows only in the preview [P] docs/features/payments.
- **Own Supabase:** "Each Lovable project connects to one Supabase project at a time"; migrations are approved in chat [P] docs/integrations/supabase. There is no staging guidance on that page. A search summary attributes advice to use "a second Supabase project… or Supabase branching" to a Lovable FAQ that now redirects [U].

## 3. Backend
- **What Cloud is:** "a built-in backend for Lovable apps… No external dashboards or configuration screens"; "Authentication and row-level security are built in"; "scales up as your app gains users" [P] https://lovable.dev/blog/lovable-cloud (29 Sep 2025). It is built on "Supabase's open-source foundation"; "Lovable manages the hosting and backend infrastructure for you"; no cloud provider is named [P] docs/features/cloud. Lovable owns the account; the user owns the code (prior doc).
- **Who decides a backend is needed:** the agent, when "a feature needs it", gated by the Enable Cloud permission [P] docs/features/cloud. Since 16 Mar 2026, "Cloud tools now auto-approve by default" [P] docs/changelog. Users can resize compute by asking in chat (8 Jul 2026) [P] docs/changelog.
- **Secrets:** since 26 Jun 2026, "paste an API key or token into chat and Lovable will save it as a project secret automatically" [P] docs/changelog.
- **Third-party accounts are created for the user:** Stripe: "Claim the sandbox account Lovable created" [P] docs/features/payments. Auth email DNS: "automatically manages domain verification and authentication (DNS, SPF, DKIM, and DMARC)" (16 Mar 2026) [P] docs/changelog. Payments: "Lovable handles the setup and infrastructure, including account creation, webhooks, and subscription data" (24 Apr 2026) [P] docs/changelog.
- **Security:** a Quick scan "runs automatically every time you publish" and checks for "tables without per-record access control (row-level security)". The Deep scan runs on demand. "Lovable can automatically fix eligible security findings while you build". Admins can turn on "Block publishing with critical issues". Scans are free [P] docs/features/security. Since 23 Sep 2026 the Security view "explains what each finding means for your app and its users" [P] docs/changelog.

## 4. Starting points and rules
- **Fixed stack, no choice offered:** TanStack Start for new apps since 13 May 2026; older Vite apps "can now upgrade in place" (28 Jul 2026) [P] docs/changelog.
- **Templates:** curated "Lovable templates" in a dashboard tab, with preview and remix from the card (Aug–Sep 2026); workspace "default design template" [P] docs/changelog. "Templates are best for initial project scaffolding"; design systems give "ongoing UI and design guidance" [P] docs/features/design-systems.
- **Design systems are enforced, not suggested:** "every generation is scanned for violations of the design system… Lovable automatically retries to correct them before finishing" [P] docs/features/design-systems.
- **Instructions (was Knowledge, renamed 27 Oct 2026):** workspace and project, each up to 10,000 characters; project wins on conflict; `AGENTS.md` or `CLAUDE.md` in the repo are also read [P] docs/features/knowledge.
- **System prompt:** none published; leaked copies exist [U], not used.

## 5. The agent's workflow
- **Modes:** Build (default) "implement[s] and verif[ies] changes directly"; Plan writes and approves a plan; Chat "discusses the app you have open without changing its code" (21 Sep 2026) [P] docs/features/agent-mode, docs/changelog.
- **Tools:** console and network reads, browser testing, frontend tests, edge-function checks, web search, image and video generation. But "Most verification tools run only when you ask for them" [P] docs/features/agent-mode. Browser testing runs "selectively, after trying faster verification methods first", and signs in as the user when the app has exactly one [P] docs/features/browser-testing.
- **Self-test on business rules:** since 16 Oct 2026, "Lovable now adds a small test when you add or change a rule in your app, such as a price, a limit, or a permission… runs the tests that cover the change before it reports the work as done". It does not write tests for copy or styling [P] docs/changelog.
- **Self-heal:** "Lovable reads your app's console logs itself"; use **Try to fix** "once or twice". It warns that "Repeated blind fixes tend to pile up code that hides the real problem", and that "rewinding is often faster than untangling" [P] docs/prompting/prompting-debugging. Users get 10 free fixes, each renewing 24 h after use [P] docs/introduction/faq.
- **Long runs and cost:** up to 10 hours per Build message; Goals run "until the goal is achieved"; usage-priced and "Many requests cost less than one credit"; no upfront estimate; a check-in pauses at 20 credits by default [P] docs/features/agent-mode.

## 6. Where non-technical users get stuck, and what Lovable added
Lovable's docs do not list complaints. The fixes in the changelog show where users were stuck:
- **Blank or broken screens:** Try to fix on a blank screen, readable error messages, automatic transient retries [P] docs/changelog 2025.
- **Error loops and fix spend:** 10 free fixes, plus advice to stop and diagnose in Plan mode [P] docs/prompting/prompting-debugging.
- **Publishing:** visible failures with Try to fix (Jan 2026), a guided flow (Feb 2026), then a single dialog with metadata filled in (Aug 2026), plus publish-by-chat (Jun 2026) [P] docs/changelog.
- **Losing data to schema changes:** Drizzle migrations that refuse breaking changes (Oct 2026); self-serve backup restore (May 2026) [P] docs/changelog.
- **Two databases:** Test/Live was pulled after a beta [P] docs/features/environments.
- **Keys, DNS, email, Stripe:** paste-to-secret, Entri DNS, automated SPF/DKIM, Stripe sandbox created for the user [P] above.
- **Security:** a scan on every publish, auto-fix, and plain-language findings [P] above.
- **Founder framing:** Osika says the team found where the AI fails ("login, data persistence, Stripe integration") and eliminated those failures one by one [S] Lenny's Podcast summary, https://metacast.app/podcast/lenny-s-podcast-product-growth-career/Jd3KQZ6s/building-lovable-10m-arr-in-60-days-with-15-people-anton-osika-ceo-and-co-founder/m3X2HJ4x. He also says Lovable was designed for non-technical users first and "designed down to simplicity" [S] https://tbpn-digest.vercel.app/story/2026-01-29/lovable-hits-300m-arr-co-founder-anton-osika-on-building-a-technical-co-founder-for-the-masses.

## 7. Ten lessons for Lightbulb Apps
1. **Never say "environment".** Use two nouns: "your draft" (what the agent is working on) and "the live app" (what people use). One button moves the draft to live. Lovable's glossary has no word for stage [P].
2. **One database by default; do not ship test/live databases to non-technical users.** Lovable built them and withdrew them inside two months: data in Test never reached Live, and moving it was a manual chore [P]. With Stripe Projects, that means one database resource per app, not two.
3. **Make the schema add-only by default.** That is the real dev/prod safety. The agent adds columns and copies data across; drops and renames need an explicit yes with the SQL shown. Keep every migration as a file in the repo [P].
4. **Keep code history separate from data history, and say so.** Code: versions with a "live" badge and one-click revert that never touches data. Data: daily backups the user can restore. Lovable states both rules in plain words [P].
5. **Split payments by draft versus live.** The draft uses Stripe test mode with a visible banner; publish syncs products to live. The Stripe sandbox should be created for the user and claimed later. This maps cleanly onto Stripe Projects [P].
6. **The agent provisions; the user approves once.** The backend turns on when a feature needs it, behind a single permission (allow or ask). Keys pasted in chat become secrets automatically. Region is asked once [P]. In Lightbulb: the room message "this needs a database, add one on your Stripe account?" with one tap.
7. **Make publish one action with nothing to fill in.** Default URL, generated metadata, a ~10-second security scan that does not block by default, "Try to fix" when the build fails, and "ship it" in chat [P]. Do not ask for build settings.
8. **Have the agent test what can lose money or data, not pixels.** Copy Lovable's Oct 2026 rule: add and run a small test when a price, limit or permission changes; browser-test only when cheaper checks are not enough [P].
9. **Cap self-repair.** Allow a free "fix" a few times, then switch to diagnose-first. Show live cost counters and a pause at a credit threshold [P]. Lightbulb should keep its own equivalents and not let an agent loop silently on the customer's bill.
10. **Do not copy the lock-in.** Lovable owns the Cloud account, and the export leaves out files, functions and secrets (prior doc). Lightbulb's difference is that everything sits on the customer's own accounts. Keep that, but hide it the way Lovable hides Supabase: the user sees "your app's data", never a provider dashboard, unless they ask.
