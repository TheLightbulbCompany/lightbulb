## Why a Part 2

Part 1 framed this as a **credential-linking layer** built around Nango, whose job was to fetch tokens and inject them into `openclaw.json` paths (`mcp.servers[].env`, `skills.entries.*.apiKey`, `channels.*`). That framing led to the M1/M2 code currently uncommitted in the `credentials-m1-m2` worktree (the Nango CDK stack + container env wiring).

Re-investigating OpenClaw and the Isol8 backend from first principles surfaced two facts that reframe the work:

1. **Delivery was never the missing piece.** OpenClaw already ships every delivery rail (SecretRef `file`/`exec` resolve at use-time — `src/secrets/resolve.ts:358,632`; channel config hot-reloads the adapter — `src/gateway/config-reload-plan.ts:152-169`; the bash-tool env whitelist passes credential *pointers* — `src/infra/host-env-security-policy.json:240-271`), and **Isol8 already exercises all of them**: EFS file pre-staging (`core/containers/workspace.py:700-786`, ChatGPT OAuth), Secrets-Manager→env (`core/containers/ecs_manager.py:1140-1169`, BYO keys), and runtime config deep-merge (`core/services/config_patcher.py:201-224`, channel tokens). The hard problem is **acquisition + custody + refresh of a *customer's* credential through a no-shell web UX** — not delivery.

2. **Agent-native CLIs are a first-class answer, not a thing to avoid.** Part 1 §500 deferred CLIs like `gog` and preferred `gcloud`, because it modeled credential delivery as "inject a token into config." But `gog` (and the broader class generated by **Printing Press** — `github.com/mvanhorn/cli-printing-press`, "print an agent-native CLI for any API/app/site") is an **actor**: it can own its own OAuth refresh once seeded, and it can be provisioned headlessly (`gog auth tokens import -` over stdin + `GOG_KEYRING_PASSWORD`; the binary is already baked into our image at `apps/infra/openclaw/Dockerfile:64`). Treating CLIs as first-class *reduces* the steady-state work for many integrations.

The result is a cleaner core abstraction that subsumes Part 1's `providers.yaml`: **an Integration Registry with two orthogonal axes — acquisition and actor — plus an explicit per-integration refresh owner.**

## The core reframe: two orthogonal axes

Every integration is defined by two independent choices plus who owns refresh:

| Axis | Question | Backends |
|---|---|---|
| **Acquisition** | How does the credential get minted, vaulted, and (optionally) refreshed? | `paste_token` · `direct_oauth` (we run the dance) · `nango` (OAuth broker, deferred) · `aws_sts` · `secrets_manager` (platform-owned) |
| **Actor** | How does the agent actually *do work* with the credential? | `cli` (gog, Printing-Press output) · `mcp` (stdio MCP server) · `skill` (raw API) · `nango_proxy` (call provider API through Nango, no local token — reserved) |
| **Refresh owner** | Who keeps the credential live after acquisition? | `actor` (CLI self-refreshes) · `none` (long-lived key) · `isol8_rematerialize` (we re-fetch + rewrite) · `nango_proxy` (no local token) |

The axes are independent. A broker (acquisition) does **not** give you an actor — except `nango_proxy`, the one mode that spans both axes (reserved for high-sensitivity providers). `gog` and Printing Press live **entirely on the actor axis**. MCP is **one actor pattern**, a sibling of CLI — *not* a credential layer; the credential still has to reach it, and `mcp.servers[].env` accepts **literal strings only** (`src/config/types.mcp.ts:6`, no `SecretRef` in the union), which is why an OAuth-backed MCP forces `isol8_rematerialize`.

```
            ACQUISITION                         ACTOR
   ┌──────────────────────────┐      ┌──────────────────────────────┐
   │ paste_token   (v1)        │      │ cli         (gog, PP output)  │
   │ direct_oauth  (v1)        │  ×   │ mcp         (stdio server)    │
   │ nango         (deferred)  │      │ skill       (raw API)         │
   │ aws_sts                   │      │ nango_proxy (reserved)        │
   │ secrets_manager (platform)│      └──────────────────────────────┘
   └──────────────────────────┘
                 │                                   │
                 └────────── Integration Registry ───┘
                    (one recipe per integration:
                     acquisition × actor × refresh_owner × wiring)
```

## v1 Decision (2026-05-29): build our own integrations panel; defer Nango and Composio

A bucketing pass over **everything Isol8 actually ships in HEAD** changed the build/buy call. Of the full live integration set, the number that genuinely needs a true-OAuth broker (redirect + callback + PKCE + refresh) is **zero today, one on the horizon** (Microsoft 365 / Outlook, currently `enabled:false`). Every shipped MCP in the 9-agent roster (HubSpot, Attio, Apollo, Pipedrive, Instantly, Smartlead, Perplexity, PostHog, Stripe, Twilio, Qdrant) is an **API-key env var (paste-once)**; all three channels (Telegram/Discord/Slack) are paste-a-token (Slack ships as a self-installed app manifest with long-lived `xoxb-`/`xapp-` tokens — *not* the user-OAuth dance); the only OAuth tools (`gog`, `gh`, ChatGPT) are **self-refreshing CLIs**.

### The three buckets

| Bucket | Live launch set | Acquisition | Delivery / actor | Refresh owner | Broker? |
|---|---|---|---|---|---|
| **A — paste-key** | all 3 channels; **every shipped MCP** (all API keys); all BYOK tool/LLM keys; `wacli`, `xurl`, CalDAV | `paste_token` (validate→store) | literal env via `config_patcher` → `mcp.servers[].env`; or BYOK rail (`key_service` → Secrets Manager → ECS env); or `channels.*` block | none (long-lived) | **No** |
| **B — dedicated self-refreshing CLI** | `gog` (Google), `gh` (GitHub), `spogo`, `op`, ChatGPT-OAuth | one-time seed (device-code where supported; redirect dance only if forced) | materializer writes 0600 file to EFS (`workspace.py:700-786` rail). Seed BOTH artifacts — OAuth client + refresh token | **actor** (CLI self-refreshes forever) | **No** |
| **C — true OAuth dance + refresh** | **Outlook/MS365 only — `enabled:false`** | `direct_oauth` (build the PKCE+state store + generic callback once) | materializer file (Actor A) or `mcp.servers[].env` literal (Actor B) | `isol8_rematerialize` if MCP literal; `actor` if self-refreshing CLI | self-built dance; **no third-party broker for one provider** |

Buckets A + B cover 100% of what is wired and live today.

### Decision

**v1 = build our own integrations panel (direct OAuth dance + materialize), modeled on the existing channels + ChatGPT-OAuth flows. Defer Nango; do not adopt Composio.**

The build-our-own case is cheap because **Isol8 already owns the expensive half**: the materialize rail (`workspace.py:700-786` — atomic write + `chmod 0600` + `chown 1000` + EFS-chroot), the token vault (`oauth_service.py` Fernet + the `oauth-tokens` DDB table at `database-stack.ts:237-245` — add a `provider` sort key, zero new infra), the wiring engine (`config_patcher.py`), and the full connect→poll→disconnect UX (`useChatGPTOAuth.ts`, `MyChannelsSection.tsx`, `BotSetupWizard.tsx`). The **only genuinely missing piece is the true-OAuth redirect dance** (a shared PKCE+state store + a generic `GET /oauth/{provider}/callback`; verified absent — the ChatGPT flow is device-code, so Isol8 has never generated PKCE/state). Estimate: **panel + scaffolding + first providers ≈ 10–14 days**, ~1 day/provider thereafter for self-refreshing CLIs.

**This decision is reversible** — the registry's `acquisition` field makes flipping a provider `direct_oauth → nango` a config change, not a rewrite. **Flip to Nango when OAuth providers cross ~5–8**, or when many Actor-B live-token (`isol8_rematerialize`) integrations accumulate.

### Nango: deferred, not deleted

- The **uncommitted `credentials-stack.ts` is parked** (not wired into `isol8-stage.ts`). It is ~70% scaffold with a **vault-fatal bug** — `NANGO_ENCRYPTION_KEY` generated as 44 alphanumeric chars (must be base64-32-byte) and without `RemovalPolicy.RETAIN`; if it ever regenerates, every customer re-connects every provider. Do not deploy it as-is.
- **Nango's open-source catalog is our reference data.** `packages/providers/providers.yaml` (+ `providers.scopes.yaml`) encodes per-provider `auth_mode` / `authorization_url` / `token_url` / `refresh_params` / `disable_pkce` / `default_scopes` / `scope_separator` / `proxy.base_url` — i.e. the variant-trap knowledge (`greenhouse-harvest` = Basic auth, `github` vs `github-app`, Jira cloud-vs-server URLs). These OAuth endpoints/scopes are **facts** about the providers (not copyrightable); transcribe them into our `providers.yaml`, verifying against each vendor's own docs. Read their flow *code* (ELv2) for reference but **write our own dance** (standard OAuth2) to avoid the derivative-work / notice obligation. Keep our provider keys aligned with Nango's so a future adoption is a near-trivial key match.
- **Nango Proxy stays reserved** for the one hygiene case build-our-own cannot match: a provider that requires *tokens never on disk* (Proxy holds the token; the container calls through it). Pull it in per-provider if/when that need arises — independent of provider count.

### Composio: not v1

Fails the hard rule "no SaaS in the critical path holds end-customer OAuth tokens" — the OSS repo is SDK-only; tokens vault in Composio's cloud; on-prem is enterprise-custom-pricing. Strictly worse than Nango on custody. Cost is **tool-call-metered and open-ended** (~$2,200/mo at 10M calls; scales with agent chattiness, independent of customer count) — a new re-billing burden on top of the existing Stripe Meters. For buckets A/B it is pure overhead. Reserve only as a deliberate, rule-relaxing exception for a future high-OAuth-complexity provider.

### AWS Bedrock AgentCore Identity: evaluated, deferred (future hybrid candidate)

"Rely on AWS" was assessed (2026-05-29). **AgentCore Identity** is a real à-la-carte option: usable from plain ECS without AgentCore Runtime (AWS blog *"Secure AI agents with AgentCore Identity on Amazon ECS"*), does outbound on-behalf-of-user 3LO OAuth with a BYO client (branded "Isol8 wants access" consent), 24+ built-in providers + a custom-OAuth2 provider, and vaults tokens **in our own account** (KMS-CMK Token Vault) — a genuinely different, stronger custody posture than Nango Cloud / Composio. The backend retrieves the token as a string via `GetWorkloadAccessTokenForUserId` → `GetResourceOauth2Token` (plain ECS task-role IAM, no Runtime).

**Deferred for v1, because:**
- **Delivery gap (decisive):** it vends a token to our backend; it cannot reach into the OpenClaw container. The materialize / `config_patcher` / `isol8_rematerialize` rails stay 100% ours under every option — AgentCore replaces at most the *acquisition half*, and its auto-refresh doesn't propagate into a literal already written to EFS.
- **v1 is 100% Bucket A** (paste keys) + Bucket B self-refreshing CLIs. AgentCore's one real value (provider-aware auto-refresh) lands on Bucket C = **zero live providers** (Outlook deferred). For a pasted API key it's pure overhead.
- **Worst lock-in of any option:** redirect URI pinned to `bedrock-agentcore.<region>.amazonaws.com` (baked into every provider app registration) + no bulk token export → migrating = every customer re-consents + re-register everywhere. Breaks the "flip acquisition = config change" property.
- **Time-to-ship is a wash** (saves the ~3-day dance, adds Clerk-inbound reconciliation + a session-binding service — AWS assumes Cognito/ALB-OIDC, we use Clerk); GA'd only 2025-10-13, no public Identity SLA.

**Future:** reconsider as a **(C) hybrid** acquisition backend (never a wholesale replacement — the delivery gap forbids it) only when (i) the custody constraint is formally ruled — *does first-party AWS-in-account-with-CMK satisfy "no SaaS in the critical path holds end-customer tokens"?* (passes a "no non-AWS SaaS" reading; fails a literal "our own byte-inspectable store" reading), **and** (ii) true-OAuth (Bucket C) providers cross ~5–8 — then evaluate AgentCore vs self-hosted Nango on lock-in (Nango wins reversibility; AgentCore wins managed-catalog maintenance + custody hardness). Recorded as a third `acquisition` candidate so the flip stays config.

### Corrections to Part 1 (verified this session)

- **D3 is wrong: Nango sends NO webhook on successful refresh** (`auth_refresh` is gated by `on_auth_refresh_error`, fires only on failure — `packages/webhooks/lib/utils.ts`). Token freshness comes from **lazy refresh-on-read** when the backend calls `GET /connection` during reconcile. If/when Nango is adopted, reconcile-on-read is the **primary** mechanism, not a fallback. (Largely moot for v1 — CLI actors self-refresh and there is no Nango.)
- **Self-host cost reality:** ~$161/mo dev+prod flat (54% is Aurora's non-zero floor); Nango Cloud Starter $50 + $1/connection (crossover ~131 connections). Self-host's only win over Cloud is the no-SaaS-holds-tokens rule — not cost, not refresh.

### Marketplace / BYO layering

The credential layer (**acquire + deliver**) is orthogonal to the actor layer (**consume** — a skill, MCP, or CLI a marketplace agent or a hand-added integration brings). They meet at exactly one declarative point: `requires.credentials` in the manifest (Part 1 D4).

A marketplace deploy is a **pure backend data operation into the buyer's own container — no seller code runs server-side** (`marketplace_listings.py` → `catalog_service.deploy_from_artifact`). The seller's slice ships the credential's **shape, never its value**: `catalog_slice._scrub_secret_fields` blanks `apiKey`/`env`/`headers`/`webhookToken` but **keeps the key names**, so the buyer's `openclaw.json` lands with e.g. `mcp.servers.slack.env.SLACK_BOT_TOKEN = ""` — an empty slot the credential layer fills with the **buyer's own** token via `config_patcher`/materializer. **The seller has no read/write/execute path to the value.** A BYO actor added outside the marketplace (`routers/integrations.py`) rides the same rails. In v1, an uncatalogued provider is an **Isol8-side ~1–2h PR** (registry entry + materializer + OAuth app if needed), not customer self-service.

Residual risk (named): an approved-then-malicious marketplace MCP/skill running at chat time can read the *buyer's own* co-resident credential literals/files — blast radius is one owner's own credentials (per-tenant isolation), and the steer for genuinely sensitive providers is Nango Proxy (token never on disk). The byte-level safety scanner (`marketplace_safety.py`) is best-effort; there is no intra-container tool sandbox in v1.

## The Integration Registry (core object)

One recipe per integration. Serialized in `apps/backend/core/services/credentials/providers.yaml`, loaded + schema-validated at import (`providers_loader.py`), CI-gated against every provider referenced by a deployed marketplace manifest or an installed skill's `requires.config`.

```yaml
# providers.yaml — one entry per integration

# Bucket A — paste-key (no OAuth, no refresh)
linear:
  acquisition: paste_token
  actor: mcp
  refresh_owner: none
  validate: { method: GET, url: "https://api.linear.app/graphql", auth_header: "Authorization" }
  wiring:
    openclaw_paths:
      - path: mcp.servers.linear.env.LINEAR_API_KEY
        from: input.token

# Bucket B — dedicated self-refreshing CLI
google:
  acquisition: direct_oauth          # we run the dance (Nango deferred)
  oauth:
    authorization_url: "https://accounts.google.com/o/oauth2/v2/auth"   # transcribed from Nango catalog, verified vs Google docs
    token_url: "https://oauth2.googleapis.com/token"
    scopes: [gmail.modify, calendar, drive]
    scope_separator: " "
    pkce: true
  actor: cli
  binary: gog
  refresh_owner: actor               # gog self-refreshes after one-time seed
  requires: { bins: [gog] }
  wiring:
    materializer: gog_keyring         # writes config.json + keyring on EFS

# Bucket C — true OAuth dance, MCP delivery (refresh owned by us)
outlook:
  acquisition: direct_oauth
  oauth:
    authorization_url: "https://login.microsoftonline.com/common/oauth2/v2.0/authorize"
    token_url: "https://login.microsoftonline.com/common/oauth2/v2.0/token"
    scopes: [Mail.ReadWrite, Calendars.ReadWrite, offline_access]
    scope_separator: " "
    pkce: true
  actor: cli
  binary: outlook-email-pp-cli
  refresh_owner: actor                # PP CLI self-refreshes (uniform 0600 TOML)
  requires: { bins: [outlook-email-pp-cli] }
  wiring:
    materializer: toml_cli            # 0600 ~/.config/<cli>/config.toml
```

The registry is the single place that answers, per integration: *who acquires it, who acts with it, who keeps it fresh, and exactly what files/config get written where.* Adding an integration is a PR that adds one entry (+ a materializer if a new file shape, + an OAuth app registration if `direct_oauth`).

This extends OpenClaw's own pattern: skills already declare `requires.bins`/`requires.config` (`~/Desktop/openclaw/skills/gog/SKILL.md`). The registry is the Isol8-side half that says *how to satisfy those requires*.

## Acquisition backends

> **v1 uses `paste_token` + `direct_oauth` only.** `nango` is deferred (see *v1 Decision*); `aws_sts` / `secrets_manager` are later milestones.

| Backend | When | Mechanics |
|---|---|---|
| `paste_token` | Bucket A — API keys, bot tokens | Customer pastes; validate against the provider; store (Fernet/DDB or Secrets Manager); deliver via `config_patcher`/BYOK/channels. Works **today**. |
| `direct_oauth` | Buckets B/C — OAuth providers | We run the dance ourselves (one BYO OAuth app + one callback), store the refresh token Fernet-encrypted in DDB. Same custody class as ChatGPT OAuth (`oauth_service.py:253-274`). OAuth metadata transcribed from Nango's catalog. |

| `agentcore` (deferred) | OAuth providers, at breadth — AWS-native alternative to Nango | Bedrock AgentCore Identity: in-account KMS Token Vault, 3LO OAuth w/ BYO client, `GetResourceOauth2Token` from plain ECS. Gated on a custody ruling; worst lock-in (AWS-pinned redirect URI, no token export). See the AgentCore subsection. |

| `secrets_manager` (later) | Platform-owned identity (Jarvis) | One-time admin vault in Secrets Manager + KMS. Part 1 M6. |

## Actor backends (with refresh ownership + wiring, grounded in code)

### Actor A — Agent-native CLI, self-refreshing (`gog`, self-refreshing Printing-Press CLIs)

A CLI that stores its own refresh token and mints access tokens itself.

- **Seed once, then hands-off.** `gog` keeps a refresh token in a keyring and a client config in `config.json`; PP CLIs keep both in a `0600` TOML. Once seeded, they refresh forever. `direct_oauth` runs **once**; no standing loop.
- **Headless provisioning** (verified): seed **two artifacts** — the OAuth **client** (`gog auth credentials set` / the TOML `client_id`+`client_secret`) and the **refresh token** (`gog auth tokens import -` / the TOML `refresh_token`). No TTY, no browser inside the container.
- **Wiring = a materializer, not an `openclaw.json` edit.** Write the CLI's config files onto EFS (the `workspace.py:700-786` rail). Eligibility is satisfied by `requires.bins` alone.
- **`refresh_owner: actor`** → no reconcile loop.

### Actor B — CLI or MCP needing a live access token (no self-refresh)

- **Token must be current at the moment of use.** For MCP this lands in `mcp.servers[].env` — **literal strings only** (`types.mcp.ts:6`).
- **Refresh = `isol8_rematerialize`** — an expiry-tracking + re-fetch + `config_patcher` rewrite loop; the `mcp` prefix hot-reloads (`dispose-mcp-runtimes`) so the next chat respawns with fresh env. **No container restart.**
- This is the **only** actor that carries a standing refresh loop — minimize how many integrations land here. **None of the shipped MCPs hit it** (all are paste-key, refresh_owner=none).

### Actor C — Nango Proxy (no local token) — reserved

- Agent calls provider APIs **through** Nango's proxy with a connection id; the token **never touches the container's disk**. Best hygiene; requires running Nango. Reserve for a future provider that demands tokens-never-on-disk.

### Actor D — Skill (raw API in a skill script)

- A skill reads a credential (SecretRef→`file`, resolved at use-time) and calls the API directly. For simple single-call integrations where a whole CLI/MCP is overkill.

## Refresh-ownership decision matrix

| Actor | Token lives | Refresh owner | Standing loop? |
|---|---|---|---|
| Paste-key (A/B) | literal env / config | `none` (long-lived) | No |
| Self-refreshing CLI (`gog`, PP) | CLI config/keyring on EFS | the CLI (`actor`) | **No** |
| MCP/CLI, live OAuth token | `mcp.env` literal / token file | `isol8_rematerialize` | Yes |
| Nango Proxy (reserved) | nowhere in container | `nango_proxy` | No |

**Design bias:** prefer paste-key (no refresh) and self-refreshing CLI (Actor A) wherever possible; reserve Proxy for sensitive providers; fall to Actor-B `isol8_rematerialize` only when forced. The fewer integrations in the live-token row, the less standing machinery.

## Printing Press's role

Printing Press generates **actor backends**, not acquisition. For a provider with no good off-the-shelf CLI/MCP, run `/printing-press <service>` to generate a token-efficient Go CLI, **vendor it at a pinned commit** (never `@latest`), bake the binary, add a registry entry.

**Spike RESOLVED 2026-05-29** (`docs/architecture/credentials/2026-05-29-printing-press-spike.md`; inspected `mvanhorn/printing-press-library`). PP CLIs follow **one uniform auth contract**, both self-refreshing and env-injectable on the same binary:

- **Self-refresh (Actor A):** OAuth CLIs (`figma`, `outlook-calendar`) ship `auth login`, persist `access_token`/`refresh_token`/`token_expiry` to a `0600` TOML, and **auto-refresh on next request** (figma `internal/cli/auth.go:217`; outlook `internal/oauth/device.go:258-322`). Same model as `gog`, TOML instead of keyring.
- **Env override (Actor B):** every CLI honors *"Env-var token wins over file-stored AccessToken"* — a `<PROVIDER>_TOKEN` env overrides the file.
- **Uniform:** even key-only providers carry the same `SaveTokens`/`refresh_token` struct (fields just stay empty).

**Consumption (assessed 2026-05-29):** Apache-2.0 (not the README's "MIT") — bake **with NOTICE attribution**; **3 unlicensed CLIs excluded**. **Vendor at a pinned commit + per-CLI allowlist** (never `@latest` — monorepo HEAD pseudo-version is a supply-chain trap; ~125/198 hold real customer creds). Quality is uneven (15 FAIL / 54 WARN; runtime-verify is a no-op; **no upstream API-drift detection** — screen each CLI's `dogfood-results.json`). Build blocker: bump Dockerfile `GO_VER` 1.24.2 → 1.26.3. `.dockerignore` strips `SKILL.md` (seed onto EFS or `!`-negate).

## Milestones (v1 = build-our-own panel)

Detailed, executable task breakdown: **`docs/superpowers/plans/2026-05-29-integrations-panel-build.md`**. Summary:

- **M0 — Printing Press refresh spike ✅ DONE (2026-05-29).** PP CLIs self-refresh + env-override (uniform contract). Evidence in the spike doc.
- **M1 — Integration registry foundation.** `providers.yaml` (extended schema) + `providers_loader.py` + validation + CI gate. Migrate `key_service` allowlists into the registry.
- **M2 — Credential vault + wiring engine.** Extend the `oauth-tokens` DDB table with a `provider` sort key (reuse `oauth_service` Fernet); `apply_connection` dispatching to (a) `config_patcher` literal injection, (b) materializer, (c) existing BYOK/channels rails. Unit-tested with mock payloads.
- **M3 — Materializer.** Interface + `toml_cli` (generalize `workspace.py:700-786`, for PP CLIs) + `gog_keyring` (for `gog`). Atomic 0600, EFS-chroot, chown 1000.
- **M4 — Paste-key panel (Bucket A).** Connect/validate/inject API-key integrations behind the registry (unifies `key_service` + channels). Lowest-risk bucket ships the panel UX first.
- **M5 — OAuth dance scaffolding (Buckets B/C).** Shared PKCE+state DDB store, registry-driven authorize-URL builder, generic `GET /oauth/{provider}/callback`, exchange → vault → `apply_connection`. The one genuinely new piece (~3 days).
- **M6 — First OAuth integration end-to-end: Google via `gog`.** Registry entry + `gog_keyring` materializer + dance + `gog` self-refresh. Smoke in a one-off task, then live in chat. No container restart.
- **M7 — Connections panel UI.** Frontend list / connect / status / disconnect, modeled on `MyChannelsSection.tsx` + `useChatGPTOAuth.ts`.
- **M8 — Marketplace `requires.credentials` seam.** Pre-deploy validator blocks deploy + surfaces Connect for missing providers; fill empty slots with the buyer's token on deploy; extend `marketplace_safety` with credential-leak rules.

**Deferred (post-v1, when triggers hit):**
