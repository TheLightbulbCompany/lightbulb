# OpenClaw 5.28 → 6.1 config breaking-change audit

**Date:** 2026-06-06
**Context:** The MCP cold-connect-storm fix ships as a fork base-image bump
(upstream OpenClaw `2026.6.1` + patches B/D), merged in #822. Before promoting
the fork-based extended image to an environment, we must confirm the
`openclaw.json` our backend emits is valid against 6.1's **strict** config
schema — an unrecognized/removed key crash-loops the container at boot (this is
how the `embeddedHarness` key bricked the 5.12 → 5.28 bump).

## Method

1. Generated the full config matrix `build_openclaw_config_dict` emits — every
   `provider_choice` (`bedrock_claude`, `byo_key` anthropic/openai,
   `chatgpt_oauth`) × `owner_type` (personal/org) × paperclip present/absent ×
   integration MCP server present/absent. 7 representative configs.
2. Validated each against 6.1's **actual boot validator**
   (`validateConfigObjectWithPlugins`, the function `src/config/io.ts` calls at
   gateway startup) in the fork checkout at tag `v2026.6.1-isol8.1`.
3. Probed schema strictness empirically.

## Findings

### ✅ No config-brick. All 7 configs are boot-valid against 6.1.

The 6.1 schema is **strict** — confirmed empirically: it rejects an injected
junk top-level key, a junk nested key, *and* the exact `embeddedHarness` key
that bricked 5.12 → 5.28 (`Unrecognized key: "embeddedHarness"`). Because the
strict boot validator **accepted every one of our configs with zero dropped
keys**, our emitted `openclaw.json` contains nothing 6.1 doesn't recognize.
There is no embeddedHarness-class removed-key brick in the 5.28 → 6.1 bump for
our config.

### ⚠️ Deferred (6.1-only optional keys — do NOT emit until the env's image is 6.1)

Two enhancements exist in 6.1 that our config does not emit, and **must not** be
emitted unconditionally while any environment still runs 5.28 (5.28's strict
schema would reject the unknown key and brick on reprovision — the same trap
Codex flagged for `mcp.runtimeScope`):

- **`mcp.runtimeScope: "shared"`** — activates fix D (shared MCP runtime reuse).
  Reverted in #822; deferred.
- **`channels.{slack}.mode` / `channels.{discord,telegram}.groupPolicy`** — 6.1's
  bundled-channel validator (`collectRawBundledChannelConfigIssues`) flags these
  as required for enabled channels. **They are NOT enforced at boot** (the core
  schema treats them as optional; the strict validator that requires them is an
  opt-in nothing in the boot path calls), so they are not a brick. But our
  channels ship `enabled: true`, so 6.1 channel *activation* behavior with these
  absent should be observed on dev and the fields likely added before prod.

**Recommended pattern for both:** gate emission on
`openclaw_version.deployed_upstream_version()` so a 6.1-only key is written only
when the env's deployed extended image is ≥ 6.1. That activates D + the channel
fields per-env automatically as each env's tag is promoted, with zero brick risk
on the lagging env.

## Decision

Promote to **dev** first (`dev.tag` → `2026.6.1-isol8.1-9a12256`) with `config.py`
**unchanged** — the config is boot-valid on both 5.28 and 6.1. Reprovision a dev
container and observe: boot logs, chat round-trip, the MCP non-blocking
materialization fix (no "RPC timed out"), and channel activation behavior. Prod
promotion + the 6.1-gated config enhancements follow after dev validation.
