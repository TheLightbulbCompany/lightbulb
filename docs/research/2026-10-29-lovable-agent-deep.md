# How Lovable's agent works, in depth (29 Oct 2026)

The question: how does Lovable's builder agent work inside (modes, tools, loop, rules, how it decides, how it tests and fixes, how it handles the backend), so Lightbulb's builder agent can match or beat it? Every source was fetched on 2026-10-29. Tags: **[P]** primary, meaning Lovable's own docs, changelog or blog; **[S]** secondary, meaning interviews, third-party write-ups, or open-lovable as a documented proxy (its code is primary for open-lovable, secondary for Lovable); **[U]** unverified, meaning leaked prompts and claims no source backs.

This doc builds on two earlier ones and does not repeat them: `2026-10-29-how-lovable-builds.md` (user loop, dev/prod, drafts, Drizzle add-only, publish, payments test/live, 10 free fixes, 10-hour runs) and `2026-10-28-small-software-open-lovable-read.md` (open-lovable sandbox and stream). Docs root `https://docs.lovable.dev`, written below as `docs/…`. Blog root `https://lovable.dev/blog/…`.

## 0. The short version
- **One agent edits, others read.** One main builder agent owns every file change. Read-only subagents (a generic kind and an "Explore" kind) research in parallel with fresh context and report back [P] docs/features/subagents.
- **The loop is a logged event stream, not a chat transcript.** Each LLM call is an iteration in an append-only, forkable "trajectory". The prompt is re-rendered from that log every iteration, compaction is an event, and runs can suspend and resume on any machine [P] https://lovable.dev/blog/how-lovable-agents-work-together (24 Sep 2026).
- **Three modes split by permission, not by model.** Chat (no code changes), Plan (no code changes, writes `.lovable/plan.md`), Build (changes and verifies). A `/goal` message is Build that does not stop to ask [P] docs/features/chat-mode, plan-mode, agent-mode, goal-runs.
- **Verification is cheap-first.** It runs automatically only for the tests it writes for business rules (Oct 2026). Browser testing is "selective, after trying faster verification methods first". Everything else runs when asked [P] docs/features/testing, browser-testing.
- **Lovable fixes the platform, not the prompt.** Its levers are a vent tool the agent uses to report broken tools, a curated "Lovable Stack Overflow" injected when a conversation is detected as stuck, LLM judges calibrated against human labels, and multi-run evals scored on the finished app [P] https://lovable.dev/blog/we-gave-our-agent-a-vent-tool (21 May 2026), https://lovable.dev/blog/the-model-picker-is-a-dead-end (11 Aug 2026).

## 1. The loop, from message to changed preview

### 1.1 What Lovable says the loop is
- "Behind every message, Lovable's agent works in a loop: it gathers context from your conversation and project, takes action with tools, and checks the result before moving on" [P] docs/features/projects/chat.
- At the agent-mode beta (30 Jun 2025) the steps were spelled out: "First interpret what you are asking for / Explore the codebase as needed / Uncover missing context / Make the right changes / Auto-fix issues as they come up / Wrap up with a clear summary." Before that, "The default version of Lovable tries to do everything in one single step." The beta claimed it "Reduces build error rates by 90%" and "Cuts down on unwanted changes" [P] https://lovable.dev/blog/agent-mode-beta. Agent mode became the default on 11 Aug 2025 ("reducing errors by 91%"); legacy single-step mode was retired on 1 Sep 2025 [P] docs/changelog.
- Beta tools, as listed: search the codebase for "the exact files, functions, or components"; "Read files on demand"; "Inspect logs and network activity… without you needing to feed in the errors yourself"; web search for docs, content, images or screenshots; image generation and editing [P] https://lovable.dev/blog/agent-mode-beta.
- Later additions: video generation; "Suggests publishing at the right moment and opens the publish menu"; "Cleans up unused edge functions"; "Tests authenticated edge functions while you're logged in"; "IDE-level code intelligence for types, references, and relationships" (16 Jan 2026) [P] docs/changelog. Browser performance profiling ("Core Web Vitals, resource loading, memory usage, DOM complexity, and long tasks", CPU profiles) (2 Apr 2026) [P] docs/changelog. Chat-history search: "retrieve specific past messages, run keyword searches… and answer semantic questions" (24 Apr 2026) [P] docs/changelog. Awareness of which editor tab the user is on, and screenshots on request (5 Nov 2025) [P] docs/changelog.

### 1.2 The runtime underneath (the Sep 2026 architecture post)
This is the most detailed primary account of the loop, from Lovable engineer Rouzbeh Delavari [P] https://lovable.dev/blog/how-lovable-agents-work-together (24 Sep 2026):
- **Trajectory = append-only event log.** Events include `UserMessage`, `AgentStart/AgentDone`, `IterationStart/IterationEnd` around each LLM call, thinking and content events, and a full tool lifecycle: `ToolParametersValidated`, `ToolExecutionStart`, `ToolExecutionEnd`, and `ToolApprovalRequired` when a human must approve. "Nothing is thrown away: events are immutable and append-only." Reverts are `Revert` events.
- **Git-like forking, never merging.** Each event has one parent; any `IterationEnd` or `AgentDone` can be forked cheaply; "Trajectories only ever branch." Agents share results by message.
- **Context is a projection.** A prompt builder walks the trajectory backward each iteration and renders the prompt. Compaction is `PromptCompactionStart/End`; "a summarizer runs asynchronously on a side trajectory", admitted at the next iteration boundary. Builder, subagents and other agents render the same events through different presets.
- **Inbox vs trajectory.** Other actors "only ever write to the inbox, never to the agent trajectory." Unhandled inbox items are copied onto the trajectory at run start and at each iteration boundary. That is how mid-run follow-ups work: they are "picked up at its next natural stopping point" [P] docs/features/projects/chat.
- **Control plane.** `SpawnAgent`, `ForkAndSendMessage`, `SendMessage`, `NotifyParents`, `StopAgent`. "Agents don't call each other… or know which machine the other is on."
- **Suspend/resume.** At an iteration boundary a run can exit "suspended"; any node can resume. "A dead sandbox causes the run to suspend rather than retry blindly." "The agent process is genuinely disposable; the work lives in the trajectory and in git."
- **Scale.** About half a billion events on a typical weekday, about 2.6 million user turns; Bigtable for events, a content-addressed blob store for large payloads such as "knowledge files and file changes"; Pub/Sub activations with a reconciler.
- **Chats → project.** The workspace-level Chats agent hands work to a project with `send_message_to_project`. "The builder sees only the message it receives"; the chat agent must write a self-contained brief.

### 1.3 Which files it reads
- Lovable documents no fixed "read these files first" list. It says the agent "explores the codebase for context" [P] docs/features/agent-mode, uses code search and on-demand reads [P] blog/agent-mode-beta, and has IDE-level type and reference intelligence [P] changelog 16 Jan 2026.
- The user can pin context with `@file` or `@project`; cross-project reads are "read-only and respects workspace permissions" [P] docs/features/agent-mode.
- Always in context: workspace and project Instructions ("always part of the context") and any repo `AGENTS.md`/`CLAUDE.md` (§6) [P] docs/features/knowledge. Skills load only when a request matches their description [P] docs/features/skills.
- Before the agent loop, the stack injected the relevant files itself: "Responds faster by selecting relevant information more efficiently during generation" [P] changelog 16 Jan 2026. The leaked prompt shows "useful-context" blocks pre-filled with files and a rule to avoid re-reading them [U] (§9).

### 1.4 How it edits
- **Lovable does not document its edit format.** The docs say only that changes are "surfaced through file diffs and summaries" with a Changes tab [P] docs/features/agent-mode. One changelog line (4 Apr 2025) mentions a "Refactor of diff creation which handles multiple edits to the same file" [P]. The March 2025 diff-viewer post covers only rendering: more output from Claude 3.7 Sonnet meant "more changes to more files at once", so the viewer renders "in small batches of 2 with 50ms delays" [P] https://lovable.dev/blog/anthropic-sonnet-3-7-lovable-diff-viewer.
- **Visual Edits do not use the LLM for simple changes.** A custom Vite plugin gives "each JSX component generated by our AI… a unique, stable ID". The code is held as an AST in the browser (Babel/SWC), a client-side Tailwind generator previews class changes, and the saved AST is written back as JSX with line-level diffs and HMR, "without requiring AI intervention" [P] https://lovable.dev/blog/visual-edits (13 Mar 2025). Since 2 Apr 2026 visual edits are "fully AI-powered and work across your entire app, including dynamic content" [P] changelog. Inline text edits "now apply in a few seconds" (7 Oct 2026); text built from data or translations "takes a little longer" [P] changelog. So simple text edits take a deterministic fast path, and the rest goes to the model.
- The leaked prompt (§9) names the tools: a line-range search-replace (`lov-line-replace`) preferred over full writes, and `lov-write` with `// ... keep existing code` markers [U].

### 1.5 Build, watch, iterate, stop
- **What it watches:** "build errors and failures from test runs", and console and network output "when verification tools are used" [P] docs/features/agent-mode. "Lovable reads your app's console logs itself" [P] docs/prompting/prompting-debugging. Network logs have been read as context since 21 Feb 2025 [P] changelog.
- **Iteration:** it "can inspect logs, runtime output, and network activity and iterate on fixes until the issue is resolved or clarified" [P] docs/features/agent-mode FAQ.
- **Stop conditions:** (a) the work is done and the tests that cover a changed rule pass [P] docs/features/testing; (b) a question card, up to four questions with options [P] docs/features/projects/chat; (c) a credit check-in, 20 credits by default [P] docs/features/agent-mode; (d) the user presses stop; completed changes are kept [P]; (e) the 10-hour cap, with "In the final half hour, Lovable wraps up… summarizes what is done and what remains" [P]; (f) for goals, it stops "early only when it needs something that only you can provide, such as access to another service" [P] docs/features/goal-runs; (g) out of credits pauses the run and does not end it (18 Aug 2026) [P] changelog.
- **The end of a turn** is a summary of "what changed and what you can do next", Undo/Revert actions, "Worked for / Credits used", and suggestion chips for what to build next [P] docs/features/projects/chat.
- **Separate runs:** Try to fix, security one-click fixes, inline text edits and preview comment threads are queued as "Runs after the current task" and never merged into a running task [P] docs/features/projects/chat.

## 2. Modes

| Mode | May change code? | What it does | Price | Source |
|---|---|---|---|---|
| **Chat** ("Ask anything, explore ideas") | No | Reads code, files, the app's data (when Cloud is on), the conversation, referenced projects and connected tools. Connectors read without asking; writes through connectors ask unless "Always allow" is saved | Usage, "typically a fraction of a credit", daily chat allowance first | [P] docs/features/chat-mode |
| **Plan** ("Detailed spec for complex builds") | No | Investigates "across multiple steps, inspecting files, logs, and other relevant context", often asks clarifying questions, and writes a plan only "when there is a clear implementation to propose" | 1 credit plus subagent research | [P] docs/features/plan-mode |
| **Build** (was Agent) | Yes | "takes ownership of execution end to end… resolves issues that appear during development" | Usage; "Many requests cost less than one credit" | [P] docs/features/agent-mode |
| **Goal** (`/goal`, a Build message) | Yes | Works "until the goal is achieved", up to 10 h, "doesn't pause to ask questions about the work", "builds the finished version" | Costs "noticeably more… the same work uses more credits" | [P] docs/features/goal-runs |
| **Visual edits / preview toolbar** | Yes, scoped | Select an element, edit text inline, draw, comment; queued as a separate run | Free within daily limits (Apr 2026) | [P] changelog 2 Apr 2026, docs/features/projects/chat |

- **Naming history:** "Chat mode" was the original no-code-change mode, renamed "Plan Mode" on 5 Feb 2026 [P] changelog. A new conversation-only Chat mode came back on 21 Sep 2026 (prior doc). In Dec 2025 a new project could be started in Chat mode ("Instead of immediately generating an app from your first prompt… have a conversation") [P] https://lovable.dev/blog/chat-mode-and-questions (5 Dec 2025).
- **The plan artefact:** overview; "Key decisions, assumptions, and constraints"; "Components, data models, and APIs"; step sequencing; optional diagrams. The user can edit inline, highlight a section and comment ("Lovable edits just that section rather than rewriting the whole plan"), browse versions, Approve or Skip. Approve "switches to Build mode" and "continues until the plan is complete" [P] docs/features/plan-mode. The file lives at `.lovable/plan.md` and moves to a dated file in `.lovable/plan/` on approval, "so context persists across messages" [P] changelog 5 Feb 2026.
- **When the product steers to Plan:** the docs, not the agent, steer to Plan for "larger or riskier changes", for comparing approaches, for schema design, and above all after one or two failed fixes: "Stop retrying blind fixes… Switching to Plan mode after one or two failed attempts is usually faster" [P] docs/prompting/prompting-debugging. Build mode asks for permission to test larger features: "There is a larger feature change, and Lovable offers to test the flow and you confirm" [P] docs/features/browser-testing. No doc says the agent switches itself into Plan mode.
- **Autonomous behaviours in Build:** explores, edits across files, starts subagents, generates assets, reads logs, writes rule tests, auto-fixes eligible security findings when enabled, enables Cloud (or asks, per permission), saves pasted keys as secrets, suggests publishing [P] sources in §1, §4, §5. On questions, skipping "continues with reasonable defaults for the work you already asked for. It does not treat the skip as approval for additional work it suggested" (15 Sep 2026) [P] changelog.
- **Agent permissions:** one page lists "what Lovable may do without asking you first, for each connector… and for creating or editing projects from a chat", each Always allow / Ask each time / Never allow (21 Sep 2026) [P] changelog. Cloud permissions add "Enable Cloud" and "Execute backward incompatible database migrations" (prior doc).

## 3. Rules and defaults

### 3.1 Stack and structure
- **Stack:** new apps since 13 May 2026 use TanStack Start on Cloudflare Workers. TanStack Server Functions replace separately deployed edge functions, and Supabase remains the database, auth, storage and realtime layer. "The AI marks the server-only parts with createServerFn and the build handles the rest": server logic sits in the same file as the component that uses it [P] https://lovable.dev/blog/building-apps-using-tanstack-start (1 Jun 2026). The reason given is SEO and link previews; SPAs "rendered entirely in the browser" [P] same.
- **Tests:** Vitest, React Testing Library and jsdom in `src/test/*.test.ts(x)`; Deno's runner for edge tests [P] docs/features/testing.
- **Lovable-owned files:** `drizzle/`, `drizzle/schema.ts` and `drizzle.config.ts` ("leave them as they are"); `.lovable/plan.md` and `.lovable/plan/`; `.env` holding public `VITE_*` values, which must stay committed ("Gitignoring it will break the preview") [P] docs/features/database, plan-mode, secrets. Design-system components are copied into `src/design-system/<slug>/` [P] docs/features/design-systems.
- **What it refuses:** native mobile ("it does not generate React Native projects") [P] docs/introduction/faq; unsupported Postgres extensions ("Lovable builds it with plain SQL instead") [P] docs/features/database; breaking schema changes by default [P] same; `VITE_` names in Secrets [P] docs/features/secrets; buying a domain or acting through a connector without a confirmation card [P] docs/features/projects/chat, chat-mode. For WebMCP tools in a generated app, it "starts with tools that read information or are easy to undo, and adds tools that delete, pay, send, publish, or share only when you ask" (13 Oct 2026) [P] changelog. That is a reversibility rule, and it applies to the app it writes.
- **History of one rule:** "Lovable will no longer introduce refactors automatically" (3 Dec 2024) [P] changelog. The Sep 2025 leaked prompt instead says "Always consider whether the code needs refactoring" [U] (§9). Lovable's own docs lean towards minimal diffs: the community snippets say "Change only what this task requires… If you notice improvements outside the task, list them separately" [P] docs/prompting/prompting-debugging.

### 3.2 Design defaults and how it decides the look
- **Questions or build:** one card with up to four questions, three of them design questions (palette, font pair, layout from a fixed list of about 15 wireframes such as "hero grid… bento grid… dashboard"), first option preselected. A fourth question is added "when the project needs it, for example what content the site will have" [P] docs/features/design-guidance.
- **When it asks:** visually open prompts ("Build me a portfolio site"). **When it skips:** an explicit style, purely functional requests, "app types [with] standard defaults, such as dashboards, admin panels", or a project that already has a template or design system [P] same. From the choices it "derives details such as spacing, corner radius, and animation intensity" [P] same.
- **Three design directions,** rendered previews before the first build, shipped 18 May 2026 and **removed 8 Oct 2026**. Lovable "now builds the look directly" [P] changelog. A mock-up step before the build was tried and dropped after five months.
- **Design-system enforcement:** "every generation is scanned for violations": raw colour literals, one-off values, local re-implementations of system components. It auto-retries before finishing [P] docs/features/design-systems; prior doc.

### 3.3 Writes without asking vs asks
| Without asking (defaults) | Asks first |
|---|---|
| Code edits in Build; new files; packages | Clarifying and design questions when scope or look is open [P] chat, design-guidance |
| Enable Cloud ("Always allow" default) [P] docs/features/cloud | Enable Cloud when set to Ask; region shown only then [P] same |
| Additive migrations, type regeneration [P] database | Breaking migrations (default Never; Ask shows SQL) [P] same |
| Rule tests; auto-fix of eligible Quick-scan findings when on [P] testing, security | Which app user to sign in as when there are several; impersonation is admin-only [P] browser-testing |
| Saving a pasted key as a secret [P] secrets | Secret values, through a secure form, never in chat [P] secrets |
| Connector reads [P] chat-mode | Connector writes, Stripe product creation ("asking for your approval first"), domain purchase [P] chat-mode, integrations/stripe, chat |
| Routine decisions inside a `/goal` [P] goal-runs | Anything "only you can provide" inside a goal [P] same |

## 4. Self-checking

- **Try to fix** is a separate run that "scans the logs, finds the issue, and attempts a fix". Ten free fixes are shared across Try to fix and security fixes, each renewing 24 h after use (limit added 11 Aug 2026) [P] docs/features/projects/chat, changelog. The same button blocks Publish while the latest build fails [P] same.
- **Error-loop handling is advice, not a mechanism.** Lovable documents no automatic loop breaker for users. The docs tell the user: one or two Try to fix, then "Stop retrying blind fixes", go to Plan mode, then revert. Its reasoning: "Repeated blind fixes tend to pile up code that hides the real problem" [P] docs/prompting/prompting-debugging. The Testing FAQ ends the same way: "If the issue still does not resolve, revert to the latest stable version" [P] docs/features/testing.
- **Internally, Lovable detects stuck conversations.** "LLM judges flag stuck conversations… calibrated against hand-labeled data and revalidated whenever prompts or models changed." On detection it injects a curated "Lovable Stack Overflow" knowledge base into the agent's context; the early version "cut stuck rates by about 5% and raised publish rates by about 2%". Users stuck early were "about 4x more likely to leave". Lessons: AI rewrites of the knowledge drifted "toward low-quality 'AI slop'"; entries go stale, so they run "random drop-out A/B tests and prune"; failure modes vary by model, so every new model means re-discovering them [P] https://lovable.dev/blog/we-gave-our-agent-a-vent-tool.
- **The vent tool.** The agent can post frustrations to Slack (#agent-vents). About 20% of vents were actionable; a debug agent opens auto-PRs, about half of them false positives, with ~10 fixes merged a day after human review. The agent "got stuck in futile retry loops less often". One agent sent 43 vents in minutes, so the limit is now one vent per message [P] same. **The agent reports broken tools; it does not retry them forever.**
- **Recovery targets the failure.** "Recovery should change the thing that failed, whether that is the context, plan, tool, or model." Provider overload goes to the same model through another provider [P] https://lovable.dev/blog/the-model-picker-is-a-dead-end. Routing pins a project to one provider chain "for the next few minutes" so the prompt cache holds, with a PID controller re-weighting providers every 30 s on error rate [P] https://lovable.dev/blog/routing-billions-of-tokens-per-minute (4 Mar 2026).
- **Tests it writes (16 Oct 2026):** when a rule changes ("a price, a limit, a permission, a date, or who can do what"), it adds a small test, keeps it, and "runs the tests that cover your change" before reporting done. It writes none for "copy, styling, markup, or snapshots". On TanStack apps it also tests server-side logic; edge tests only on request [P] docs/features/testing.
- **Browser testing:** a remote browser drives "the version of the app you are viewing", with screenshots, clicks, forms, console and network capture, and viewport sizes. It runs "selectively, after trying faster verification methods first": when the user says "verify it works / make sure it works / test this", when "Visual or UI issues can't be pinpointed through logs or code inspection", or when Lovable "offers to test the flow and you confirm" after a larger change [P] docs/features/browser-testing. Known limits: canvas, complex uploads, drag-and-drop, clipboard, "subtle visual design details or color differences", icon-only buttons. Fix for a stuck element: "make the element easier to interact with (for example, by adding visible text or an accessibility label)" [P] same. Advice: "Avoid asking Lovable to make a large change and test it in the same prompt… build first, then test in a follow-up" [P] same.
- **Backend checks:** direct edge-function calls with the user's session; reproduce → fix → re-call → add an edge test [P] docs/features/testing. "Tests authenticated edge functions while you're logged in" [P] changelog 16 Jan 2026.
- **Security scan in the loop:** Quick scan on every publish covers the dependency audit, unauthenticated MCP servers, and a database review ("tables without per-record access control and rules that let everyone through", storage rules, leaked-password protection). The Deep scan adds leaked secrets in code or repo, auth bypass, data exposure in logs and errors, server code that ignores DB ownership, and role checks on privileged actions [P] docs/features/security. Auto-fix "adds a few of the latest **Critical** database findings and dependency findings… to what it knows about your project when you send a build request". It is limited to "safe" classes (RLS, access patterns, vulnerable deps) and never covers Deep-scan findings [P] same. **Security memory**: a per-project document the scanner reads first ("access control model, business logic rules, and risks you have already reviewed and accepted"), which the scanner itself can append to. Lovable reports about 20% fewer ignored findings [P] changelog 18 May 2026; https://lovable.dev/blog/how-lovable-protects-your-apps-automatically. Pasted keys are detected and turned into secrets [P] docs/features/security.
- **After launch:** Project monitoring reviews "project code" and "Visitor errors" daily at 06:00 (only if edited), posts a brief above the chat, and emails the owner [P] docs/features/project-monitoring.
- **What counts as done** (assembled from the above, since Lovable never states it in one place): the build compiles; the tests covering changed rules pass; there are no design-system violations; a summary is written. Browser verification is not required unless asked or offered. Publish adds the Quick scan.

## 5. Backend decisions

- **Trigger:** "When a feature you ask for requires backend functionality (for example, authentication or file storage), Lovable enables the backend automatically or asks." Database, auth and storage are provisioned together ("Enabling any one of them provisions all three"). It cannot be enabled from a draft [P] docs/features/cloud. Lovable publishes no decision rule beyond "requires backend functionality". The prompting guide teaches users to "anticipate" auth state, dynamic content, and empty/loading/error states [P] docs/prompting/prompting-one.
- **Schema:** "Describe the data your app needs… Lovable creates the tables"; it "also updates the type definitions in your app's code"; every change is a Drizzle SQL file in `drizzle/migrations/` (older projects use `supabase/migrations/`) [P] docs/features/database. Destructive SQL in the editor needs confirmation [P] same. The leaked tools show a table-schema tool that also returns "security analysis prompt" text [U] (§9). That implies the RLS review prompt is fed in alongside the schema.
- **Server code:** edge functions are "written, deployed, and maintained" by Lovable, with no create button in the UI; scheduled work goes in "Jobs"; unused functions are cleaned up [P] docs/features/edge-functions, changelog. On TanStack Start, `createServerFn` lives in the component file [P] TanStack blog.
- **Secrets:** a secure form whose message says "which secret it needs and why"; Skip is allowed, and dependent parts stay broken until the secret is added; a "Generate" button covers secrets shared between two systems; values are never echoed "in the project chat, in logs, or in your code"; secrets are write-only; `VITE_` values are rejected [P] docs/features/secrets, changelog 9 Oct 2026.
- **Payments:** "it analyzes your project and either presents both options or recommends a specific provider based on what you are selling", steering away from a provider whose policy restricts the product. Built-in payments create products, prices, checkout and UI, register two webhooks per environment (the app's own and Lovable's monitoring copy), and add a preview-only test banner [P] docs/features/payments. **Bring-your-own Stripe:** a restricted key (`rk_`) through a form; checkout via edge functions; subscriptions checked "directly with Stripe" on sign-in, with **no webhooks by default** ("enough for most apps"); products are created after approval [P] docs/integrations/stripe.
- **Email:** auth emails come from six branded templates generated on request; app emails are generated from the feature ("order confirmations, purchase receipts"); an unsubscribe footer is added automatically; sending is from `notify.<domain>`; there are hourly send caps [P] docs/features/custom-emails.
- **AI features in the app:** the built-in connector with an auto-managed `LOVABLE_API_KEY`; "describe the result you want and Lovable picks a supported model" [P] docs/features/ai.

## 6. Context: what it knows, keeps, forgets, retrieves

- **Always loaded:** workspace Instructions and project Instructions (10,000 characters each; "Lovable is encouraged to prioritize" project on conflict). "root-level `AGENTS.md` files are always read by the Lovable agent regardless of session length". Connector knowledge files [P] docs/features/knowledge. The phrase "regardless of session length" suggests other context can drop out of long sessions [U, inference].
- **Loaded on demand:** Skills, whose description is the trigger ("Start with 'Use when...'"). Built-in skills cover accessibility checks, redesigns, SEO reviews, skill creation and video. Skills use the Agent Skills `SKILL.md` format and can be imported from Claude [P] docs/features/skills.
- **Plans persist as files** (`.lovable/plan.md`, archived) "so context persists across messages" [P] changelog 5 Feb 2026. Security memory is a separate file [P] §4.
- **Compaction:** summaries are produced asynchronously on a side trajectory and swapped in at an iteration boundary; nothing is deleted from the log [P] Sep 2026 architecture post.
- **Retrieval:** chat-history search by exact message, keyword, or semantic question (24 Apr 2026) [P] changelog; cross-project read of "code, files, assets, and project chat history" [P] docs/features/agent-mode; an LLM-assembled starting context ("they're also used to assemble the context that kickstarts that agent"; "our agent typically does some exploration before starting code generation") [P] https://lovable.dev/blog/routing-billions-of-tokens-per-minute.
- **Large projects:** subagents exist because "The chat can quickly fill with file contents, search results, logs, stack traces… and abandoned paths". They keep that out of the main context and run in parallel; "Explore uses the most capable model available", while routine lookups go to "lighter models" [P] docs/features/subagents. A file over 10 MB cannot be committed and is moved to a CDN on request [P] docs/features/projects/chat.
- **What users are told to do about forgetting:** after a hard bug, "Summarize what the issue was and how we fixed it, so we can add it to the project instructions"; after a revert, "tell Lovable what you did so it has the context"; save design keywords to Instructions [P] docs/prompting/prompting-debugging, prompting-one. **That is the admission: lessons do not carry over between sessions unless a human writes them into Instructions.**

## 7. Quality levers and what the prompting guide reveals

| User advice in Lovable's docs | Weakness it reveals |
|---|---|
| "Prompt by component, not page… A full-page prompt gets you noise" [P] prompting-one | Large single-shot generations lose fidelity |
| "Say what to change and what to leave alone… a small request can ripple into parts of the app that already work" [P] prompting-one | Scope creep and collateral edits |

## 8. open-lovable where Lovable's docs are silent
Read first-hand at `firecrawl/open-lovable` commit `806b807` (9 Oct 2026). It is a proxy, not Lovable's code [S as a proxy; code facts are first-hand].
- **Edit targeting is a two-step plan, not tools.** `app/api/analyze-edit-intent/route.ts` asks the model (`generateObject`) for a *search plan* rather than a file choice: `editType` ∈ {UPDATE_COMPONENT, ADD_FEATURE, FIX_ISSUE, UPDATE_STYLE, REFACTOR, ADD_DEPENDENCY, REMOVE_ELEMENT}, `searchTerms` ("Be VERY specific - exact button text, class names"), `regexPatterns`, `expectedMatches` (1–10), and a `fallbackSearch`. `lib/file-search-executor.ts` runs the plan, and the hit becomes the one "Files to Edit" target. `lib/context-selector.ts` always adds `App.jsx`, the Tailwind config, `index.css` and `package.json` as context.
- **A forced "mental diff" before code** (`generate-ai-code-stream/route.ts` ~L404): Understand Intent → Locate the Code ("'nav' might be Navigation.tsx, NavBar.tsx… DO NOT create a new file if a similar one exists!") → minimal changes → "Verify Preservation" → write.
- **Full files, with an optional fast-apply.** The default output is whole `<file>` blocks ("NEVER TRUNCATE FILES"; "It's better to have 3 complete files than 10 incomplete files"). With `MORPH_API_KEY` set, edits come as `<edit target_file><instructions/><update/></edit>`, merged by `morph-v3-large` (`lib/morph-fast-apply.ts`; parsed in `apply-ai-code-stream/route.ts` L283). This corrects the 28 Oct doc's claim that edit blocks are not parsed.
- **Scope rules are written as threats:** "YOU MUST ***ONLY*** GENERATE THE FILES LISTED ABOVE… DO NOT fix unrelated issues… VIOLATION OF THESE RULES WILL RESULT IN FAILURE". There is a "RECENTLY CREATED/EDITED FILES (DO NOT RECREATE THESE)" list, and conversation memory is trimmed to the last 5 messages, 3 edits and 2 major changes (`conversation-state/route.ts` L85–88).
- **Error handling is mostly not wired.** `check-vite-errors` is a stub that returns `errors: []` ("This endpoint is being called but the source is unknown"); `lib/build-validator.ts` (`validateBuild`, `classifyError`, retry delays) has no callers. The one closed loop is that imports are regex-scanned after apply (`detect-and-install-packages`), missing packages are `npm install`ed, and Vite restarts (`apply-ai-code/route.ts` L280–327). The LLM call itself retries transient provider errors with linear backoff (L1329–1356). **No runtime error is ever fed back to the model.**
- **The lesson:** open-lovable shows what one-shot generation needs as scaffolding (intent classifier, search plan, preservation rules). Lovable's 2025 move to a tool loop cut build errors by about 90% [P], and that loop is what replaced the scaffolding.

## 10. Builder agent spec for Lightbulb

### 20 rules and mechanics to adopt
1. **One writer, many readers.** Only the builder edits files; research and review go to read-only subagents with fresh context and a self-contained brief, returning findings only. [P] docs/features/subagents; blog/how-lovable-agents-work-together
2. **Append-only run log as the source of truth.** Log every iteration, tool call, approval and revert as an event; render the prompt from the log; make compaction an event; allow forking at iteration boundaries. [P] blog/how-lovable-agents-work-together
3. **Inbox, not interrupts.** Room messages land in the agent's inbox and are picked up at the next iteration boundary; fix runs (Try to fix, security fixes) are queued as separate runs. [P] same; docs/features/projects/chat
4. **Suspend instead of retrying a dead sandbox.** Runs exit "suspended" and resume on any node; durable state lives in git plus the log. [P] blog/how-lovable-agents-work-together
5. **Three permission levels on one agent:** discuss (no writes), plan (writes only `plan.md`), build. Approving a plan switches to build, and the plan is archived with a date. [P] docs/features/chat-mode, plan-mode
6. **Line-anchored search/replace as the default edit,** with whole-file writes only for new files, and edits validated against the file before applying. [U] §9; corroborated by [P] changelog 4 Apr 2025 "multiple edits to the same file"
7. **Deterministic fast path for trivial UI edits.** Stable element IDs injected at build time map a click to its JSX; text and class changes are applied without the LLM. [P] blog/visual-edits; changelog 7 Oct 2026
8. **At most four questions, each with options, defaults preselected.** Skipping means defaults for the asked-for work only, never approval of extra work. [P] docs/features/projects/chat; changelog 15 Sep 2026
9. **Ask about the look only when it is open,** and skip for functional apps, dashboards, or anything with a template; derive spacing and radius from the chosen palette and type. [P] docs/features/design-guidance
10. **Scan every generation against the design tokens** (raw colours, one-off values, re-implemented components) and auto-retry before finishing. [P] docs/features/design-systems
11. **Add-only schema by default,** with every change as a migration file in the repo and types regenerated; destructive changes need an approval that shows the SQL. [P] docs/features/database
12. **Write a small test whenever a rule changes** (price, limit, permission, date, who-can-do-what), keep it, and run the covering tests before saying done; none for copy or styling. [P] docs/features/testing
13. **Verify cheapest-first:** build, then logs, then tests, then direct function calls, then the real browser. Browser-test when asked, when logs cannot explain the bug, or after offering on a big change. [P] docs/features/browser-testing
14. **Sign in to test as the app's only user, or ask which one;** impersonation needs an approval from an admin. [P] same
15. **Cap blind fixes:** after two failed fixes on the same error, switch to diagnosis (list what was tried, form hypotheses, find the root cause) or propose a revert. [P] docs/prompting/prompting-debugging
16. **Detect stuck runs and inject curated fixes.** An LLM judge calibrated on labelled runs triggers a pruned, A/B-tested knowledge base. [P] blog/we-gave-our-agent-a-vent-tool
17. **Give the agent a "report broken tool" call,** limited to one per turn and routed to the team, so it stops retrying broken tools. [P] same
18. **Secrets only through a secure form,** never echoed; a pasted key becomes a named secret automatically; a "Generate" option covers shared webhook secrets; keys never go into frontend env. [P] docs/features/secrets; changelog 26 Jun, 9 Oct 2026
19. **Security scan on publish plus auto-fix of safe classes** (RLS, open policies, vulnerable dependencies), with a per-app security memory the scanner reads and appends to. [P] docs/features/security; changelog 18 May 2026
20. **Reversibility-first capabilities in generated apps:** start with tools that read or are easy to undo; add delete, pay, send, publish or share only on explicit request. [P] changelog 13 Oct 2026

### 5 things to do better than Lovable, given a room
1. **Lessons that persist without a human copying them.** Lovable tells users to paste bug post-mortems into Instructions [P §6]. A persistent room agent should write its own "what broke, what fixed it" entries into app memory after every resolved error loop, and read them before touching that area again.
2. **Team context instead of a 10,000-character box.** Lovable's context is a fixed text field plus `AGENTS.md` [P]. The room already holds the decisions, people, and linked docs. The builder should read the room thread that produced the request, not only a self-contained brief, which Lovable's Chats→project handoff deliberately avoids [P §1.2].
3. **Approvals routed to the right person, asynchronously.** Lovable's approvals are per-user toggles and in-editor cards [P §3.3]. In a room, a breaking migration, a payment product, or an impersonated test login can go to the named owner as a one-tap approval while the agent keeps working on everything else.
4. **Verification the team can watch.** Lovable's browser test runs in a hidden remote browser and is conservative because it is slow and can lose work [P §4]. With a shared browser, the agent records the flow it tested (screens plus console) into the room as proof of done, and a teammate can take over or point at the failing element. That covers Lovable's weak spots: canvas, drag, icon-only buttons, subtle visuals.
5. **Always-on ownership after launch.** Lovable's monitoring is an opt-in daily job that emails the owner [P §4]. A persistent agent can watch visitor errors and failed webhooks continuously, open a draft fix with a test, and post it in the room for approval. "Done" then extends to the app still working a week later.
