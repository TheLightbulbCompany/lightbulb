# Bump OpenClaw upstream 2026.4.23 → 2026.5.7 — Phase 1 of credential-system overhaul

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move Isol8's pinned OpenClaw upstream image from `2026.4.23` to `2026.5.7` (current stable as of 2026-05-09) so we can build the credential-proxy / Connections-UI work (Phases 2 and 3) on top of OpenClaw's native `proxy.proxyUrl` config field (added in 2026.4.27) and the SecretRef hardening that landed in 2026.4.24-2026.5.7.

**Architecture:** This is a base-image bump, not a feature. The work is concentrated in three PRs sequenced by CI/CD: (1) update the Dockerfile + version manifest + version-pinned Python constant, which triggers the extended-image rebuild and ECR push; (2) bump `dev.tag` in `openclaw-version.json` once the new ECR tag exists, which causes CDK to roll the dev backend service onto the new task definition; (3) copy `dev.tag` → `prod.tag` after dev validation. No application logic changes; the risk surface is OpenClaw schema drift and behavioral regressions in the per-user container at boot.

**Tech Stack:** Docker (extended-image multi-stage build), GitHub Actions (`build-openclaw-image.yml`, `deploy.yml`, `e2e-dev.yml`), AWS ECR (immutable tags + SOCI v2 manifests), AWS CDK (TypeScript, `apps/infra/`), pytest (Python backend), pnpm/Playwright (E2E gate).

## Critical preconditions

Read these before starting any task:

1. **Three-PR cutover, NOT one PR.** The CI workflow `build-openclaw-image.yml` (triggered on `Dockerfile` or `openclaw-version.json` changes pushed to main) builds the extended image and pushes to ECR with tag `{upstream}-{short-sha}`. The deployed dev/prod task definitions reference `dev.tag`/`prod.tag` — those fields must be bumped *after* the extended image exists in ECR. Combining all three changes in one PR results in CDK referencing a tag that doesn't exist yet → CFN deploy failure.

2. **ECR tags are immutable.** Per the workflow comment at `build-openclaw-image.yml:54-61`, the SOCI v2 manifest is the only push that claims a tag. Don't try to overwrite a tag in ECR.

3. **Existing user containers do NOT auto-upgrade.** The CDK task definition references the new `dev.tag`/`prod.tag`; ECS services using that task def will roll. But Isol8's *backend* service (FastAPI on Fargate) and the *backend's* OpenClaw task definition pattern are separate from per-user OpenClaw services. Per-user services were created with a task def revision pinned at provision time — they keep running on whatever revision was current then. New provisions and `force_new_deployment` calls pick up the new tag. **This means existing prod users will not see the new OpenClaw until they reprovision.** Document this explicitly; don't surprise users.

4. **Extended-image rebuild can fail in CI but produce silent issues at runtime.** The Dockerfile prebake logic (lines 156-175) walks `/app/dist/extensions` and installs each plugin's `dependencies + optionalDependencies`. If 2026.5.7 reorganized the extensions directory, the prebake silently no-ops and the user pays cold-start cost on first plugin use. We've already been bitten by this (per the comment in `Dockerfile:144-150`). Verify after the build that the prebake found extensions.

5. **Local Docker build is NOT required for this bump.** The README at `apps/infra/openclaw/README.md:16-19` mandates it for engineers without other access to upstream internals. We have an upstream checkout at `~/Desktop/openclaw` (read-only reference per memory `reference_openclaw_source`) that gives us file-level access to the new version's schema, constants, and extensions layout — fetch the new tag there and read directly. CI builds the extended image; the dev rollout is the real smoke test. Skip Task 2's local build unless something in CI surfaces a Dockerfile issue.

6. **E2E gate runs before prod promotion.** `.github/workflows/e2e-dev.yml` runs against dev with the `isol8-e2e-testing@mailsac.com` Clerk account. Per `feedback_no_speculative_event_filtering` and the CLAUDE.md note about the E2E gate, this must be green before PR-3.

7. **No mandatory soak between dev and prod.** PR-3 (prod promote) runs once dev smoke + E2E are green. A blanket "wait 24h" rule slows iteration without buying real safety at our scale; the user has authority to cut PR-3 immediately after E2E passes.

- **No deletion of the stale CODEX_HOME comments** in `ecs_manager.py` and `config.py` (per the earlier conversation finding) — that's a small cleanup belonging in Phase 3 when we touch credentials code anyway, not coupled to the version bump.
