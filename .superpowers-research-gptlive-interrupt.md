## 1. Every client→server event GPT-Live accepts

The reference lists exactly 11 client events (`REF` "Client events", lines 73-5446). LiveKit's `ClientEvent` union mirrors them one for one (`PKG/plugins/openai/realtime/gpt_live_types.py:188-200`).

| Event | What it does |
|---|---|
| `session.start` | First message. Sets model, instructions, history (`input`), audio, delegation and `store`. |
| `session.update` | Changes Responses-delegation settings only. Any other field is rejected (`CONV` "Update a live session"). |
| `session.input_audio.append` | Audio in. Has no acknowledgment. |
| `session.input_audio.mute` / `.unmute` | Mutes or unmutes **input**. Acknowledged with `.muted` / `.unmuted`. |
| `session.instructions.append` | Adds a developer instruction (≤500 tokens). **It can interrupt speech in progress** (see below). |
| `session.thinking.append` | Adds silent context (≤500 tokens). |
| `session.commentary.append` | Adds context to be spoken; the model paraphrases it (≤500 tokens). |
| `response.item.create` | Responses delegation only. |
| `response.create` | Responses delegation only. Starts or continues **backend** work. It is not a voice response. |
| `session.close` | Graceful close. The server answers with `session.closed`. |

**No event cancels, truncates, commits or clears anything.**
- None of these exist: `response.cancel`, `conversation.item.truncate`, `input_audio_buffer.commit`, `input_audio_buffer.clear`, `output_audio_buffer.clear`.
- Nothing tells the model "the user heard up to N ms". `session.output_audio.delta` on the primary WebSocket carries no timing at all (`REF` lines 6901-6935: `start_ms`/`end_ms` are "omitted on the primary WebSocket").
- LiveKit's doc says it outright: "**Server-driven.** No client event creates, cancels, or truncates a response" (`LK` "Overview", bullet 1).

**The one documented lever on in-flight speech is `session.instructions.append`.**
- `CTRL` "Redirect the conversation": "Use `session.instructions.append` for guardrail steering. It can interrupt speech in progress and apply a new instruction." Its example content is "Stop speaking immediately. Do not continue or act on the last request…"
- `CONV` line 294: "An instruction sent during the conversation can interrupt speech in progress."
- `DELEG` "Send the right kind of update": `session.instructions.append` is the event for "direction to stop speaking". Also: "An appended instruction can interrupt the model's current speech or behavior."

Caveats on that lever:
- The acknowledgment arrives "after estimated context injection", not when speech stops (`CTRL`; `CONV` "Understand when context reaches the model").
- It "does not cancel backend work" (`DELEG` line 413).
- Instructions persist "for the rest of the session" (`LK` "Conversation context"). Word them as a one-off event, not as a standing rule.

## 2. What happens server-side when the client simply stops playing

Nothing happens on the server. The model's context keeps the whole reply.
- `CTRL` "Check speech before playback": "**Discarded speech remains in the model's conversation context**, so test how the conversation continues after withheld audio."
- `CTRL` "Control playback when needed": "If your application needs to block model audio, control playback at the client or media relay… corrective instructions cannot retract audio the caller has already heard."
- `LK` "Turn detection and interruption": "When playback stops, the agent's history records only the part that played, but the model's context still holds the whole turn. GPT-Live doesn't support message truncation, so you can't correct it, and the model can refer to something the user never heard."
- `LK` "Overview": "The framework can stop the audio it plays to the user, but the model keeps talking until it stops on its own."

## 3. External barge-in (someone other than the input speaker)

OpenAI does **not** document a multi-speaker or external barge-in flow. Every guide assumes one caller on one input stream.

The documented path for an application-initiated stop (`CTRL` "Redirect the conversation" plus "Control playback when needed") is:
1. Mute or drop the output **locally** and discard queued audio.
2. Send `session.instructions.append` with an application-authored "stop and redirect" instruction.
3. Resume playback by your own recovery policy. "an instruction acknowledgment is not a signal to resume."

**`mute_input` plus feeding new input is not the documented path. It is the wrong tool.**
- `CTRL`: "`session.input_audio.mute` controls the caller's microphone input. **It does not mute model output or cancel delegated work.**"
- `WS` "Configure an ongoing session": "Muting input does not cancel backend work or stop generated speech."
- `CONV` "Control microphone input": "the model can keep generating speech."
- Muting would also stop the model from **hearing** the new speaker. The model's own barge-in depends on hearing the interrupter (`PROMPT` "Interruptions"; template "Interruption policy: Stop speaking when the user interrupts").
- The docs ask for continuous input: "preserve a continuous, ordered stream" (`WS` "Send and receive events"); "Keep input audio running" (`CONV` "Greet before the caller speaks").

## 4. Verdict on the PR's claims

**(a) "The duplex adapter `interrupt()` is a no-op": CORRECT.**
- `PKG/agents/llm/duplex_adapter.py:644-645`: `def interrupt(self) -> None: pass  # barge-in is the model's own, and it cannot be cancelled`.
- `truncate()` is also a no-op (`:647-655`), and so are `commit_audio`/`clear_audio` (`:638-642`).
- The adapter declares `message_truncation=False` (`:269`), so the activity never calls truncate (`agents/voice/agent_activity.py:4545`).
- Context is append-only: `update_chat_ctx` only appends new items, and logs and ignores edits or deletes (`duplex_adapter.py:574-596`).
- What the PR misses: `interrupt()` is the wrong hook to look at. The real lever is `session.instructions.append`, which the plugin exposes as `GPTLiveSession.append_instructions()` (`gpt_live_model.py:1060-1062`). You reach it through `Agent.duplex_session` or `adapter_session.duplex_session` (`duplex_adapter.py:537-540`).

**(b) "`AgentSession.interrupt(force=True)` only clears our playback buffer": ESSENTIALLY CORRECT.**
- `agent_session.py:1634-1651` → `agent_activity.py:1889-1935`. It:
  - cancels preemptive generation,
  - interrupts the current, background and queued `SpeechHandle`s (which stops forwarding and calls `audio_output.clear_buffer()`; `generation.py:664,738`),
  - calls `self._rt_session.interrupt()`, which is the no-op from (a) (`agent_activity.py:1916-1917`).
- Effect: playback stops and the local chat history records only the played part, marked `interrupted` (`agent_activity.py:4542-4565`). Nothing reaches OpenAI.
- Two additions the PR does not mention:
  - **Nothing stops the next burst from playing.** If the model keeps talking and then pauses for longer than the gate's silence window (`_MIN_SILENCE_DURATION = 0.8` s, `gpt_live_model.py:50,362-363`), a new burst opens. That emits `generation_created(user_initiated=False)` (`duplex_adapter.py:420-441`), and the activity schedules and **plays** it as a fresh speech (`agent_activity.py:2273-2300`). So a cut reply can "resume" a moment later.
  - Per `LK`, the session's own barge-in needs an explicit VAD. That VAD only hears the RoomIO-linked participant, so it **cannot** detect a non-pinned participant. External barge-in detection has to come from us.

**(c) "GPT-Live has no response.cancel / commit / clear, only mute/unmute": HALF RIGHT.**
- Right: there is no cancel, commit, clear or truncate (§1).
- Wrong: mute/unmute is not the only control, and it is not an interruption control at all (§3).
- The documented interrupt-and-redirect control is **`session.instructions.append`** (`CTRL`, `CONV:294`, `DELEG`).
- `session.thinking.append`, `session.commentary.append` and `session.close` also exist (`REF`). So does `response.create`, but it drives backend work, not voice.

**(d) "So the model may keep generating the reply after we cut it": CORRECT, with two qualifications.**
- Confirmed by `LK` ("the model keeps talking until it stops on its own") and `CTRL` (discarded speech stays in context). Mute "does not mute model output" (`CTRL`).
- Qualification 1: the model **does** stop on its own when it hears an interruption, per the prompt's interruption policy (`PROMPT` "Interruptions"). It will only hear the new speaker if their audio reaches the session, i.e. after `set_participant`.
- Qualification 2: an instruction like "Stop speaking immediately…" is OpenAI's documented way to make it yield sooner.
- Even when it stops, the model keeps the whole reply in context, so tell it what was actually heard (§5, step 3).

## 5. Recommended sequence for Lightbulb (client delegation, LiveKit 1.8.3)

Each step is marked **documented** or **inference**.

0. **At startup, put an interruption policy in the voice instructions** *(documented, `PROMPT` template)*. Instructions cannot change after start (`gpt_live_model.py:1107-1113`). Example: "Interruption policy: stop speaking as soon as anyone in the room interrupts, and listen to them. More than one person may speak; you will be told who is speaking."

1. **Detect the external barge-in yourself** *(inference)*. Run VAD or energy detection on the non-pinned participants' tracks. RoomIO only forwards the linked participant (`room_io.py:312-336`), so neither the AgentSession VAD nor GPT-Live hears anyone else.

2. **Cut local audio:** `session.interrupt(force=True)` *(documented by `CTRL`: "control playback at the client… discard locally queued audio"; mechanism in §4b)*.
   - Stops playback, clears the RoomIO output buffer, and leaves the played part (`interrupted=True`) as the last assistant message in `agent.chat_ctx`.
   - Then **hold output closed** until the new speaker's input transcript starts. Otherwise a resumed burst plays (§4b). *(inference; `CTRL` says resume "according to your application's recovery policy… an instruction acknowledgment is not a signal to resume")*
   - Simplest hold: `session.output.set_audio_enabled(False)` now and `True` when step 5 fires. Alternative: interrupt any `speech_created` with `user_initiated=False` during the hold window.

3. **Make the model drop the cut reply and acknowledge it** *(documented: `CTRL` "Redirect the conversation")*:
   ```python
   ds = agent.duplex_session  # GPTLiveSession
   ds.append_instructions(
       "Stop speaking now; do not continue your last reply. "
       f"{new_name} just interrupted you. Listen to {new_name} and answer them."
   )                                   # -> session.instructions.append, delegation_id=null
   ds.append_thinking(
       f"Your last reply was cut off; the room only heard: \"{played_text}\"."
   )                                   # -> session.thinking.append (silent context)
   ```
   - `played_text` is the `text_content` of the last assistant `ChatMessage` with `interrupted=True` in `agent.chat_ctx`.
   - This is the only way to "truncate". It is a correction the model reads, not an edit to its context.
   - Keep each append under 500 tokens.
   - Keep the instruction application-authored. Never paste participant speech into `append_instructions` (`CTRL`).
   - Optional: confirm via `session.instructions.appended` matched on `client_event_id` (`CONV`). The plugin only logs acks (`gpt_live_model.py:730-743`); listen on `ds.on("openai_server_event_received", ...)` if you need them.

4. **Switch the listener:** `session.room_io.set_participant(new_identity)` *(documented in LiveKit turns doc, "Listen to a specific participant", https://docs.livekit.io/agents/build/turns)*.
   - **Do not** call `mute_input()`. Keep input continuous so the model hears the new speaker (§3).
   - Skip the doc's `clear_user_turn()` and `commit_user_turn()`: GPT-Live has no input buffer to clear or commit (`duplex_adapter.py:638-642`).

5. **Let the model respond to the new speaker** *(documented: the model owns turn-taking, `WS` "GPT-Live manages when to listen and speak"; `LK` "Turn detection and interruption")*.
   - Re-enable output when the first `input_audio_transcription_completed` (or `user_input_transcribed`) from the new speaker arrives.
   - No `generate_reply` is needed. If one is used, it is only an `append_commentary` ask and can be refused within 10 s (`LK` "Initiating speech"; `duplex_adapter.py:610-636`).

6. **In-flight client delegations** *(documented, `DELEG` "Keep updates accurate and useful")*: "Interrupting the spoken conversation leaves backend work running."
   - Decide in app state whether the delegation for the cut reply is still wanted.
   - If not, cancel it in your backend and drop its late result.
   - If you abandon it, you can tell the model with `append_thinking("Abandoned; do not report it.", delegation_id=d.id)`. *(inference about the wording; the event and the id use are documented)*

## 6. Multiple speakers in one GPT-Live session

- No speaker attribution exists anywhere in the protocol.
  - There is one mono input stream (`session.input_audio.append`).
  - `session.input_transcript.delta` has no speaker or participant field (`REF` lines 6940-6987).
  - The docs only ever say "the caller"/"the user".
- The full-duplex material is about **caller and assistant** overlapping, not several callers (`CONV` "Display captions").
- Relevant prompting templates (`PROMPT`):
  - "Do not treat a cough, music, or **nearby conversation** as a new request." This suggests the model is tuned to ignore other voices unless told otherwise.
  - "Selected requests only: Respond when the user asks about [topic] or addresses you directly."
- **Inference:** to make several participants first-class, either
  - announce speaker changes with `append_thinking("Now speaking: Priya")`, or
  - mix the room's audio into the one input, with a prompt that says several people share it.

  Neither is documented by OpenAI. Test both. The LiveKit plugin merges all input into one `user` role (`gpt_live_model.py:766-816`), so your transcript-to-participant mapping has to come from RoomIO's linked identity at the time.
