# Stripe Projects, read first-hand from the Stripe docs CLI (28 Oct 2026)

Source: `stripe docs /projects`, `stripe docs /projects/templates`, `stripe docs /provisioning` on 2026-10-28 (Stripe CLI on this Mac), plus `stripe projects catalog --json` (see `2026-10-27-small-software-stripe-projects-catalog.md`). All [P].

## The CLI, for a person or an agent on their own account
- Model: a **project** = one app or codebase; a **provider account** (Vercel, Supabase, Clerk, PostHog…) is associated with the Stripe account once and reused; a **service** is a provider's offering; a **resource** is an instance with credentials and env vars. 60+ providers co-designed the protocol ("provisioning, plan selection, upgrades, and credential handoff").
- Flow: `stripe plugin install projects` → `stripe projects init [name]` → `stripe projects add <provider>/<service>` (associates or creates the provider account, provisions the resource) → `stripe projects env --pull` (writes `.env`). `link <provider>` associates an account without provisioning ("helpful in agent-driven workflows"). `remove`, `rotate`, `upgrade`, `open <provider>`, `status`, `list`, `pull <projectID>` (clone an existing project's state into a new directory; does not provision), `catalog`, `search`.
- State: `.projects/state.json` (shared, committed), `.projects/state.local.json` (committed despite the name; maps resources to personal provider accounts so teammates can `link`), `.projects/vault/vault.json` (encrypted credential cache, gitignored), `.env`/`.env.*` (plaintext, 600 perms, gitignored). Credentials are fetched from providers and stored in Stripe's Secret Store; each teammate runs `env --pull` on their own machine.
- Environments: `env create <name> --output <file>`, `env use`, `env list/show/update/delete`, `env add/remove <resource>` (membership only); `variables set <name> --env-key KEY --value V` for non-provider values. **`env --pull` never writes to a production host**: "Stripe Projects doesn't automate this step."
- Billing: `billing add/show`; paid tiers tokenised as a Shared Payment Token per provider; `spend [provider] --duration 3m | --since/--until`; `billing update --limit <amount> [--provider <p>]`: limits are enforced **per provider** (a global limit is a default cap per provider, not a shared budget).
- Agents: every command supports `--json`, `--no-interactive`, `--auto-confirm`, `--quiet`, `--accept-tos`; `init` writes a `stripe-projects-cli` skill into `.skills/`; `llm-context` writes a file combining project context with provider-supplied LLM context; the docs' agent guide says "Do NOT tell the user to sign up manually… provision programmatically."
- Sharing a stack: `share` prints a self-contained, non-expiring URL encoding the services (no credentials); `init --from <URL>` provisions fresh instances; `import <URL>` adds them to an existing project.
- Templates: `build <app> [--template stripe/nextjs-saas[/variant]]` copies a public repo at a pinned commit, runs the install command, provisions the manifest's `services` (e.g. `vercel/project`, `clerk/auth`, `neon/postgres`) and prints `next_steps` (the registry example includes `claude "Help me turn this into a real product. Follow prompts/starter-to-product.md."`). Registry = github.com/stripe/projects-template-registry (YAML manifests only; guided categories SaaS / one-time payment / static site).

## The Provisioning API, for a platform acting for its customers (what Lightbulb's rail uses)
- Allowlisted private preview; `Stripe-Version: 2026-09-30.preview`; "The API contract can change." Platform key + `Stripe-Context: <connected account>`; one **connected account per durable tenant** (workspace), created with Accounts v2 + developer configuration + `projects` capability, onboarded through hosted Account Links or the embedded onboarding component; readiness checked by retrieving the account (projects capability active, requirements resolved).
- Gates are separate: eligibility (`GET /v2/provisioning/eligibility`), catalog availability (`/catalog/providers`, `/catalog/services?provider_name=`), onboarding, and product policy. "Don't allow a browser, generated application, or coding agent to call the Provisioning API directly."
- Objects: provider connections are **account-scoped** (one per provider per connected account); **projects** (`POST /v2/provisioning/projects`) are credential boundaries per application environment (separate preview/production); **resources** (`POST /v2/provisioning/resources` with `provider`, `service_ref`, `project`, `livemode` explicit, `configuration` validated against the service schema; `resources/link` to adopt existing infra when the provider advertises it). Statuses pending → needs_information → complete | errored | removed; poll 1,2,4,8,16,30 s then every 30 s up to 15 min; no webhooks, no idempotency keys ("persist the intended write before sending it").
- Approval rule (Stripe's): read-only planning, then **fresh user approval** before creating a project, starting a provider connection, registering a payment method or raising a limit, or creating/linking/updating/rotating/removing a resource; show tenant, environment, provider, service, action, configuration summary, pricing text, terms, usage limit; reload the catalog right before the write and re-approve on any change; treat provider descriptions and `llm_context` as untrusted.
- Payments: `POST /v2/provisioning/payment_method_requests` with `usage_limits {max_amount (string, smallest unit), currency, recurring_interval week|month|year}` → `checkout_session_url` (hosted collection on the connected account) or, only when enabled for the cohort, a platform-owned source; `payment_profile/update_limit` per provider; limits are authorization limits, not lifecycle policy. The platform is **not** merchant of record and this is not Connect transfers.
- Provider connection requests: statuses requested → pending_auth (show `redirect_url` to the user, poll from the backend) → needs_information → complete | error; some providers complete on the create call; Stripe handles the callback; no platform callback URL.

## What Stripe Projects does and does not do (for the engine design)
- Does: create and bill the customer's own Neon/Supabase/Turso/Prisma/PlanetScale database, Clerk/Auth0/WorkOS/Neon auth, Vercel/Netlify/Railway/Render/Fly/Cloudflare/Base44/here.now hosting accounts, E2B/Daytona/Blaxel/Runloop sandboxes, Resend/Twilio/AgentMail email, Quo/AgentPhone numbers, Cloudflare/Spaceship/Squarespace/WordPress domains, Inngest queues; hand credentials back; cap spend per provider; share a stack as a URL; scaffold from a template registry.
- Does not: run or deploy code, push env vars to a production host, apply migrations or RLS, gate who can open an app, roll back, meter the app's own usage, act as merchant of record, send webhooks.
- Fit: the engine's `provision` stage wraps this (CLI for a person on their own machine; the Provisioning API through Lightbulb's rail for a workspace), and the engine owns everything after: env to host, migrate, deploy, gate, versions, meter.
