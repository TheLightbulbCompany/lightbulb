## 1. How Hermes boots in a container — command, entrypoint, privilege model

- **Image:** `debian:13.4` (Dockerfile:3), runs as PID 1 under `tini -g` (Dockerfile:13-14,119). Entrypoint is `/opt/hermes/docker/entrypoint.sh`. The published default `command` is `["gateway", "run"]` (docker-compose.yml:56), i.e. the **messaging gateway daemon** (`python -m gateway.run` per spec §0/§7), NOT a chat/RPC server.
- **Root-then-drop, not non-root.** The container *must start as root* so the entrypoint can `usermod -u $HERMES_UID hermes` / `groupmod` then `exec gosu hermes` (entrypoint.sh:12-59; Dockerfile comment :106-107). This is a hard mismatch with the kind of locked-down ECS task that runs a single fixed UID: Isol8's OpenClaw EFS access point pins **POSIX UID/GID 1000** and OpenClaw "runs as node" / `chown 1000` (CLAUDE.md "Config Patching Notes"; `workspace.py` chowns to 1000). Hermes's internal user is **UID 10000** (Dockerfile:21), and its volume-ownership logic is driven by the `HERMES_UID`/`HERMES_GID` *remap* dance (entrypoint.sh:13-46) designed for bind mounts on a developer laptop, not an EFS access point that *forces* a UID server-side. The spec (§7 "EFS layout … chown 1000") silently assumes UID 1000; the image defaults to 10000 and the chown path is gated on `HERMES_UID != 10000` (entrypoint.sh:30). **Open question the spec does not resolve:** does `chown -R hermes:hermes` (entrypoint.sh:40) even succeed against an EFS access point that overrides ownership? On OpenClaw, Isol8 deliberately works *with* the access-point UID instead of chowning at boot.

## 2. The transport mismatch is the load-bearing risk — and it is a *config-activated, off-by-default* surface

- Isol8's whole control plane is **inbound**: the per-user container binds an OpenClaw WS server (`gateway --port 18789 --bind lan`, container-stack.ts:540), exposes `portMappings: containerPort 18789` (container-stack.ts:610) and a `/healthz` healthcheck (container-stack.ts:627); the backend *dials in* via `discover_ip` + a persistent WS pool (ecs_manager.py:37 `GATEWAY_PORT = 18789`, :1210 `discover_ip`).
- Hermes `gateway run` is the **opposite shape**: an *outbound* bot client that connects out to Telegram/Discord/Slack/Teams/etc. It has **no inbound RPC/WS control port**. The only inbound HTTP surface usable by Isol8 is the **OpenAI-compatible `api_server` adapter** (`gateway/platforms/api_server.py`, `DEFAULT_PORT = 8642` :58). The spec correctly picks this (§3) — but two boot-time facts make it more fragile than the spec implies:
  - **api_server is a `platforms:` adapter that is OFF in the shipped config.** The example config leaves the entire `platforms:` block commented out (cli-config.yaml.example:675-699); the adapter is only constructed if `Platform.API_SERVER` is enabled (`config.platforms[Platform.API_SERVER].enabled = True`, config.py:1480) and is materialized in `gateway run` via `APIServerAdapter(config)` (run.py:5521-5527). So the Hermes adapter MUST write an enabled `platforms.api_server` stanza into `config.yaml` at provision time — the default container would boot with NO Isol8-reachable port at all. The spec's §7 "Bind api_server on the container IP … with `API_SERVER_KEY` set" is necessary but the *enablement* step (writing `platforms.api_server.enabled: true` to EFS config.yaml) is not called out as a boot prerequisite.
  - **The adapter `return False`s (does not start) on a bad bind.** `is_network_accessible(host) and not api_key` → refuse to start (api_server.py:3433-3441). `DEFAULT_HOST = "127.0.0.1"` (:57) and host comes from `API_SERVER_HOST` env (:642). So the task def MUST set `API_SERVER_HOST=0.0.0.0` (or the task IP) AND `API_SERVER_KEY` (≥8 chars, non-placeholder, :3444-3451) or the only inbound surface silently never binds. Spec §3 covers the key; it does not flag that a missing/loopback `API_SERVER_HOST` is a silent no-port failure mode.

## 3. First-boot behavior writes to HERMES_HOME at runtime — heavier and more EFS-hostile than OpenClaw

- `HERMES_HOME=/opt/data` (Dockerfile:116), `VOLUME [/opt/data]` (:118). Spec §7 maps the EFS access point to `~/.hermes`/`/opt/data`. `get_hermes_home()` reads `HERMES_HOME` env first (hermes_constants.py:30-32), so pointing it at the EFS dir works.
- **But first boot does real work against that filesystem, every time:** entrypoint.sh:71 `mkdir -p $HERMES_HOME/{cron,sessions,logs,hooks,memories,skills,skins,plans,workspace,home}`; copies `.env`/`config.yaml`/`SOUL.md` from the image if absent (:74-86); seeds `auth.json` from `HERMES_AUTH_JSON_BOOTSTRAP` env once (:97-100 — note: this is a *clean, supported* non-interactive OAuth seed path the spec under-uses); and runs **`python3 tools/skills_sync.py`** on every boot (:103-105) which syncs bundled skills into `$HERMES_HOME/skills` — i.e. a many-small-file write storm onto EFS at each cold start. This is the exact class of EFS small-file pain Isol8 already hit with OpenClaw npx extract (`project_mcp_npx_efs_extract_stall`). The spec does not budget for skills_sync's per-boot EFS cost.
- **NFS/EFS lock incompatibility — direct contradiction of an Isol8 invariant.** The Hermes gateway takes its singleton lock with **`fcntl.flock()`** (gateway/status.py:329, :416) on `gateway.lock`, and that lock file lives at **`HERMES_HOME/gateway.lock`** (status.py:54-55) — i.e. on EFS under the spec's layout. Isol8's CLAUDE.md is explicit: *"`fcntl.lockf()` for file locking (not `flock()` — incompatible with NFS)"*; `config_patcher.py` uses `lockf` for exactly this reason. `flock` over NFS is unreliable/no-op depending on server config. The spec's §7 WAL-SQLite single-writer note covers `state.db` corruption but **misses that the gateway's own boot lock is `flock`-on-EFS**, which can either spuriously fail or (worse) silently not exclude — undermining the single-writer guarantee the spec relies on. (Token-scoped locks at status.py:63-69 are deliberately *machine-local* under `XDG_STATE_HOME`/`HERMES_GATEWAY_LOCK_DIR`, so those are fine; the `gateway.lock` one is not.)

## 4. Image weight & build cost — a per-provision task-def churn concern

- The image bakes a **full Node + npm toolchain and Playwright Chromium**: `apt-get install … nodejs npm … ` (Dockerfile:17), then `npm install` + `npx playwright install --with-deps chromium` + two more `npm install`s (web/, ui-tui/) (:52-55), plus `npm run build` for web + ui-tui (:88-89), plus a `uv sync --extra all --extra messaging` Python resolve (:81). Chromium alone is ~hundreds of MB; `--with-deps` pulls system libs. This is a **much larger image than OpenClaw's extended image** and a slower cold pull onto a fresh Fargate task. Spec §7 ("Build a pinned Hermes image → new ECR repo") treats this as a routine mirror of `openclaw-version.json`, but does not size the image-pull-latency hit against the cold-start animation budget, nor note that ECS task-def is **re-registered every provision** (spec §7 cites `_register_task_definition` ecs_manager.py:376) so a heavier image is pulled on every re-provision/runtime-switch.
- `.dockerignore` excludes **`*.md`** (.dockerignore:24) and `data/`, `hermes-config/`, `runtime/` (:27-33). The `*.md` exclusion already bit Isol8 once on OpenClaw (`feedback_backend_dockerignore_strips_md` — Atlas SKILL.md/IDENTITY.md). Hermes works around it for its own README via `touch ./README.md` (Dockerfile:80) but ships `SOUL.md` from `docker/SOUL.md` which IS copied (it lives under `docker/`, and `COPY . .` at :85 brings it in despite `*.md` because… it does not — **`*.md` in .dockerignore would strip `docker/SOUL.md` from the build context**, yet entrypoint.sh:84-85 copies `$INSTALL_DIR/docker/SOUL.md`). This is a latent contradiction worth a live `docker build` check: if `*.md` strips `docker/SOUL.md`, the SOUL seed at entrypoint.sh:85 fails and Hermes boots without its default soul. The spec's identity-seeding design (§5, persona via `ephemeral_system_prompt`) sidesteps SOUL.md, so it may not matter for Friday/Atlas — but any reliance on baked `.md` files needs the same `!*.md` negation Isol8 learned to add.

## 5. Resource assumptions vs Isol8's 0.5 vCPU / 1 GB box

- Isol8's per-user box is fixed at **512 CPU / 2048 MiB** in this worktree (ecs_manager.py:43-44 `PER_USER_CPU="512"`, `PER_USER_MEMORY_MIB="2048"`) — note this is 2 GB, not the 1 GB stated in CLAUDE.md's billing section (CLAUDE.md is stale here; the code says 2048). Either way it is a small box, and Isol8 already documents OpenClaw CPU-starvation crash-loops on it (`project_openclaw_mcp_connect_storm_crashloop`: 7 MCP servers serially connecting saturate the 0.5 vCPU).
- Hermes's README pitches "run it on a $5 VPS" (README.md:15) — no published RAM/CPU floor in the repo's README (the resource grep returned only marketing copy, README.md:15). But the image carries a Chromium + Node runtime alongside the Python agent, and `tini` exists specifically because Hermes *spawns many subprocesses* — "MCP stdio subprocesses, git, bun, etc." that "accumulate when hermes runs as PID 1" (Dockerfile:13-14). A subprocess-heavy agent on a 0.5 vCPU box is the same starvation profile that already bites OpenClaw. **The spec never re-validates the box size for Hermes** — it inherits OpenClaw's sizing by assumption (§7 says nothing about CPU/MEM). This is an unverified load-bearing assumption: Hermes may need a bigger box, which changes the $50 flat-fee unit economics.

## 6. Writable HERMES_HOME on a network filesystem — yes, expected, but with runtime mutation the spec downplays

- Hermes is **designed to treat HERMES_HOME as a persistent writable volume** (Dockerfile:118 `VOLUME`, entrypoint bootstrap :71-105) and the `.venv` is deliberately kept **hermes-writable so `lazy_deps.py` can `uv pip install` optional platform packages at first use** (Dockerfile:99-105 comment; entrypoint :44 re-chowns `.venv` on UID remap). That `.venv` is in the **image** (`/opt/hermes/.venv`), not on EFS — good — but it means a runtime `uv pip install` (e.g. a messaging adapter or a `hermes skills install github/...`) mutates the *image layer's* venv, which is **lost on task restart** and re-downloaded over the network each cold start (same ephemeral-cache cold-download trap as `project_openclaw_mcp_cache_crashloop`). The spec's §6 acknowledges remote skill installs need outbound HTTPS (Q7) and §"open questions" #4 flags ECS egress policy as undecided, but does **not** flag that Hermes's lazy-install model re-pays the install cost on every restart unless that cache is redirected to EFS — a known Isol8 footgun the spec should pre-empt, not discover in prod.

---

### Net: the spec's deploy/boot story is directionally right but rests on 4 unverified boot-time assumptions
1. **api_server is off-by-default + silently no-binds** without `platforms.api_server.enabled:true` in config.yaml AND non-loopback `API_SERVER_HOST` AND `API_SERVER_KEY` — three EFS/env preconditions, only one of which (the key) the spec calls out.
2. **`gateway.lock` uses `flock` on EFS** — directly violates Isol8's documented NFS lock rule and undercuts the single-writer corruption guard the spec leans on.
3. **UID 10000 vs EFS access-point UID 1000** + a root→gosu chown-the-volume boot dance built for bind mounts, never validated against an EFS access point that pins ownership.
4. **Heavier image (Chromium+Node) + per-boot skills_sync write storm + lazy `uv pip install`** re-paid on every cold start — none budgeted against the small box or the cold-start animation, and the box size itself (512/2048) is inherited from OpenClaw without re-validation for a subprocess-spawning Python agent.
