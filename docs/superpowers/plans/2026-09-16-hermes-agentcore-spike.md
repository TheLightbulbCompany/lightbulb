## Design: an in-process bridge, no gateway, no EFS
Taken from AWS's own reference (`aws-samples/sample-host-hermesagent-on-amazon-bedrock-agentcore`, `bridge/contract.py`): the microVM runs a small Python contract server that imports Hermes and holds one `AIAgent` per agent profile; each `/invocations` runs `agent.run_conversation(user_message, system_message, conversation_history)` and returns `final_response` (plus tool/status events via the `*_callback` hooks). No `hermes gateway`, no API server, no multiplex flag, no platform plugin: our backend is the only caller, and it already owns rooms, membership, the run ledger and the reply path. Fewer moving parts than the Runs-API design in the spec §4.2; that design stays as the fallback if in-process turns lack something (approval callbacks, MCP lifecycle).

State: no EFS mount. `HERMES_HOME=/opt/data` on the ephemeral disk, one profile dir per agent (`/opt/data/profiles/<agentId>/`: `config.yaml`, `SOUL.md`, `memories/`, `skills/`, `state.db`), restored from S3 at the first invocation and saved after each turn and on SIGTERM using the sample's `workspace_sync.py` pattern (SQLite copied with the backup API, `*.db-wal` excluded). Same path on every host, so the OpenClaw "workspace path alias" class of bug cannot occur. Chat history comes from the room (`conversation_history`), so the profile's `state.db` is a cache plus memory.

Two platform facts (measured by the OpenClaw session on 2026-09-16) the bridge must respect: ~10 warm-pool instances per runtime version run the container CMD before any session exists, so nothing session-bound starts at container start; and a session's mounts attach at session assignment, so anything state-dependent runs on the first `/invocations`. The bridge therefore: `/ping` → `HealthyBusy` until the first invocation completes its restore; first `/invocations` → S3 restore, construct agents, run the turn.

## Facts fixed before starting (2026-09-16)
- Official image `nousresearch/hermes-agent:latest` = Hermes v0.21.3 (2026.9.14), multi-arch, **0.95 GB compressed on arm64 (46% of the 2 GB cap)**, 2.69 GB uncompressed, runs as **root**, `HERMES_HOME=/opt/data`, entrypoint `/opt/hermes/docker/entrypoint-dispatch.sh`, Python 3.13.5, Node 26 present, `uv` present; no `aws`, `gh`, `sqlite3`, `litestream`, `chromium`. AgentCore runs the container as uid 1000: the spike image sets `USER 1000` with `/opt/data` owned by 1000.
- Bundled Anthropic SDK 0.87.0: `AnthropicBedrock` has **no `api_key` (bearer) parameter**; current releases (1.x, latest 1.6.0) have `api_key` defaulting to `AWS_BEARER_TOKEN_BEDROCK` and `base_url` defaulting to `ANTHROPIC_BEDROCK_BASE_URL`, and a bearer skips SigV4. Hermes's `build_anthropic_bedrock_client` passes no static AWS keys, so the SDK defaults apply once the package is bumped. Bump in the spike image to the smallest release that has the parameter; if 1.x breaks Hermes, fallback = a ~30-line `sitecustomize` subclass setting the bearer in `_prepare_request`.
- The gate (`apps/infra/lambda/bedrock-gate/core.mjs`) accepts only `/model/{urlEncodedId}/{converse|converse-stream|invoke|invoke-with-response-stream}` with `Authorization: Bearer`; the SDK URL-encodes an ARN with `safe=':'`; the gate `decodeURIComponent`s. Same as OpenClaw today.
- `AIAgent(model=, provider=, base_url=, api_key=, session_id=, platform=, user_id=, chat_id=, enabled_toolsets=, quiet_mode=, tool_start_callback=, tool_complete_callback=, stream_delta_callback=, status_callback=, …)`; `run_conversation(...)` → `{completed, api_calls, messages, final_response}`. Multiple instances coexist in one process (the sample and Hermes's own subagents do it). Per-profile `HERMES_HOME` is context-local (`hermes_constants.get_hermes_home()`; the override used by multiplexing) — read `hermes_constants.py` inside the image on day 1 to get the exact call.
- The AWS sample's "warm-up agent" (a boto3 Converse stand-in answering during the 10–30 s Python load) is NOT adopted: a room reply from a lesser stand-in is wrong for us; the backend's 10 s ingress retry absorbs the load instead. Measure whether that is enough.

## Day 1 — image, bridge, gate (criteria 1 and 4)
1. `apps/infra/hermes/Dockerfile.spike`: `FROM nousresearch/hermes-agent:latest`; `uv pip install` the bumped `anthropic` + `boto3`; `COPY bridge/` (contract server + workspace sync, ported from the sample, ~300 lines Python); `USER 1000`; `CMD ["python3", "/opt/bridge/contract.py"]`. Measure compressed size (≤ 1 GB).
2. Push to ECR `lightbulb/hermes-agent-arm64:spike-1`.
3. Bridge `/invocations` envelope: `{action: "turn", agentId, message, conversationHistory, sessionKey, runId}` → `final_response`, plus `{action: "diagnostic", cmd}` (same escape hatch as the OpenClaw contract server) and `{action: "status"}`. Env on the runtime: `ANTHROPIC_BEDROCK_BASE_URL=<gate>`, `AWS_BEARER_TOKEN_BEDROCK=<owner bearer>`, `AWS_REGION`, `HERMES_MODEL=<owner sonnet AIP ARN>`, `HERMES_PROVIDER=bedrock`, `S3_BUCKET`, `S3_PREFIX`, `HERMES_HEADLESS=1`.
4. Create the runtime by hand (boto3, admin profile, same request shape as `build_runtime_request` minus `filesystemConfigurations`; role = the owner's Bedrock role). Invoke `status`, then one `turn`. **Pass 4** = a reply and a settled row in the gate ledger for the owner. **Measure 1** = cold and warm turn latency from the invoke.

## Day 2 — profiles, our messaging plane, state (criteria 2, 3, 5)
5. Six profiles (the org's Paperclip roster ids) as six `AIAgent`s with per-profile `HERMES_HOME`; two `turn`s in flight at once; RSS from the diagnostic hatch. **Pass 2** = < 1 GB resident, both turns complete.
6. A room turn: in the worktree, a `runtime_host=hermes` branch in `openclaw_work._post` that submits the room message as a `turn` with the room's recent messages as `conversationHistory`, writes `run.started/ended` to the ledger, and posts the reply through the canonical writer. Reuse `runtime_transport` (envelope) and `ensure_runtime` (Hermes image/env, no EFS). **Pass 3** = the CEO agent's reply appears in `#general` of the spike org.
7. State: `StopRuntimeSession`, re-invoke, confirm each profile's memories and skills survive via S3; record restore time and object count; the warm pool shows zero agent constructions. **Pass 5** = survives, restore ≤ 5 s. If S3 restore is too slow, and only then, compare an EFS access point (expect Hermes `state.db` on NFS to misbehave, as OpenClaw's did). If S3 passes, the cutover deletion list is: litestream, the local-volume-in-EFS layout, `boot-layout.sh`'s symlink spine and fence, the `.isol8-guard`/`.isol8-protocol` lock protocol, chokidar polling.

## Day 3 — migration and verdict (criterion 6)

9. ChatGPT OAuth into Hermes's Codex provider for one profile (from an existing dev OAuth row).
10. Verdict against the six criteria written into the spec (§7 outcome table) with measured numbers, and the recommended next plan.
