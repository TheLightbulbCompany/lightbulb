# Where a room-scoped internal tool can run, and how "only this room can open it" is enforced

Researched 2026-10-27. Tags: [P] primary doc, [S] secondary, [U] could not verify. All URLs fetched 2026-10-27 unless noted.

## The one idea that matters

Every platform below hosts code fine. Almost none of them can answer "is this visitor a member of room X in *our* product?" The access check must come from one of three places:

1. **A gateway we control in front of the tool** (Cloudflare dispatch Worker, or our own proxy) that verifies a JWT our messaging product minted with a `room_id` claim. Works everywhere, costs nothing per user, no per-tool config.
2. **The host's own allow-list** (Val Town restricted access, Base44 private apps, Vercel Authentication, Netlify team login). Each makes the visitor log in to *that vendor's* account, so we would have to mirror room membership into the vendor and users get a second login.
3. **An OIDC bridge** (Cloudflare Access generic OIDC, Vercel Passport, Supabase third-party auth) where our product is the identity provider. Clean, but Passport is Enterprise-only and Access is $7/user past 50.

Option 1 is the only one that scales to hundreds of tiny tools without per-tool money or per-user money.

## 1. Stripe Projects

**What it is.** A Stripe CLI plugin that "provisions and manages third-party services (such as hosting, databases, auth, AI, and observability)" and "Run one command to create your accounts, sync credentials to your `.env`, and handle billing through Stripe." It is in developer preview. [P] https://docs.stripe.com/projects

**What it can provision.** 68 providers. Databases: Neon, Supabase, PlanetScale, Prisma, Turso, ClickHouse, Chroma. Cache/Redis: Upstash ("Cache, search, database"), Cloudflare, Railway, Laravel Cloud. Hosting: Vercel, Netlify, Cloudflare, Fly.io, Railway, Render, Base 44, Here.now, Wix, WordPress.com, Laravel Cloud. Auth: Clerk, Auth0, WorkOS, Neon, Privy. Email: Resend, AgentMail. Queue: Inngest. [P] https://docs.stripe.com/projects#available-providers. Live catalog: https://projects.dev/providers. "Free to use. You pay providers directly at their standard rates." Services are "created in provider accounts you own, so you can leave and keep your resources." [P] https://projects.dev

**What it does not do.** It hosts nothing, deploys no code, and has no notion of who may open a tool. `env --pull` "doesn't write environment variables to your production host." [P] https://docs.stripe.com/projects#production-env

**Billing flow.** Payment method added once to the Stripe account; on a paid tier "Stripe tokenizes your payment credentials into a Shared Payment Token and grants the provider a payment credential… The provider charges using that token." Spend limits are per provider, not a shared budget. [P] same page.

**Platform provisioning on behalf of customers (this is what Lightbulb would use).** "Integrate the Provisioning API into your platform… provision Resources, retrieve credentials, and manage paid services for authorized tenants." Allowlisted private preview; email provisioning-preview@stripe.com. Headers: `Authorization: Bearer {platform key}`, `Stripe-Context: {connected account id}`, `Stripe-Version: 2026-09-30.preview`. One connected account per durable tenant (workspace), created with `POST /v2/core/accounts` with `configuration.developer.capabilities.projects.requested=true`, then hosted or embedded onboarding. Endpoints: `GET /v2/provisioning/eligibility`, `GET /v2/provisioning/catalog/providers|services`, `POST /v2/provisioning/payment_method_requests` (returns `checkout_session_url`; platform-owned payment source only if Stripe enables it), `POST /v2/provisioning/projects`, `POST /v2/provisioning/provider_connection_requests`, `POST /v2/provisioning/resources`, `POST /v2/provisioning/resources/{id}/reveal_access_configuration` (returns e.g. `DATABASE_URL`), `/rotate_credentials`, `/remove`, `/unlink`. Constraints: not merchant of record, no Connect transfers model; no webhooks or idempotency keys (poll up to 15 min); credentials revealed one resource at a time; `livemode` defaults to `true` if omitted. [P] https://docs.stripe.com/projects/platform-integration

**Read.** Gives each workspace its own provider accounts on its own card and hands the agent credentials; not where the tool runs, not what gates the door.

## 2. Cloudflare Workers for Platforms (and Pages)

**Hosts.** "Build a multi-tenant platform that runs untrusted code in secure, isolated sandboxes." Each customer's code is its own Worker in a dispatch namespace; a dynamic dispatch Worker we write "Executes authentication, rate limiting, or request validation before customer code runs," then `env.DISPATCHER.get("customer-a").fetch(request)`. User Workers get KV, D1, R2 bindings. "No per-account script limits apply… Unlimited number of Workers." Docs recommend one namespace for all customers (plus `staging`). [P] https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/how-workers-for-platforms-works/

**Provisioning API.** `PUT /accounts/{account_id}/workers/dispatch/namespaces/{dispatch_namespace}/scripts/{script_name}`, multipart with a `metadata` JSON part (bindings array: `d1`, `kv_namespace`, `r2_bucket`, `compatibility_date`, `assets`) plus the script part; needs `Workers Scripts Write`. [P] https://developers.cloudflare.com/api/resources/workers_for_platforms/subresources/dispatch/subresources/namespaces/subresources/scripts/methods/update/. Per-customer CPU/subrequest limits and tags. [P] https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/

**Pricing.** $25/mo; 20M requests included then $0.30/M; 60M CPU-ms included then $0.02/M; 1,000 scripts included then $0.02/script; 30 s CPU per invocation. So 500 tools ≈ $25/mo total. [P] https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/platform/pricing/. "Requests for static assets on Workers are free." [P] https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/

**Access restriction.** Two options. (i) Our dispatch Worker verifies a Lightbulb-signed JWT/cookie with `room_id` before dispatching; nothing to configure per tool. (ii) Cloudflare Access: policies on Emails, Emails ending in, IdP group, or "OIDC Claim… with a generic OIDC identity provider"; "Access is deny by default." [P] https://developers.cloudflare.com/cloudflare-one/policies/access/. The app validates `Cf-Access-Jwt-Assertion` against `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, matching `kid` and checking `aud` (the app's AUD tag) and `iss`. [P] https://developers.cloudflare.com/cloudflare-one/identity/authorization-cookie/validating-json/. Access is free "up to 50 users", then $7/user/mo pay-as-you-go. [P] https://www.cloudflare.com/plans/sase-zero-trust.md

**Pages.** "Enable access policy" restricts *preview* deployments to our Cloudflare account; "this will only protect your preview deployments"; the `*.pages.dev` and custom domains need a separate Access application. [P] https://developers.cloudflare.com/pages/configuration/preview-deployments/. Workers "has a distinctly broader set of features" than Pages. [P] migration guide above. Use Workers static assets, not Pages.

**Unusually good.** Flat $25 for the whole fleet; per-tool D1 database and secrets as bindings; our own gateway in the request path. **Bad.** D1 and cron for user Workers inside a namespace: pricing page mentions "15 minutes of CPU per Cron Trigger" but I did not confirm Cron Triggers attach to namespace user Workers [U]; safe pattern is a platform-owned scheduled Worker that calls the tool through the dispatcher.

## 3. Vercel

**Deploy.** `POST /v13/deployments` "for the authenticated team or user. For non-git deployments, upload files first via the file upload API, then reference them here by SHA — or inline small files directly in the request body"; `teamId` query param. [P] https://vercel.com/docs/rest-api/reference/endpoints/deployments/create-a-new-deployment

**Access restriction.** Methods: Vercel Authentication (all plans), Passport (Enterprise), Password Protection ("Pro for $20 per month per protected project"), Trusted IPs (Enterprise). "Standard Protection" protects everything except production domains; "All Deployments" also protects production. [P] https://vercel.com/docs/deployment-protection. Vercel Authentication admits "Logged in team members with at least a viewer role… project members… members of an access group… Vercel users who have been granted access… Anyone who has been given a Shareable Link"; set via API `ssoProtection.deploymentType`. [P] https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication. Viewer seats are free and unlimited on Pro. [P] https://vercel.com/docs/plans/pro-plan. Passport: "protect deployments with your own identity provider… Microsoft Entra ID, Okta, or another OpenID Connect compatible provider"; app reads identity from a Passport token; "Passport is available as an Enterprise feature. Contact your Vercel account team for pricing." [P] https://vercel.com/docs/passport

**Pricing implication.** Pro $20/mo platform fee with 1 deploying seat and $20 usage credit; extra deploying seats $20/mo. [P] Pro plan page. Password Protection at $20/project kills the per-tool economics; Vercel Authentication forces every room member to have a Vercel account on our team (free viewer seat, but a second login and a seat we administer).

**Vercel Sandbox.** Firecracker microVMs for "untrusted or agent-generated code"; "Run development servers… with live previews"; idle 1 vCPU/2 GB ≈ $31.45 per 30 days, stopped $0; persistent sandboxes resume state. [P] https://vercel.com/docs/vercel-sandbox. It is a build/run box for the agent, not a place to leave a tool running for a month.

## 4. Supabase

**Model.** Free: "2 active projects. Projects are paused after 1 week of inactivity." Pro $25/mo with $10 compute credit covering one Micro; each additional project (Micro) $10/mo ($0.01344/h, billed hourly, not covered by Spend Cap); Branching $0.01344/branch/h; third-party MAU $0.00325 beyond 100,000. [P] https://supabase.com/pricing and https://supabase.com/docs/guides/platform/manage-your-usage/compute. The multi-tenancy guide URL returned 404 [U] https://supabase.com/docs/guides/platform/multi-tenancy. Conclusion from pricing alone: one project per tool is a $10/mo floor per tool; a shared project per workspace (or per Lightbulb) with RLS on `room_id` is the only shape that fits hundreds of tools.

**Provisioning.** Management API with scoped personal access tokens or "OAuth2… for third-party apps acting on behalf of Supabase users"; `POST /v1/projects` is org-scoped; 120 req/min. [P] https://supabase.com/docs/reference/api/introduction. MCP server exposes `create_project`, `pause_project`, `execute_sql`, `apply_migration`, `deploy_edge_function`, branching (paid plan), with cost confirmation before `create_project`. [P] https://supabase.com/docs/guides/getting-started/mcp. Supabase is also a Stripe Projects provider (database, auth, storage). [P] Stripe provider table.

**Access restriction.** Third-party auth: Clerk, Firebase, Auth0, Cognito, WorkOS, and "Custom OIDC provider… any other provider that supports OpenID Connect"; "the API will trust JWTs issued by the provider similar to how it trusts JWTs issued by Supabase Auth"; asymmetric only, `kid` required, key rotation picked up within 30 min. [P] https://supabase.com/docs/guides/auth/third-party/overview. So if Lightbulb publishes an OIDC discovery doc and JWKS, RLS policies can read `room_id` from Lightbulb's token directly. The web page still has to be served from somewhere else.

## 5. Val Town

**Hosts.** JavaScript/TypeScript vals triggered by HTTP, cron, or email, with SQLite, blob storage, env vars; HTTP triggers give a file "a live URL, like solitaire-game.val.run", plus custom domains. [P] https://docs.val.town/ and https://docs.val.town/vals/http/. REST API and TypeScript SDK manage vals, blob, SQLite. [P] https://docs.val.town/reference/api

**Pricing/limits.** Free $0: unlimited public vals, 100,000 runs/day, 1 min wall-clock, 15-min cron, 3-day logs. Pro $21/mo: 1,000,000 runs/day, 10 min wall-clock, 1-min cron, 2,000 private vals, 10 custom domains. Business from $167/mo: 5M runs/day, unlimited custom domains, team accounts. Enterprise: no limits. [P] https://www.val.town/pricing. Limits page returned 404 [U].

**Access restriction (the strongest built-in of any host here).** Code access (public/unlisted/private) is separate from app access; for private vals "HTTP endpoints are reachable by anyone with the URL, unless you restrict app access." Restricted app access: Business account, org-owned vals; allow Val Town users/orgs by handle, email invitations (expire 7 days, 20 outstanding per val, invitee gets the val only), email domains (up to 10 per val); "Visitors are sent to Val Town to sign in, then returned to the val. Sessions last 30 days." Bypass tokens `vtba_…` in `X-Val-Town-Access`, up to 10 per val, for webhooks. Applies to custom domains. Controlling access is "fully supported by our MCP server and plugin." Downgrade → restricted vals return HTTP 402. [P] https://docs.val.town/reference/permissions and https://docs.val.town/reference/access

**Read.** Per-val SQLite + cron + email allow-list covers all three sizes; cost is a Val Town login for every visitor, invites mirrored from room membership, and one org we own.

## Fit by tool size

**(a) Single-file page with snapshot data.**
Fits: Cloudflare WfP (upload one Worker with static assets; free asset requests), Val Town (HTTP val returning HTML), Netlify/Vercel static. Door: on Cloudflare, the dispatch Worker checks a Lightbulb-signed cookie (`room_id`, `exp`) issued when the user clicks the tool link in the room; no vendor login. On Val Town, restricted app access with the room members' emails invited (Business plan, Val Town login). Vercel Authentication and Netlify team login both require the visitor to be a member of *our* vendor team: wrong shape. Identity plug-in: Lightbulb mints the token; the gateway verifies it.

**(b) Page that reads live QuickBooks/CRM at view time.**
The credential must sit server-side. Two patterns. Thin: the page calls Lightbulb's own API with the room token and Lightbulb's agent-held credential does the QuickBooks call (credentials never leave the place they already live). Thick: a user Worker on WfP with the token as a per-Worker secret binding, or a Val Town val with env vars, calling QuickBooks directly. Door: same as (a). Supabase is not needed. Vercel works technically (function + env) but the door problem remains unless Passport (Enterprise). Identity plug-in: gateway JWT; if thin, the room token is also the credential-broker key.

**(c) Multi-user tool with its own database and a scheduled job.**
Fits: Cloudflare WfP with a D1 binding per tool plus a platform-owned scheduled Worker that invokes the tool (cron on namespace user Workers unverified [U]); Val Town with per-val SQLite and a cron val (1-min interval on Pro); Fly Machine ($2.19/mo + auto-stop) or Railway (sleeping) for anything that needs a real process. Database alternative: one Supabase project per workspace with RLS reading `room_id` from Lightbulb's OIDC token via third-party auth ($10/mo per workspace, not per tool). Door: gateway JWT for the page; for direct-to-Supabase reads, Supabase itself verifies Lightbulb's JWT. Identity plug-in: Lightbulb publishes OIDC discovery + JWKS once; Cloudflare Access (generic OIDC), Supabase (custom OIDC), and Vercel Passport (Enterprise) can all consume it; Val Town, Base44, Floot cannot and need email mirroring.

**Billing plug-in.** Where a workspace should own and pay for the substrate (Supabase project, Fly app, Base44 account, Neon DB), Stripe Projects' Provisioning API does it on the workspace's connected account with `2026-09-30.preview`; the credential comes back via `reveal_access_configuration` and goes into the WfP secret binding. Where the substrate is ours (the WfP namespace at $25/mo), there is nothing to provision per customer.
