# DeepSeek's "Super-agent" design vs Lightbulb's runtime, from the code

Source: DeepSeek Harness, "Exploring Super-agent Design: Towards a More Autonomous Agent System" (x.com/deepseekharness, 1 Nov 2026) and `deepseek-ai/dsh-superagent-prototype/docs/002-authorization.md`. Lightbulb facts from the monorepo (`apps/infra/hermes/bridge/*.py`, `apps/backend/core/services/*.py`) and the CLI engine (`src/workers.rs`, `src/mail.rs`), read on 2 Nov 2026 by a read-only code mapper. Line numbers are from that read. Correction of an earlier claim in chat: having the same primitives (hosted agent, workers, daemons, rooms) is not the same architecture; this is what the code does.

| Their module | What they describe | Lightbulb today (evidence) | Verdict |
|---|---|---|---|
| 1. Two-level Router / Worker | One long-lived Router session talks to humans and dispatches; isolated Worker sessions do tasks and never talk to humans | One long-lived Hermes session per agent per room (`turn.py:2611-2635`), never ended; it talks to people AND does the work; side sessions only when a room lock is held ≥30 s (`:2977`). Jev picks a responder for ambient messages (`jev.py`, `openclaw_work.py:558-645`) but is a backend call, not a session. Network workers are isolated per task (`workers.rs:130-160`, own worktree `:265-306`) but start only on an `assign`, and a hosted agent cannot send one: the plugin's network tool offers send/receipt/directory only (`plugins/lightbulb/__init__.py:420`), `kind` defaults to `message` (`ipc.rs:1925`). | Partial. The room session is both router and worker. |
| 2. Event triggers, two-stage filtering | Deterministic fast path per source/allowlist, then a model decides | For chat: `select_dispatch_targets` (`messaging.py:3964-4003`: observe/active listen modes, mentions, DMs, feed threads), then Jev (0.7 confidence, 3 s), then caps (`AGENT_REPLY_CAP = 2`, `FOLLOW_UP_CAP_PER_HOUR = 3`), then `[SILENT]`. No per-source allowlist for room events; no general event bus for webhooks or integrations. | In substance for chat; lacking for other sources. |
| 3. Subscription / pass-through | Follow-ups in a Thread go straight to the owning Worker without the Router | A human follow-up in the same DM/thread is steered into that agent's live run (`openclaw_work.py:768-866`, `/runs/{id}/steer`); once the run ends, follow-ups go back through dispatch and Jev. No lasting thread-to-worker subscription. | Partial. |
| 4. Context organization (Inline & Spill, Chain of Recall) | Summaries and ids inline, full content on demand, an object graph to follow hop by hop | 50 recent room messages per ingress, trimmed to 1 MiB (`openclaw_work.py:41-44, 282`); observed rows keyed by messageId; memory recall before each turn (`memory/agentcore/__init__.py:21-66`); run/message/thread ids threaded through tools. No object graph with on-demand expansion. | Partial. |
| 5. Speculative execution | Act in the background before being asked; deliver only if useful | Fixed timers only: specialist heartbeat daily, CEO every 8/12/24 h with board hygiene (`ceo-heartbeat.md:128-236`); agents cannot schedule (`hermes_profiles.py:366-373`); routines created disabled. No "silently reproduce and fix". | Lacking. |
| 6. Full-duplex async loop | Tool calls start/stop; the session accepts input while tools run | One thread per turn, serialized per conversation, max 4 per runtime (`turn.py:2966, 3819`); a steer lands only between tool batches (`:943-974`, "can only inject a live steer into a tool result" `:181`); abort is immediate. | Half-duplex. |
| 7. Multi-channel norms | Short in IM, dense in GitHub | `CHAT_STYLE` for rooms/DMs (`turn.py:2101-2146`), feed and voice and SMS rules in skills and profiles; nothing for GitHub; prompt text, not code. | Present for chat; none for GitHub. |
| 8. Compute / state / environment split, BYOM | Stateless cloud loop, state in a DB, lightweight daemons on people's machines | Hermes microVM per workspace (15-min idle, 8-h max, `agentcore_runtime.py:120`); session state in SQLite on the container disk synced to S3 per turn (`sync.py:635-700`); DynamoDB for runs and messages; the laptop daemon runs workers and `app.send`; a hosted agent can run a command on a paired Mac with native approval (`desktop.py:41-139`, `desktop_execution.py:541-581`). | Compute and BYOM in substance; stateless compute and DB-held state lacking. |
| 9. Watchdog | An outside control loop that detects stuck or drifting runs and corrects them | The run-ledger sweeper closes runs that never started or stopped heartbeating (`run_ledger.py`, 300 s / 90 s / 20 s), reports only, never re-runs; worker deadlines (`workers.rs:1074`); Paperclip "Watchdog review" issues. No drift or loop judgment on a live run. | Liveness only. |
| 10. Their open problems: A2A across permission boundaries; credentials the agent never sees | Unsolved in their design | Phase 1 of the A2A authority work is the boundary piece. Credentials: agents DO see raw tokens: profile `.env` passed to the shell except one gate bearer (`turn.py:2738-2756`), the hook token in the process env and the turn-context file (`bridge/__init__.py:73`, `turn.py:4174`), gh credential files materialized into the profile; protection is transcript redaction. | Boundary: ours to build. Credentials: lacking. |

## What this says

- Their five modules: none is fully present in Lightbulb. Event filtering for chat is closest; speculative execution is absent; the loop is half-duplex; the Router/Worker split does not exist for hosted agents.
- Three gaps are small and high-value, and two of them are governance-adjacent: (1) a hosted agent cannot `assign` work to a network worker, so the Worker layer exists but Friday cannot use it; (2) agents hold raw credentials in their shell and files, which is their open problem 8.4 and the thing the enterprise reviewer will ask about first; (3) the watchdog never judges drift.
- The large bets (a Router layer, a full-duplex loop, an object graph, speculative work) are runtime architecture owned by the Hermes and Workers work, not the governance scope.
