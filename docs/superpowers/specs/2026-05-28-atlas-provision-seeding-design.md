# Atlas Provision Seeding — Design

- **Status:** Approved (design); implementation plan pending
- **Date:** 2026-05-28
- **Related:** PR #744 (removes the stale `agents/` dumps, keeps `atlas`), closed PR #740 (`feat/agent-skills-folders` — source of Atlas's skill bundles)

## Problem

Every provisioned container seeds two agents in Paperclip: **Friday** (CEO) and
**Atlas** (the in-house agent-recruiter). Friday gets a fully working workspace
because `core/services/friday_identity.py::pre_stage_friday_identity` writes her
identity files to EFS before the container boots. **Atlas gets nothing** — it is
created only as a bare Paperclip agent record (`paperclip_provisioning.py:370-390`)
and its rich, actively-developed automation (`agents/atlas/`: 6 markdown, 8
`.lobster` workflows, 18 `.js` tools) has **no path into a provisioned container**.

The `agents/` directory at the repo root is otherwise a static, unreferenced dump
(removed in #744). Atlas is the one live exception. This change relocates Atlas's
source into the backend and seeds it at provision time, mirroring Friday — then
completes the `agents/` removal.

## Validated facts (evidence grounding the design)

These were confirmed against upstream OpenClaw (`~/Desktop/openclaw`), the Paperclip
clone (`paperclip/`), and the isol8 backend:

1. **Paperclip is pure transport.** The `openclaw_gateway` adapter forwards only
   `{id, name, companyId}` + a generic wake prompt — no persona/skills/config. So
   container-side seeding (EFS files keyed by the Paperclip UUID) is **sufficient**;
   nothing must be configured Paperclip-side. (`paperclip/.../openclaw-gateway/.../execute.ts`)
2. **UUID mapping is sound.** `agent["id"]` is the Paperclip UUID and is the OpenClaw
   workspace key — identical to Friday. (`config.py:437-441`, `friday_identity.py:686`)
3. **EFS → container mapping.** Files written to `workspaces/{uuid}/…` on EFS appear
   at `/home/node/.openclaw/workspaces/{uuid}/…` in the container. (`container-stack.ts:461-465`)
4. **`name`, not `role`, identifies Atlas.** Atlas is seeded with `role="general"`,
   which marketplace hires also use — not unique. Friday uses the unique
   `role="ceo"`. (`constants.ts:44-58`)
5. **Atlas's `openclaw.json` is never deployed.** Friday's mechanism writes only
   *workspace files*; the container's `openclaw.json` is generated by the backend.
   We mirror that — so Atlas's invalid `archetype: "meta-agent-builder"` field
   (rejected by upstream's `.strict()` agent schema, `zod-schema.agent-runtime.ts:1006`)
   never reaches a container. The problem is sidestepped, not patched.
6. **`fast-io` and 6 sibling skills are load-bearing and absent from `main`.** Atlas's
   `.lobster` pipelines call `openclaw.invoke --tool fast-io` constantly. OpenClaw
   resolves skills from on-disk dirs (incl. `<workspace>/skills`); a referenced skill
   with no files on disk is **silently dropped**. The 7 needed bundles
   (`fast-io, taskr, n8n-workflow, capability-evolver, skill-vetter,
   sona-security-audit, agentgate`) shipped in closed PR #740, not on `main`.
   (`gog`, `summarize`, `slack` are NOT seeded: they ship upstream as discoverable
   `SKILL.md` bundles in OpenClaw's bundled skills dir — verified `skills/gog/SKILL.md`,
   `skills/slack/SKILL.md`, `skills/summarize/SKILL.md` exist upstream — so the loader
   finds them without us copying them. Seeding our own copies would shadow upstream's
   and risk drift. So exactly 7 bundles are recovered, not 10.)

## Scope

**In scope**
- Relocate Atlas's source files into the backend as a bundled resource dir.
- Recover Atlas's 7 skill bundles from PR #740's branch into that resource dir.
- A `pre_stage_atlas` seeder mirroring `pre_stage_friday_identity`.
- Wire it into `write_user_configs`.
- Tests mirroring the Friday seeding test.
- Delete `agents/atlas/` and `agents/atlas-v0/`, completing the `agents/` removal.

**Out of scope (owned by the user)**
- Enabling `lobster` / `llm-task` plugins and a `cron` block in the generated
  `openclaw.json`. The user will handle this in the config builder separately.

**Out of scope (deferred → Aden)**
- The `ISOL8_AGENTS_DIR` / agents-root data-plane: Atlas's *build-other-agents*
  tools write to `~/.openclaw/agents/{name}/` rather than isol8's Paperclip-UUID
  workspace convention. This only affects Atlas's recruiter **output** integration,
  not Atlas running its own pipelines/chat. Requires a product/architecture decision
  about how Atlas-built agents become real Paperclip-paired agents.

## Design

### 1. Source location
Atlas's files move from `agents/atlas/` to a bundled backend resource dir:

```
apps/backend/core/services/atlas_seed/
  __init__.py            # pre_stage_atlas + helpers
  files/                 # the seeded workspace tree (read at runtime)
    IDENTITY.md SOUL.md USER.md BOOTSTRAP.md AGENTS.md TOOLS.md
    *.lobster            # 8 workflow files
    *.js                 # 18 tool scripts
    skills/              # 7 recovered bundles (fast-io, taskr, …) each = SKILL.md + _meta.json (+ assets)
```

Friday inlines her 5 markdown files as Python string templates; Atlas's 38+ files
(incl. executable `.js`) cannot be inlined, so they live as packaged files read at
runtime. The dir ships in the backend Docker image, so it is present at provision.

**Docker-context caveat (load-bearing).** Friday is immune to `.dockerignore`
because her content is inline Python; Atlas's content is *files*, and
`apps/backend/.dockerignore` excludes `*.md` (with only `!README.md` negated) plus
`.DS_Store`/`__pycache__`/`*.log`. The backend image is a CDK `DockerImageAsset`
(`service-stack.ts:120`) that honors `.dockerignore` and does `COPY . .`, so without
a fix **every `.md` — all 6 identity files and every `SKILL.md` — is stripped from
the image** and Atlas seeds an empty-ish workspace in prod. The implementation MUST
add a negation re-including the resource dir (`!core/services/atlas_seed/files/**`,
placed after `*.md` since `.dockerignore` is last-match-wins) and assert an
`IDENTITY.md` survives the build context.

### 2. What ships vs. what doesn't
- **Ship:** the 6 markdown, 8 `.lobster`, 18 `.js`, and the 7 skill bundles.
- **Do not ship:** `agents/atlas/openclaw.json` (never deployed — see fact #5) and
  `tests/` (runtime doesn't need them).

### 3. The seeder — `pre_stage_atlas(owner_id, paperclip_agents, workspace)`
A near-copy of `pre_stage_friday_identity`:

1. Resolve Atlas: `next(a for a in paperclip_agents if a.get("name") == "Atlas")`.
   If absent, emit a skip metric + log and return (defer to next provision). Matching
   by name is intentional (role is not unique); a user-renamed Atlas or a name
   collision is skipped — acceptable for a best-effort seed and documented inline.
2. `atlas_uuid = agent["id"]`.
3. Write `workspaces/{atlas_uuid}/.openclaw/workspace-state.json` with
   `setupCompletedAt` first, so OpenClaw's boot reconcile doesn't delete
   `BOOTSTRAP.md`. NOTE the semantics differ from Friday: Friday's BOOTSTRAP is a
   non-actionable greeting guide we want to *survive*; Atlas's `BOOTSTRAP.md` is a
   prescriptive one-time setup checklist ("runs on first activation, then deletes
   itself") that initializes `fast-io` state. The trick is still correct (it stops
   *premature* deletion at boot, before Atlas's first activation runs it), but the
   reason is "let Atlas run its setup," not "preserve a greeting." See the
   fast-io-init risk below.
4. Walk `atlas_seed/files/` and write each file to
   `workspaces/{atlas_uuid}/<relpath>` via `workspace.write_file_if_missing`
   (idempotent — preserves Atlas's evolved workspace across reprovisions).
5. Best-effort throughout: per-file try/except, success/skip/error metrics, **never
   raises** — mirrors Friday so an Atlas failure cannot block container provision.

### 4. Wiring
Call `pre_stage_atlas` in `ecs_manager.write_user_configs` immediately after
`pre_stage_friday_identity` (~`ecs_manager.py:1847`), inside the same best-effort
try/except posture, passing the already-fetched `paperclip_agents`.

### 5. Tests
Mirror `tests/unit/containers/test_write_user_configs_seeds_friday.py`:
- Files land under `workspaces/{atlas_uuid}/` with expected relpaths.
- `write_file_if_missing` semantics (existing files not clobbered on reprovision).
- Name-matching: Atlas found by `name`, skipped when absent.
- Best-effort: an EFS write error logs + returns, never raises.

### 6. Complete the `agents/` removal
PR #744 already deletes the static dirs. Once Atlas's source lives in the backend,
this change also deletes `agents/atlas/` and `agents/atlas-v0/` (the frozen,
superseded predecessor), finishing the folder removal.

## Accepted decisions
- Resource dir: `apps/backend/core/services/atlas_seed/files/`.
- Recover the 7 skill bundles from PR #740's branch (`feat/agent-skills-folders`).
- Delete `atlas-v0`.
- **Packaged files, NOT inline Python templates (unlike Friday).** Friday inlines
  because her 5 markdown files are *templated per-owner*; that rationale does not
  apply to Atlas. Atlas is 38+ files of executable `.js`/`.lobster` + skill directory
  trees with no per-owner customization — inlining would mean stringifying code
  (escaping bugs, breaks the lint/test workflow on actively-developed files, and can't
  represent skill dir trees that OpenClaw discovers by scanning for `SKILL.md`). The
  `*.md` `.dockerignore` exclusion that this exposes is handled with a `!`-negation +
  a build-context assertion (see §1), which is a one-line fix vs. a permanent
  maintainability tax.

## Risks / open items
- **Name-match fragility** (above) — accepted, documented.
- **Skill-bundle provenance:** the 7 bundles must be copied verbatim from #740's
  branch; confirm each has a valid `SKILL.md` so OpenClaw's loader discovers it.
- **Config dependency:** Atlas's pipelines need `lobster`/`llm-task` enabled (+ cron
  for triggers). The user owns this in the config builder; the seeded files are inert
  until that lands. Not a blocker for this change, but Atlas won't *function* until
  both are present.
- **Deferred agents-root integration** remains open (Aden).
- **`.dockerignore` strips `*.md`** (see the Docker-context caveat in §1). Without a
  `!`-negation re-including the resource dir, Atlas's markdown silently never ships.
  This is a build-context risk Friday never had (her content is inline Python). The
  plan must add the negation and a build-context presence assertion.
- **BOOTSTRAP / fast-io init is load-bearing (missing-risk, now noted):** Atlas's
  `.lobster` pipelines depend on `fast-io` state that its `BOOTSTRAP.md` initializes
  on first activation. That init only happens once Atlas is actually woken AND the
  out-of-scope config (lobster/llm-task/fast-io) is enabled. So a "seeded +
  config-enabled" Atlas may still no-op until its first activation completes the
  bootstrap. Not a blocker for *seeding*, but it gates real function.
- **Cross-PR functional gate:** merging this ships an Atlas whose automation surface
  is inert until the separate config PR (plugins/cron) also lands. Do NOT announce
  Atlas as functional until both this seeder PR and the config PR are merged. Sequence
  or link them.
