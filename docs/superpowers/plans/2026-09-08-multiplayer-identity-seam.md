## Decision

**Controller qualification, 2026-09-08:** the shared-token/trusted-proxy conflict is verified, but the node-relay credential inference below is incomplete. `node_connection.py:236` forwards the client's signed connect verbatim; its stored `gateway_token` constructor argument is not used to rewrite that handshake. Frozen9.3 `auth-context.ts:239-350` has independent bootstrap/device-token paths subject to ingress/pairing/role rules. Actual client credentials, existing reconnect, new enrollment and service-device scopes are being traced before selecting any custom bridge. Do not treat the report's remote-token example as proof that every node path needs one.

Qualifying 9.3 can preserve today's personal-chat product, but does not deliver native multiplayer. The first product seam is an authenticated human gateway connection plus a full session reference. Keep owner-service operations separate. Build one explicitly company-readable room after human identity, machine authentication, and legacy-private-history gates pass. Do not turn off current member filters or fan out the owner-admin stream to make rooms appear to work.

## Where organization-member identity collapses today

The Lambda authorizer verifies Clerk and returns `userId`, `orgId`, and `authKind` (L/apps/infra/lambda/websocket-authorizer/index.py:367–410). The backend stores the frontend connection under its member but derives `owner_id = x_org_id or x_user_id` (L/apps/backend/routers/websocket_chat.py:598–624). Personal chat constructs `agent:<agent>:<member>[:<uuid>]`, then sends `chat.send` via `pool.send_rpc(user_id=owner_id, ...)` (same file:82, 2698–2710). Generic permitted RPCs follow the same owner pool (same file:2223).

The pool connects to the owner's container IP, authenticates with the owner token and signed backend device, and requests tool/approval capabilities (L/apps/backend/core/gateway/connection_pool.py:806, 957). That device grants `operator.admin`, `operator.read`, `operator.write` (L/apps/backend/core/crypto/operator_device.py:85). The pool is keyed by owner, not human; L/apps/backend/core/gateway/connection_pool.py:2891, 3201. Thus upstream authority is collapsed even though Lightbulb retains the member separately for routing and billing. Depending on upstream presence/client classification it can be owner-attributed or unprofiled; neither represents distinct humans. U/src/gateway/server/ws-connection/connect-session.ts:197; U/src/gateway/gateway-owner-profile.ts:4.

Native admin is explicitly exempt from sharing restrictions and event filtering (U/src/gateway/session-sharing-policy.ts:165; U/src/gateway/session-sharing.ts:493). This is why current backend key guards, default-deny RPC methods and event demux are authorization, not cosmetic filtering. A cosmetic `sender` field would not repair the boundary: public `chat.send` is a closed schema with no sender override, and the recorder derives sender from the authenticated client (U/packages/gateway-protocol/src/schema/logs-chat.ts:245; U/src/gateway/server-methods/chat-user-turn-recorder.ts:51). Internal synthetic sender attribution exists, but is not a browser author API.

Keep backend authority over verified membership and tenant routing, current request admission/entitlements/spend, method and parameter permissions, device ownership and selection, privileged maintenance, credential handling, public publication admission, and notification audience. Keep OpenClaw authoritative for native profile attribution, session/transcript state, participation policy and per-recipient session access. Paperclip remains the durable task/run ownership system. Do not copy its task history into a second transcript database.

## Native auth compatibility: what source proves

1. **Token and trusted-proxy are mutually exclusive.** Startup throws if `gateway.auth.token`/resolved environment token remains configured with trusted-proxy (U/src/gateway/auth.ts:188–202; matching tests U/src/gateway/auth.test.ts:1603). Lightbulb currently generates token mode and a token (L/apps/backend/core/containers/config.py:1694–1704).
2. **Trusted-proxy identity needs a trusted network source and attributable forwarding.** It validates the socket peer, rejects loopback unless `allowLoopback: true`, checks configured required headers and `allowUsers`, then returns the header identity (U/src/gateway/auth.ts:211–262). Successful identity also requires ingress attribution to classify it as trusted-proxy (same file:491). Do not restore a broad VPC trust range or forward arbitrary browser identity/scope headers. Current config deliberately trusts only loopback because the remote backend is presently a token client, not an identity proxy (L/apps/backend/core/containers/config.py:1740–1759).
3. **The native service escape hatch is local, not VPC-wide.** On failed proxy auth, password works only when `localDirect && auth.password && connectAuth.password` (U/src/gateway/auth.ts:504). Local-direct means loopback socket and no forwarded request headers (U/src/gateway/net.ts:79). A separate backend ECS task cannot switch to a password and retain its current remote path. Existing one-shot/pool signed-connect accepts a `token` parameter and sends `auth.token` (L/apps/backend/core/gateway/operator_rpc.py:124, 220); both Paperclip and node proxies pass `container.gateway_token` to a remote-IP upstream (L/apps/backend/core/services/operator_proxy.py:225; L/apps/backend/core/services/node_proxy.py:168). Human proxy auto-approval explicitly excludes node roles (U/docs/gateway/trusted-proxy-auth.md:206).
4. **Generic proxy users currently become email aliases.** `connect-user-profile.ts:28` calls `ensureProfileForEmail(authenticatedUserId)`; `user-profiles.ts:88, 246` trims/lowercases it and durably resolves/inserts an alias. Use an issuer-qualified immutable encoding compatible with this normalization, not mutable email or case-sensitive raw Clerk subject. Profile/display renames must not change identity. A concrete prototype candidate is `clerk-<sha256(UTF8(JSON.stringify([verifiedIssuer, verifiedSubject])))>@identity.lightbulb.invalid`; that is a proposed alias convention, not a claim of official upstream OIDC support. Keep the original verified tuple mapped for provenance. Test cross-issuer and case-only subject distinctions.
5. **Scope headers narrow; they do not create authority.** Device grants and configured identity grants combine, then `x-openclaw-scopes` caps the result; empty means no scopes (U/src/gateway/server/ws-connection/connect-admission.ts:110; U/src/gateway/server/ws-connection/connect-session.ts:231). Prototype with distinct paired human operator devices and explicit read/write/approvals/questions grants/caps, never the backend admin device. Configure an appropriate human role and prove profile-resolution failures reject admission; configured-role profile failure handling is explicit at connect-session.ts:220.

The legacy comments saying trusted-proxy universally blocks loopback are incomplete for 9.3: an explicit loopback-proxy opt-in and local password path exist. Neither proves compatibility with Lightbulb's remote machine paths. Control UI remains disabled in generated config (L/apps/backend/core/containers/config.py:1760); a prototype must exercise the intended backend gateway-client path under that setting, not rely on enabling an upstream UI or public admin ingress.

## Smallest concrete prototype before rooms — proposed, not executed

Use one isolated dev gateway with synthetic data and the frozen candidate, a test proxy/backend on a distinct network peer, two human identities A/B from one synthetic organization, and a foreign-owner identity C. Keep Control UI/general public ingress disabled. No room UI is needed.

**First prove native boundaries:** pre-pair two distinct non-admin operator devices, assert only server-authored proxy headers, configure exact proxy source/required headers and no shared token, establish A/B through the actual intended gateway-client mode, then create/send/read an authorized synthetic session and reconnect. Assert durable A/B profile IDs in canonical user-turn history and session creator metadata, not only hello/display names. Use two simultaneous clients for A with different subscriptions to check whether per-member pooling is sufficient; presence is keyed by connection specifically to avoid two tabs overwriting viewing state (U/src/gateway/server/ws-connection/connect-session.ts:180). Default to `(owner, verified member, frontend client)` for the pilot unless the test proves safe aggregation.

**Then prove coexistence with machine work:** from direct loopback, test signed internal operator admission using native password; from the backend network peer, demonstrate expected rejection of the same password path. Replay the actual pool health + one-shot operator path, Paperclip operator handshake and node relay/pairing/refresh against the candidate. The unchanged remote-token versions should be expected to fail under pure trusted-proxy. This establishes the concrete gap before choosing a bridge.

**If the remote paths cannot use an existing supported native mechanism, evaluate one constrained bridge:** a private, authenticated backend-to-gateway service hop terminating locally and producing native password/operator or node handshakes, separated from the human proxy route. Preserve signed-device and role binding; never reinterpret a human frame as service authority, and do not assume a transparent token-to-password rewrite preserves signatures. An equivalently narrow fork service-auth path is an alternative only with a written trust contract and the same negative tests. This assessment does not select or implement either bridge. A design requiring broader public/admin reachability fails the prototype. Record actual candidate handshake traces with secrets removed and a service-compatibility matrix before declaring the fork multiplayer-ready.

## Smallest viable shared-room slice after the gates pass

Add one founder company-room entry pointing to one native canonical session; Lightbulb stores its route/title and Paperclip links, not a second editable membership list. Keep existing personal-key grammar and filters for legacy clients; add an explicit backend-authorized room target instead of overloading the private UUID field. The backend derives allowed owner/session and routes through the human connection. Native sharing controls participation; Clerk organization membership is the outer audience limit.

Extend shared live/history contracts with a full session reference (owner route, canonical key and native session ID), native profile author, creator, current assignee, run ID, optional parent lineage and advertised capabilities. Keep typed admission and idempotency for sends/steers/stops. Bind method parameter names to tagged schemas: sharing methods use `sessionKey` (U/packages/gateway-protocol/src/schema/sessions-sharing.ts:28), while `sessions.assignOwner` uses `key` (U/packages/gateway-protocol/src/schema/sessions.ts:539). Start with canonical history recovery on reconnect and only authorized native subscriptions. Owner-service telemetry may continue for billing, but its privileged stream is not a room event bus.

Update `panelRegistry` and ChatPanel to persist session-aware identity, then use the same reference in chat hooks, caches, URLs, deep links, web/Tauri and Expo. One room with two humans must survive reload and reconnect before adding a broad room browser. Render correct author, explicit company audience, allowed participant controls, typing/viewing presence and mentions; gate unsupported older clients.

Bind the room to one deliberately authorized device initially. The current send path patches session `execNode` (L/apps/backend/routers/websocket_chat.py:2580), so per-message device picking by two users would race over shared session state. Retain manual org browser routing (L/apps/backend/core/containers/config.py:1768). Parent/child handoffs, persistent side panels, personal provider-account choice, public links and Swarm remain separate slices after this seam.

## Upgrade risks versus product risks

**Upgrade qualification** owns patch replay, valid mixed-version configuration, plugins, runtime/Workshop state persistence, final-image boot/recovery and machine-path compatibility. The native-auth prototype can reveal a needed fork change early; it does not justify activating trusted-proxy during an otherwise personal-chat image rollout.

**Product qualification** owns durable human identity, legacy privacy, subscription/revocation enforcement, concurrent-room sends, full session panel routing, device/approval actor binding and correct audience labels. An image upgrade supplies native methods but none of those Lightbulb acceptance results. Native membership is not an invite-only read ACL, and transcript policy is not protection against an unrestricted runtime admin, shell, shared filesystem or memory. Confidential rooms and interorganization federation require explicit additional boundaries, not a broader RPC allowlist.
