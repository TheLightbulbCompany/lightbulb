## SIX-BULLET VERDICT

- **CONFIRM (headline holds, and harder than the spec admits).** Hermes has zero multi-agent registry. `agent:main` is hardcoded at `run.py:1031`; `/v1/models` returns one model; `_create_agent` has no agent_id; the devs' own `status.py:9-11` comment files "multiple agents concurrently" as unbuilt. The spec's port methods `list_agents` / `create_agent` / `list_sessions(agent_id)` (spec lines 225-227) have **no Hermes-side key to resolve** — on the Hermes adapter they degrade to "which persona string + which session prefix the backend invents." Agent identity MUST become a backend-held registry. **The interim report is correct.**

- **CRACK the spec's "both-agents-concurrent" framing — it's true only in the weakest sense, and one concrete shared-state bug undercuts even that.** `init_agent` ALWAYS writes `os.environ["HERMES_SESSION_ID"] = agent.session_id` (`agent_init.py:867`) on every agent build, including the API-server run path (`_create_agent`→`AIAgent`→`init_agent`). The code's own comment (`:861-866`) admits this is a "fallback for CLI mode" and that the ContextVar (`_SESSION_ID.set`, `:870`) is the concurrency-safe path — but the env write fires unconditionally. Under two simultaneous Friday+Atlas runs this is **last-writer-wins process-global state**; any tool reading the env fallback instead of the contextvar mis-attributes the session. The interim concurrency verdict ("explicitly designed for concurrency") oversold this — the contextvar isolation is real for session_context vars, but the `os.environ` session-id leak is a genuine cross-run hazard. **NUANCE the interim "yes, clean concurrency" claim.**

- **CONFIRM concurrency is real and unserialized (the daemon CAN run Friday and Atlas turns at the same time).** `_handle_runs` fires `asyncio.create_task(_run_and_close())` (`:3140`) and returns `202 {"status":"started"}` immediately (`:3152-3156`) with **no await and no global lock**. Each run's blocking work goes to the default thread pool via `run_in_executor(None, _run_sync)` (`:3053`). The run.py `_running_agents` "already running" serialization is the **chat-platform path only** (Telegram/Discord/native) and the API-server adapter never touches it. So Friday-turn and Atlas-turn submitted as two `/v1/runs` execute **truly concurrently**, not serialized. **The interim report is correct on the headline concurrency answer.**

- **NUANCE: "concurrent" is capped at 10 and the daemon is single-tenant, single-key, volatile.** `_MAX_CONCURRENT_RUNS = 10` (`:2797`); the 11th run gets `429` (`:2874-2878`). Per-Isol8-user that cap is fine. BUT: all run state is in-process Python dicts (`_run_streams`, `_run_statuses`, `_active_run_agents` — `__init__` `:658-671`); a gateway restart / ECS task replacement / OOM **silently drops every in-flight run with no terminal event**. And SSE is single-consumer: `_handle_run_events` does `q = self._run_streams[run_id]` (`:3189`) with a destructive `await q.get()` and the first disconnect pops the queue (`:3217`). Two subscribers to one run **race and split the stream** — the backend connection-pool plus any debug probe would corrupt delivery. The spec must not assume durable runs, multi-subscriber SSE, or in-daemon tenant isolation; none exist.

- **CONFIRM the persona-delivery mechanism the spec picks is the right (only viable) one — and the spec is honest about it.** Friday/Atlas-as-`ephemeral_system_prompt` (run-create `instructions`) is uncapped and unscanned (spec lines 118-124, grounded in `conversation_loop.py:736-740`). The alternatives are worse: `personalities[]` is daemon-global single-persona (`run.py:9670-9683`), and SOUL.md files are 20k-capped + injection-scanned (`prompt_builder.py:824-826,1324`). The spec correctly rejects both. The real cost — which the spec underweights — is **operational**: the FULL persona must be re-sent on EVERY `/v1/runs` (no server-side persistence of "who Friday is"), so persona storage, routing, per-agent state, and marketplace-agent identity ALL move into the Isol8 backend. This is a materially heavier backend than OpenClaw's server-resolved `agents.list[]`.

- **BOTTOM LINE: spec is feasible but mis-frames the divergence as "thin adapter." It is not.** The port (spec lines 221-239) presents `list_agents`/`create_agent`/`list_sessions(agent_id)`/`export_agent` as symmetric methods both adapters implement. On OpenClaw these are server-resolved RPCs; on Hermes they are **backend-fabricated conventions over a single shared, stateless, volatile, single-tenant daemon** that has no notion of an agent. That asymmetry is the project's true risk surface — every "agent" abstraction Isol8 relies on today (Paperclip `adapterConfig.url`→agent binding, per-agent sessions/memory/cron scoping, marketplace deploy minting a new addressable agent) has to be re-implemented backend-side for Hermes. Greenlight only with eyes open that "runtime option" = "build and own the entire agent-identity layer for the Hermes brand."
