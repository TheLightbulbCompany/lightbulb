# Native OpenClaw multi-node contract investigation

Date: 2026-09-08. Status: read-only source investigation and proposed design; no implementation, runtime tests, deployment, or live device proof performed.

## Conclusion

One shared native parent session can coordinate work across Alice's and Bob's authorized nodes. Native command tools already accept an explicit node per invocation. Native whole-session worker placement has exactly one placement and one active turn claim per session; simultaneous whole-agent work on two nodes therefore uses two native child sessions attached to that parent. These are execution children, not two replacement user conversations. Both people remain in the same shared parent, see both destinations and receive both results there.

For the first tool-execution slice, reuse native per-invocation targeting in the same shared parent; a child session is not mandatory for every tool call. Prove two authorized nodes, overlapping safe work, exact result attribution and uncertainty handling there first.

For the separate full-worker slice required by the overall goal, the smallest complete design reuses native visible-child creation, explicit `sessions.dispatch({key, deviceId})`, session-owned workspaces, run tracking, completion delivery, approvals, and cancellation. It needs a narrow adaptation to start a visible child **after** placement and an enforced Lightbulb member/node grant boundary. A fixed `execNode` room is only an identity/device prerequisite, not completion of multi-node tool execution. No extra orchestrator, gateway mesh, container per conversation, or second transcript database is justified.

## Current Lightbulb behavior that must change

L `apps/backend/routers/websocket_chat.py:2520` builds a personal session key. At `:2537` each send finds that sender's CLI node, then at `:2580` patches shared session state with `execNode` and clears `execHost` to auto. The patch error is caught and the send continues (`:2596`). It is not admission tied to that turn. With a future shared key, Alice and Bob can interleave patches and sends; later tools or queued turns can observe the other person's node. An RPC/session write lock cannot make these separate operations one immutable execution admission.

L `apps/backend/core/services/node_proxy.py:45` holds a process-local user-to-CLI/Mac map and at `:51` a process-local session-to-node patch cache. CLI disconnect clears matching session defaults through privileged `sessions.patch` (`:398`–`:420`). Neither map is a durable shared-room destination or grant owner. Preserve the existing protection against a stale socket clearing its replacement (`:377`), but do not clear an admitted multiplayer destination because presence changed. Show it as offline. The current helper also matches user-bearing personal session keys (`:110`), so it cannot be assumed correct for new room keys.

L `apps/backend/core/services/desktop_pair.py:329` stores a custom `userId` to identify a person's paired entries; `:414` derives command groups from the supplied desktop permission grant. This proves useful device ownership/provisioning context. It does not define which other human or room agent may act through that device, for which workspace or operation, or after org/grant revocation.

There is also a concrete command-grant gap to resolve before sharing devices: L `apps/backend/core/services/desktop_pair_live.py:205` documents that live `node.pair.approve` approves all declared commands, tolerating several unconditional commands that can exceed a partial grant until a later boot imports the exact surface. The report does not assume the new native schema fixes that. A live partial grant must not widen during shared-room use; reconcile against the frozen command approval implementation and prove exact approved ∩ declared ∩ Lightbulb-granted commands.

L `apps/backend/routers/websocket_chat.py:358` default-denies RPCs outside its allowlist. That list does not expose native child creation, worker dispatch/environment inventory or generic node invocation to the chat client. Keep the default-deny policy; add only the selected typed routes with room/member/destination checks. L `packages/shared/src/gateway/types.ts:27` has run/session and tool-call correlation, but no complete typed destination/grant/result-source projection. Desktop's Mac companion is expressly separate from cross-platform shell execution (L `apps/desktop/src-tauri/src/node_invoke.rs:1`). The search found no `nodeHost.workerRuns` enablement under desktop source; this is an implementation/proof gap, not evidence that current installed hosts support workers.

## Smallest complete two-person/two-node journey (proposal)

1. Alice and Bob enter the **same** native company-readable parent room through distinct verified human admission. Their personal history remains private. The parent is the durable conversation and controller; nodes remain inside the same owner gateway trust domain. Room membership is not an invite-only read ACL and does not grant computer access.
2. Each sees two stable device entries, e.g. “Alice's Mac” and “Bob's Mac”, with owner, full canonical node identity internally, connected/hosting/capacity state, supported operations and current grant availability. Neither node names nor who sent most recently determine authority.
3. Alice asks the room to perform independent work A on Alice's node and work B on Bob's node. The UI/work item shows the requester, coordinating agent, exact destination, workspace/resource scope and required target-owner grant. Bob explicitly authorizes B; Alice authorizes A under the applicable native approvals. A standing room grant is a separate later policy choice, not inferred from pairing.
4. For whole-runtime work, the existing native visible-spawn path reserves child admission and creates **two** native children without initial execution. Each gets `parentSessionKey`, spawn depth, creator/controller/completion ownership, inherited tool/spend policy and its own session-owned managed worktree or repository workspace. Fork only permitted room context; never hydrate either person's private session by default.
5. The same native spawn lifecycle dispatches child A with explicit `deviceId=A` and child B with explicit `deviceId=B`. Only after each returns active placement and current grant/member authorization is revalidated does it send that child's first task. Child IDs/run IDs are fixed before retries; no local initial turn, `autoDevice`, or other-node retry. A failed placement remains a visible non-running child with a reason and inspection/recovery action.
6. The two children run concurrently subject to existing worker capacity, child count/depth, provider cost and approval limits. Shared-parent sends continue using native queue/CAS semantics; concurrent work does not require competing foreground claims on the same transcript. Parent lineage and native subagent completion registration are retained so both results arrive in the shared room and each child remains inspectable.
7. Both clients display two run cards with requesting human, acting agent, “authorized by”, destination and workspace, actual lifecycle state, stop control and eventual result source. Child completion is distinct from successful artifact reconciliation. A conflict or lost result is never a generic green “done”.
8. Disconnect/reconnect restores canonical parent/child history and native run/placement state, folds duplicate event IDs/sequences, and does not submit a fresh mutation just because the client missed an ACK. Result delivery uses native correlated completion and durable session delivery; no Lightbulb transcript copy.

This is a proposed extension to the existing native spawn flow, not proof that steps 3–8 already work in Lightbulb. The first patch should be the minimal `deviceId`-aware visible child lifecycle plus its grant guard and client projection; do not introduce a separate Lightbulb worker scheduler. Direct device commands can use native per-invocation targeting in the parent under the same grant contract, but are not a substitute for the required whole-worker journey.

## Admission and authority requirements

The admitted operation must bind, as one immutable server-owned record/carrier: owner trust domain, verified requester/profile, parent session and lifecycle, acting agent, operation/task identity, child session/run when present, canonical node ID and pairing generation, target-owner grant identity/revision, allowed command/tool families, workspace/resource scope, and approval binding. Native placement additionally supplies environment, owner epoch, placement generation and turn claim. The exact persistent owner for any new grant metadata must be selected before implementation; reuse existing Lightbulb ownership/grant metadata and native task/approval records where they actually cover it. Do not store it in a second transcript or infer it from display names. Changing native SQLite persistent semantics needs the discussion required by U `AGENTS.md`.

Check current company membership, room action access, device ownership/pairing, grant, resource scope and spend policy at admission **and again before execution after queueing, placement, approvals or other awaited work**. Child authority must be a subset of its parent operation and the target owner's grant. Revoking the requesting member or grant closes dependent queued and running capabilities. Rejoining or re-pairing does not silently revive them. Browser/device/local-file/plugin paths must not bypass the same decision merely because they avoid `exec`.

Verified native enforcement is useful but narrower: U `src/gateway/server-methods/nodes.invoke.ts:345` checks both initial and current config command policy; `:513` checks again at dispatch and `:544` rechecks runtime/approval authority. `src/gateway/node-registry-private.ts:278` binds connection and pairing generation and at `:365` checks abort/current authority before transport. `src/gateway/node-invoke-plugin-policy.ts:234` owns policy-mediated dispatch and `:327` repeats live authority checks. These do **not** establish a Lightbulb member-to-node grant. Add the missing policy through a proven native enforcement seam; a UI filter or a lone agent `before_tool_call` check does not cover direct RPCs, worker starts, delayed approval callbacks and dedicated plugin actions.

Existing plugin policy applies to registered command surfaces, not a demonstrated universal member-grant hook over all core dispatch. Before deciding plugin-only implementation, prove its coverage across exec, dedicated node tools, worker dispatch/continuation and revocation. If it cannot cover those paths, add the narrow shared fork authorization seam at the existing native lifecycle owners and let a Lightbulb plugin supply domain policy. Do not widen admin scopes to make this work.

## Workspace and concurrent-write contract

Native worker placement is substantially stronger than setting a remote `cwd`. U `src/node-host/node-worker-workspace-identity.ts:89` validates absolute canonical workspace paths against gateway namespace, environment hash, session hash and owner epoch; it rejects symbolic links and mismatched identity-derived paths. U `src/gateway/server-methods/sessions-dispatch.ts:96` requires a session-owned worktree/repository. Use those workspaces for A/B, not the same live checkout or either person's home directory.

Native workspace reconciliation already records conflicts and retains local versions with staged worker results (U `src/gateway/worker-environments/workspace-conflicts.ts:66`). Its publication reservations are session keyed (U `src/gateway/worker-environments/placement-workspace-reservation.ts:21`); that is **not** a global lock across arbitrary filesystem paths, shared drives or external services accessed by two children.

For the first complete journey, A and B write separate native workspaces/artifacts; the shared parent integrates one deliverable serially through the existing review/approval flow. Two operations against the same declared resource must serialize at its real mutation owner or require a native version/CAS check. Do not claim that different child session IDs make a shared branch, remote database row, browser account or external API safe for simultaneous mutation. Unknown arbitrary shell side effects cannot be made disjoint by prompt text; narrow the allowed operation/workspace or serialize those approved writes. If the product promises concurrent edits to the same external resource, the concrete resource identity and conflict rule are an additional design requirement, not covered by this journey.

## Failure, cancellation and replay contracts

| UI state | Required evidence and behavior |
| --- | --- |
| Offline / not dispatched | Keep the admitted node visible. Native explicit-node resolution rejects unavailable nodes; U `src/gateway/server-methods/nodes.invoke.ts:329` reports `NOT_CONNECTED` with `nodeCommandDispatched:false`. Show retry after reconnection, subject to fresh grant checks. Never move to gateway or another node silently. |
| Waiting / queued | Distinguish placement preparation, approval waiting, native turn queue and capacity rejection. “Queued” requires an actual accepted native queue/task record; a pending client spinner or timed-out RPC is insufficient. First implementation should fail visibly before dispatch when offline/capacity-bound, without inventing a general durable offline command queue. |
| Running | A `sessions.dispatch` success means durable worker ownership, not task execution or success. Use native run/worker-start/progress evidence. Preserve separate provisioning/syncing/starting/active placement state from `placement-state.ts:1`. |
| Uncertain | After transport handoff, timeout, disconnect or malformed response can mean a command executed. U `src/agents/bash-tools.exec-host-node-failure.ts:40` explicitly classifies uncertainty and at `:85` says not to rerun automatically. Render the existing `outcome-unknown` details, not merely `failed`. Retain destination and IDs for inspection. |
| Cancel requested | Stop future dispatch/approvals and send native cancellation for the exact run/invocation/claim. A request to stop is not proof that a remote side effect was stopped. |
| Cancelled before dispatch | Confirm queue/admission cancellation and no handoff. Fresh work after a new grant uses a new explicit operation; a revoked queued operation cannot revive. |
| Running work cancelled/revoked | Close native authority, cancel exact children/invocations, deny later tool calls and fence stale results. Await native acknowledgement/reconciliation where available. If the node is unreachable, show stop unconfirmed/uncertain; no rollback or exactly-once promise. Preserve already produced work under its existing privacy policy. |
| Completed | Require the native terminal result for that exact source/run. Show reconciled artifact separately and label unresolved conflicts or uncertain external side effects. Completion delivery must be correlated and deduplicated, not inferred from an idle node. |

Native generic `node.invoke` is not a durable exactly-once command service: U `src/gateway/node-registry-private.ts:332` mints a new invocation ID and forwards the supplied idempotency key; `src/gateway/node-registry.ts:273` owns pending calls in memory. The inspected `system.run` path contains no general execution dedupe by the transport idempotency key; the dedupe cache in `invoke-system-run.ts:156` is for repeated warnings. The schema comment alone must not be sold as a side-effect guarantee.

U `src/gateway/server-methods/nodes.handlers.invoke-result.ts:49` checks the reporting node identity and passes connection identity to the pending-call owner. Late/unmatched results are acknowledged as ignored (`:65`). U `src/gateway/node-registry.invoke-stream.ts:134` consumes a pending result once; progress uses ordered sequences. A replacement node connection cannot claim an old connection's result. Reconnection may restore availability, but cannot reconstruct a lost generic invocation result from that in-memory map.

U `src/gateway/node-invoke-readiness.ts:7` only retries explicit `NODE_INVOKE_NOT_READY` rejection with a bounded original deadline. `node-registry.invoke-stream.ts:143` converts a contradictory not-ready result after progress into unavailable, blocking unsafe replay. Keep these native rules. U `nodes.invoke.ts:593` permits narrow foreground iOS pending actions only when no closure-bound agent or approval authority is present; this is not an offline queue for arbitrary shared-agent shell commands.

Cancellation support is concrete but bounded: U `src/gateway/node-registry.ts:276` sends `node.invoke.cancel` to the matching live connection for supported nodes; `node-registry.invoke-stream.ts:377` settles the pending call when cancellation is requested, without establishing remote rollback. Existing cancellation tests exercise abort before dispatch and signal propagation. Target node/version support must be checked live, especially the split CLI and Mac-companion hosts.

Worker recovery has stronger native durable identity: U `src/node-host/node-worker-turn-store.ts:170` claims by launch identity, replays the same stored receipt, and rejects different plans/owners; `node-worker-turn-lifecycle.ts:96` consumes that claim before IPC. U `src/gateway/worker-environments/worker-turn-rpc.ts:335` checks credential/environment/epoch/session attachment, and `:371` revalidates exact authority at transcript commit, then advances native ACK cursors. U `placement-worker-gate.ts:78` treats pre-restart claims as recovery-only when requested, not fresh operational authority. These are bounded launch/result/stream replay contracts, not exactly-once guarantees for external tool effects inside a worker.

Native session-create retries also have limits: U `packages/gateway-protocol/src/schema/sessions-create.ts:13` declares four-minute retry/five-minute retention windows, and `src/gateway/server-methods/session-create-idempotency.ts:77` checks request consistency. Its cache is a process-local WeakMap (`:23`) scoped to authenticated principal/device (`:35`), so restart loses that dedupe even within the nominal window. Inspect/adopt the existing child by its known native identity after ambiguous creation; do not recreate a task after restart or beyond the retry window blindly. Preserve the originating send identity through native queued followup/adoption; U `src/gateway/server-methods/chat-send-agent-dispatch.ts:643` explicitly distinguishes a queued client run from its later drain. One `clientRunId` is not universally the executing run forever.

Use native correlated child completion (U `src/agents/subagents/completion/subagent-completion-delivery.ts:102`) and session delivery (U `src/agents/subagents/announce/subagent-announce-delivery.ts:7`), preserving controller and completion-owner session keys. Independently prove live and restored UI dedupe using canonical message IDs/run lineage and sequence, with no second transcript database.

## Attribution and privacy

Display requester, grant actor and result source as separate facts. “Alice asked”, “Bob authorized Bob's node”, “Friday delegated”, and “result reported by Bob's node, child/run X” are different facts. A paired node is not a human author; a grant is not a successful action. Missing historical attribution stays unknown.

Do not use `audit.run.inspect` as authorization or silently enable broader collection to fill the UI. U `docs/gateway/audit.md:60` makes execution identity opt-in and best-effort; `:101` explains that `runId` is correlation, not unique execution identity. At `:328`, all same-gateway `operator.read` clients may receive retained identity diagnostics; this is not a hostile multi-tenant isolation boundary. Production telemetry/retention/privacy changes remain separately gated. Product-essential operation/grant/result projections should come from their authoritative native lifecycle/approval owners, with access-filtered safe fields and “unknown” when unavailable.

Parent and child rooms keep native session access policy. Publishing a result to the company-readable parent is an explicit audience consequence of authorizing the task; it must not copy unrelated personal files, local credentials or private conversation history. Existing production release approval, founder-only runtime scope and private-history contract remain unchanged.
