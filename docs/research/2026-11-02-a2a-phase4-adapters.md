# Phase 4 adapters research (2026-11-02)
Tags: [P] = fetched vendor/project page. [S] = search snippet/summary only, not fetched (do not cite without a fetch).

## 1. Summary findings
1. Copilot Studio is an A2A CLIENT today: "Add agent > A2A agent", endpoint URL, auth None / API key / OAuth 2.0; it sends `message/send` with `params.message.metadata["copilotstudio.microsoft.com/a2a/chathistory"]` plus `contextId`. No user identity field is documented there. [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-agent-agent-to-agent . This is the one platform where our door can be called natively; the authority object must be minted by a Power Automate flow / custom connector in front, or by our own A2A agent that Copilot Studio calls.
2. Copilot Studio event-triggered (autonomous) agents run ONLY on the maker's credentials; docs warn users can then reach data via the author's authority. [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-triggers-about . Conversational tools can use "User authentication" (per-user connection) or "Agent author authentication". [P] .../configure-enduser-authentication
3. Slack gives a clean, signed "who" on every event: `event.user` + `event.channel` (app_mention, message.im), `event.assistant_thread.user_id` + `.channel_id` + `.thread_ts` (assistant_thread_started), `user` object in block_actions. Requests are HMAC-signed (`X-Slack-Signature`, `v0:<ts>:<body>`, 5 min tolerance). [P] URLs in section 2.
4. Slack button presses carry who pressed (`user`), where (`container`, `channel`, `message`), 3 s ack, `response_url` usable 5 times in 30 min. So an approval-hold-for-holder flow maps to Block Kit buttons with the holder's Slack user id checked against the pressing `user`. [P]
5. Slack agents act as a bot by default; user-token acting exists via the Slack MCP server (user-token OAuth `v2_user`, only directory-published or internal apps) -- never "as whoever mentioned the bot" automatically. [P] https://docs.slack.dev/ai/slack-mcp-server . Slack AI overview page does not mention A2A. [P] https://docs.slack.dev/ai/
6. Notion: webhooks identify the actor: `authors[]` with `type` person | bot | agent. Custom Agents act on granted pages only ("never have full workspace access by default"); users without agent access can still trigger agents via Slack events. Whether agent actions are attributed to the agent or triggerer is NOT stated. [P] https://developers.notion.com/reference/webhooks-events-delivery , https://www.notion.com/help/custom-agent
7. Notion has no button block in the API (only `unsupported`), so the callback surface is comments (`POST /v1/comments`, needs "insert comment" capability, `display_name` integration|user|custom) plus links/embeds to our approval page. [P] https://developers.notion.com/reference/block , .../create-a-comment . Notion MCP is user-OAuth, acts within user's permissions; no A2A/agent statement found. [P] https://developers.notion.com/docs/mcp
8. GitHub PR review fits as an adapter: a GitHub App can create a check run (only Apps can) with `output.summary/text` (65,535 chars), `external_id`, `details_url`, up to 3 `actions` buttons that fire `check_run.requested_action`; rulesets can require that check, pinned to the App as expected source. [P] https://docs.github.com/en/rest/checks/runs , .../available-rules-for-rulesets
9. GitHub rule confirmed: requester's own approval of a Copilot PR "won't count"; another reviewer must approve; rulesets add an extra approval for Copilot PRs "not attributed to a person" (no effect at 0 required). Workflows don't auto-run on Copilot pushes. [P] https://docs.github.com/copilot/how-tos/use-copilot-agents/coding-agent/review-copilot-prs , available-rules page.
10. A2A extension path: extensions declared in `capabilities.extensions` (`uri`, `description`, `required`, `params`), activated by `A2A-Extensions` header, version in URI, breaking change = new URI. Proposal = issue in `a2aproject/A2A` with abstract, motivation, initial technical approach; needs a Maintainer sponsor, then `experimental-ext-{name}` repo; graduation by TSC vote (>=50% quorum, majority). Independent publishing is allowed; no third-party listing process is documented. [P] https://a2a-protocol.org/latest/topics/extensions/ , .../extension-and-binding-governance/

## 2. Slack
Facts
- Agents: "autonomous, goal-oriented AI apps..." with split-view container, app threads, text streaming, suggested prompts. [P] https://docs.slack.dev/ai/
- `assistant_thread_started` (Events API, no scopes): `event.assistant_thread.user_id`, `.channel_id` (the DM/thread channel, e.g. D...), `.thread_ts`, `.context.channel_id/.team_id/.enterprise_id` (channel the user is viewing; call conversations.info to check access). Wrapper: `team_id`, `api_app_id`, `event_id`, `event_time`, `authorizations[]` (`team_id`, `user_id`, `is_bot`, `is_enterprise_install`). [P] https://docs.slack.dev/reference/events/assistant_thread_started
- Suggested prompts: `assistant.threads.setSuggestedPrompts` with `channel_id`, `thread_ts`, `title`, `prompts[]{title,message}`; up to 4 per Bolt comment. [P] https://docs.slack.dev/ai/developing-agents
- `app_mention`: scope `app_mentions.read`; `event` = `type,user,text,ts,channel,event_ts` (page lists no `thread_ts`). Bot user required. [P] https://docs.slack.dev/reference/events/app_mention
- `message.im`: scope `im:history`; `event.user`, `event.channel`, `channel_type:"im"`, `ts`. [P] https://docs.slack.dev/reference/events/message.im
- `block_actions` payload top-level: `user` (required, who interacted), `container`, `channel`, `response_url`, `trigger_id`, `actions`, `team` (null if org-installed), `message`. [P] https://docs.slack.dev/reference/interaction-payloads/block_actions-payload
- Interactivity: HTTP POST form-encoded with `payload` JSON; ack 200 within 3 s; `response_url` 5 uses within 30 min; `response_type: in_channel` posts publicly (ephemeral default); `replace_original`/`delete_original`; `trigger_id` valid 3 s, single use. [P] https://docs.slack.dev/interactivity/handling-user-interaction
- Request verification: headers `X-Slack-Signature`, `X-Slack-Request-Timestamp`; HMAC-SHA256 of `v0:<ts>:<raw body>` with signing secret, `v0=` prefix, constant-time compare, reject >5 min skew. [P] https://docs.slack.dev/authentication/verifying-requests-from-slack
- Rate limits: Web API tiers 1-4 (1+/20+/50+/100+ per min, per method per workspace per app); `chat.postMessage` ~1 msg/s/channel plus workspace limit. [P] https://docs.slack.dev/apis/web-api/rate-limits
- Slack MCP server: `https://mcp.slack.com/mcp`, JSON-RPC 2.0 over Streamable HTTP, confidential OAuth, user-token scopes (`search:read.public`, `chat:write`, `files:write`), only directory-published or internal apps; clients Claude.ai, Claude Code, Perplexity, Cursor. Some tools act "on behalf of the authenticated user". [P] https://docs.slack.dev/ai/slack-mcp-server
- Agentforce: AI page says Slack AI via "workflow automations and Salesforce Agentforce" with custom Slack actions; A2A not mentioned. [P] https://docs.slack.dev/ai/
- Token model (bot vs user) for events: NOT on the pages fetched; `authorizations[]` shows installing-side ids only.

Adapter attachment point
- Mint on: `app_mention` / `message.im` / `assistant_thread_started` + first message. Requester identity = `event.user` (or `assistant_thread.user_id`), verified by Slack signature on our adapter endpoint (we hold signing secret). Agent chain = the Slack app (bot) identified by `api_app_id`; "for whom" = the installer (not in the event; adapter must hold install-time mapping from `team_id`+`api_app_id` to the installing Lightbulb principal) or the holder named by the workspace.
- Hold/ask: our door returns input-required; adapter posts a Block Kit message with approve/deny buttons to the holder's DM (`conversations.open`) ; on `block_actions` the adapter checks `user.id` == holder's mapped Slack id and sends the decision to the door; replies via `response_url` / `chat.update`.
- Needs a Slack user id <-> Lightbulb principal binding (not provided by Slack).

## 3. Notion
Facts
- Custom Agents: access limited to pages/databases/external apps explicitly granted ("never have full workspace access by default"); embedding an agent in a page does not grant access. Levels: Full Access, Can Edit, Can View and Interact. [P] https://www.notion.com/help/custom-agent
- Triggers: recurring; Notion (comment added, page added to database, property updated, page removed, AI Meeting Note finished); Slack (message posted, emoji reaction, @-mention; thread replies; keyword filter). Users without agent access can still trigger agents responding to Slack events in channels they can access. Slack account must share email with Notion account. [P] same page
- Activity tab logs "what triggered each run, actions taken, errors" (Full Access only); page does NOT say whether actions are attributed to the agent or the triggering person. [P] same page
- Webhooks: payload `type` (e.g. `comment.created`, `page.created`), `authors[]` {`id`, `type`: person|bot|agent}, `entity` {`id`,`type`: page|block|database|comment|data_source}; resolve ids with Users API. [P] https://developers.notion.com/reference/webhooks-events-delivery (signature verification not on that page)
- Notion MCP: remote server, OAuth, "operates within that user's permissions". No agent/A2A statement. [P] https://developers.notion.com/docs/mcp
- API blocks: no `button` block; `button` appears only as an `unsupported` block_type. [P] https://developers.notion.com/reference/block
- Comments: `POST /v1/comments`; target one of `parent.page_id`, `parent.block_id`, `discussion_id`; body `rich_text` (<=100 objects, 2000 chars each) or `markdown` (v2); `display_name` {integration|user|custom+name}; `attachments` <=3; needs integration capability "insert comment" (else 403); Notion-Version 2026-03-11. [P] https://developers.notion.com/reference/create-a-comment

Adapter attachment point
- Mint on: a Notion webhook `comment.created` (or page event) where `authors[0]` gives the acting person (type person) vs agent; plus the Slack-trigger route. Identity = `authors[0].id` mapped via Users API to email; verified by Notion webhook signature (verify against Notion docs, not fetched). Weakest platform: the triggered agent's own run does not expose a "triggered by" field in any page I fetched, so the adapter would have to wrap the integration the agent calls (an MCP/HTTP tool) rather than intercept the agent.
- Callback: comment with a link to a Lightbulb approval page; no native button.

## 4. Microsoft Copilot Studio
Facts
- Auth options: No authentication; Authenticate with Microsoft (Entra, Teams/SharePoint/Power Apps/Microsoft Copilot); Authenticate manually (Entra ID V2 federated creds/certs/secrets, Entra ID, Generic OAuth 2). [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/configuration-end-user-authentication
- User variables: with Microsoft auth: `User.Id`, `User.DisplayName` (+ `User.IsLoggedIn` and profile variables in web app; not `User.AccessToken`). Manual auth adds `User.AccessToken`. [P] same
- Tool auth per tool: "Agent author authentication" vs "User authentication"; user auth shows a connection card; no credentials stored by Copilot Studio. [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/configure-enduser-authentication
- Event triggers: payload from a connector (JSON or text), "Event triggers can only use the agent maker's credentials"; recurrence, SharePoint, OneDrive, Planner, Dataverse examples; admins can block triggers via data policy. [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-triggers-about
- MCP: supports MCP tools and resources (not prompts), needs generative orchestration; connect via onboarding wizard; MCP connector can be certified for cross-tenant. [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/agent-extend-action-mcp
- A2A: Copilot Studio calls out to A2A agents; endpoint URL (not agent card URL; card at endpoint + `/.well-known/agent.json` read for name/description), auth None/API key (header or query name)/OAuth 2.0 (client id, secret, auth URL, token URL, refresh URL). Sample endpoint used `/a2a/botanical/v1/message:stream`. Sends `method: message/send`, `contextId`, message ids, locale, full chat history under `metadata["copilotstudio.microsoft.com/a2a/chathistory"]` (entries From, Locale, Text, Timestamp). Uses custom-connector infrastructure (works for on-prem/vNet). Docs state responsibilities incl. "identity and traceability". [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-agent-agent-to-agent ; catblog [P] https://microsoft.github.io/mcscatblog/posts/copilot-studio-a2a-multi-agents confirms same infra, says nothing on user identity or protocol version.
- Docs table says "Connect to APIs or basic HTTP services: Custom connectors / HTTP tools". [P] add-agent-agent-to-agent page.

Adapter attachment point
- Option A (cleanest): publish our adapter as an A2A agent endpoint; Copilot Studio's OAuth 2.0 option gives a per-connection credential; the adapter reads the chat-history metadata and the OAuth identity, and builds the authority object. Whether the connection is per-user or per-maker for A2A is not stated.
- Option B: custom connector/HTTP tool with "User authentication" so the Entra token of the invoking user reaches our adapter; adapter validates the Entra JWT (oid, tid) and mints the authority object with requester = that user.
- Triggered (autonomous) runs: requester is the maker; "who asked" is the trigger event source, so the adapter should record requester = maker + trigger payload, and rules should treat it as a system actor.

## 5. Coding-agent PR review as an adapter
Facts
- Requester's own approval of a Copilot PR "won't count"; another reviewer must approve; workflows don't auto-run on Copilot pushes ("Approve and run workflows"). [P] https://docs.github.com/copilot/how-tos/use-copilot-agents/coding-agent/review-copilot-prs
- Rulesets: "Require pull request" approvals 0-10; for Copilot-opened PRs not attributed to a person an extra approval is required by default (no effect at 0); "Require approval of the most recent reviewable push" needs approval from someone other than last pusher. [P] https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets
- Required status checks: can be checks or statuses; can pin an expected source app (app installed with `statuses:write`, recently submitted a check run). [P] same
- Rulesets/branch protection can block Copilot from creating or updating PRs; admins can configure a bypass for Copilot. [P] https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent
- Check run: `POST /repos/{owner}/{repo}/check-runs`; only GitHub Apps can write; fields `name`, `head_sha`, `status`, `conclusion` (success|failure|neutral|cancelled|skipped|timed_out|action_required), `details_url`, `external_id`, `output{title,summary,text,annotations,images}`, `actions[]{label<=20,description<=40,identifier<=20}` max 3 -> buttons -> `check_run.requested_action` webhook. summary/text 65,535 chars; 50 annotations per request. [P] https://docs.github.com/en/rest/checks/runs
- Review: `POST /repos/{owner}/{repo}/pulls/{n}/reviews`, `event` APPROVE|REQUEST_CHANGES|COMMENT, `body`, `commit_id`, `comments[]`. [P] https://docs.github.com/en/rest/pulls/reviews . (Permission names and whether a bot may APPROVE: NOT on page.)

Adapter attachment point
- Mint on: PR opened/synchronize by the coding agent (`pull_request` webhook). Requester = the human who assigned the issue/task (not in the PR author field, which is the bot; recover from PR body/commit trailers/session link, which Lightbulb must write itself or read from the agent session). "For whom" and operation = merge of PR X at head_sha (operands: repo, number, sha, diff stats).
- Carry the authority object by writing a digest into check-run `external_id` and the full object into `output.text`; a required check (source-pinned to our App) is the enforcement. A decision of "hold for holder" = `conclusion: action_required` with an `actions` button; holder's decision posted by the App in a later check-run update; deny = `failure`.
- Do not rely on the APPROVE review path: GitHub's own rule says the requester cannot satisfy approvals, and a bot approval is not documented as counting; a required check is the dependable lever.

## 6. Publishing and proposing (A2A)
- Extension mechanics: AgentCard `capabilities.extensions[]` `AgentExtension{uri, description, required, params}`; clients send `A2A-Extensions: <uri>,<uri>`; agent echoes activated URIs in the response header; unsupported ones ignored; if `required` and client did not activate, agent should reject. Version in URI (`/v1`), breaking change = new URI; unsupported version must not fall back. Spec should be hosted at the URI; `w3id.org` suggested; ship libraries on PyPI/npm. [P] https://a2a-protocol.org/latest/topics/extensions/
- Official prefix `https://a2a-protocol.org/extensions/`; repos `ext-{name}` (official) / `experimental-ext-{name}` under `a2aproject`; Apache 2.0, RFC 2119 language, >=1 reference implementation, MAINTAINERS.md. [P] https://a2a-protocol.org/latest/topics/extension-and-binding-governance/
- Where/what: open an issue in `a2aproject/A2A` containing abstract, motivation (why core protocol/bindings can't do it), initial technical approach/spec draft. Then discussion, Maintainer sponsor, experimental repo, then graduation issue (link to repo, implementations, feedback/adoption summary, proposed maintainers), TSC vote (>=50% present, majority approve). [P] same page
- Independent publishing is explicitly allowed; no community-extension list or registry process documented on that page. [P] same page
- CONTRIBUTING.md: PRs from forks to `main`; conventional commits (`docs(spec):` for `docs/specification.md`, `docs:` for other docs, `feat:`/`fix:` reserved for `specification/a2a.proto`); Discord for chat, GitHub Discussions for long form, Issues for bugs/suggestions; no mention of DCO/CLA, governance or extensions. [P] https://github.com/a2aproject/A2A/blob/main/CONTRIBUTING.md
- Gap signal: an arXiv preprint (2606.31498) claims no governance extensions had been proposed in A2A; [S] only, not fetched.

## 7. What nobody exposes (<=8 lines)
- No platform passes "triggering person" and "agent identity" as separate, signed, machine-readable fields to a downstream callee: Copilot Studio A2A sends chat history, not user id; Notion run logs do not say whose authority an action used.
- Copilot Studio triggered runs use only the maker's credentials; Notion agents use their own grants.
- Slack gives a signed event user id, but no "act with that user's permissions" for bot apps; user tokens require a separate OAuth per user.
- Slack/Notion/GitHub do not tell the callee the installer ("for whom"); an install-time binding is ours to build.
- Callbacks: Slack (block_actions + response_url) and GitHub (requested_action) have real ones; Notion has none (comment + link); Copilot Studio adaptive-card callbacks not verified.
