## Correction and conclusion

The earlier inference “the proxies pass `gateway_token`, therefore their native handshakes use shared-token authentication and must fail under trusted-proxy” was too broad. `NodeUpstreamConnection` merely stores that constructor argument (L/apps/backend/core/gateway/node_connection.py:93). It opens a headerless private-IP socket (:180), forwards the gateway challenge, then sends the client's signed connect verbatim (:205, :234–237). The same class underlies the Paperclip operator relay. Credential choice belongs to the signing client. Also, a token in `auth.token` can be a valid native device credential, not necessarily successful shared-gateway authentication.

Native paired-device and bootstrap authentication are real 9.3 paths under trusted-proxy. They cannot bypass missing/untrusted ingress attribution; and **device-only operator credentials do not satisfy configured human roles**, whereas node-role credentials are not subject to that verified-human gate. Therefore first qualify native machine routes and enrollment; a custom bridge is not yet justified.

“Roles absent” is a qualification control, not a recommendation to disable human policy for multiplayer. Native device grants authenticate machines; they do not establish a canonical Lightbulb member or Slack person. A proposed service-principal profile must remain visibly nonhuman and must never author a user's chat turn. “Service profile” here means a dedicated principal mapped through the existing profile/role schema, **not a proven native service-profile type**. The native policy describes roles as governing identified people (U/src/gateway/operator-role-policy.ts:75), so actor/audit semantics are an explicit acceptance gate for that proposal.

## Three credential layers must remain distinct

1. **Outer Lightbulb edge admission.** Desktop signs a short-lived device JWT for the Lightbulb WebSocket edge. The authorizer looks up its public key and member under the owner's paired-device projection; this is not the native gateway device token. L/apps/desktop/src-tauri/src/device_token.rs:14; L/apps/infra/lambda/websocket-authorizer/index.py:206, :245; L/apps/backend/core/services/desktop_pair.py:598. Paperclip's outer URL carries a service JWT separately from its native signed connect (L/apps/backend/core/services/paperclip_openclaw_pairing.py:353–356).
2. **Native signed device authentication.** The gateway verifies signature/device binding and a matching native role credential or bootstrap token. Lightbulb's transparent relay cannot safely replace a signed token field. Keeping outer edge admission does not eliminate this inner authentication, nor does inner pairing replace owner/member/device revocation at the edge.
3. **Native identified operator policy.** When roles are configured, a device token cannot identify a person. Proxy auth supplies verified user identity, which is resolved to a native profile; generic proxy identity currently uses `ensureProfileForEmail` (U/src/gateway/server/ws-connection/connect-user-profile.ts:16–29). Even ephemeral clients can resolve that verified profile: profile resolution is not exclusively gated on presence (U/src/gateway/server/ws-connection/connect-session.ts:174–206). Role policy and per-session access then apply (:231–255). Service authentication must not silently collapse back into a human's owner-admin identity.

## Why the proxy-versus-machine ingress route matters

U/src/gateway/ingress-attribution.ts:223–249 classifies clean loopback as direct-local, a trusted proxy peer with valid non-loopback forwarded client attribution as trusted-proxy, a trusted peer without that attribution as unattributable-proxy, and a plain nontrusted remote peer without forwarding headers as direct-remote. Forwarding/Tailscale headers from a nontrusted ordinary peer also make it unattributable.

The gateway rejects unattributable-proxy before ordinary auth (U/src/gateway/auth.ts:419), and device/bootstrap fallback explicitly cannot override that reason (U/src/gateway/server/ws-connection/auth-context.ts:235–239). Consequently, adding the existing backend IP to `trustedProxies` for humans can break its **headerless machine sockets**, even with perfectly valid device credentials. This is a routing/attribution conflict, not proof native device authentication is absent.

Prototype both native alternatives: (a) a private, edge-authorized machine transport whose actual source is not classified as the human proxy and sends no forwarded identity headers; (b) the trusted proxy transport with correct server-authored forwarding attribution, but no invented human identity, allowing signed node authentication to supply the machine credential. Option (b) must be tested with the exact required-header configuration and routing. Neither means an unprotected public node endpoint, client-supplied forwarding evidence, fake `127.0.0.1`, or a broad trusted network range. Reject or overwrite all external identity/scope headers before forwarding.

The frozen docs are consistent only when read with these stages: `docs/nodes/index.md:103–111` warns that new nodes cannot authenticate by supplying a proxy's human headers, mixed shared-token config is rejected, and join/worker routes need edge coverage. It is not a blanket prohibition on already-paired or bootstrap-capable nodes. `docs/gateway/trusted-proxy-auth.md:463–467` explicitly says valid paired/bootstrap credentials have independent WS paths and `allowUsers` alone does not revoke them. Existing connections and every relevant edge route require revocation/enforcement.

## New enrollment is not paired reconnect

Native bootstrap verification first enforces the issued role/scope profile, then binds device ID and public key (U/src/infra/device-bootstrap.ts:556–611). A permitted setup-handoff profile can be auto-approved by the pairing plan; otherwise pairing can remain pending. A fresh, unpaired node with bootstrap auth has explicit wait-and-retry handling (U/src/gateway/server/ws-connection/connect-device-pairing.ts:428–451). Node startup, metadata/role changes, and node command-surface approval still matter (:475–533). Successful authentication is not blanket execution authorization.

U9.3 `openclaw connect` passes the setup bootstrap into node runtime (U/src/cli/connect-cli.ts:226–239); node runtime constructs a signed `role:node` client with empty scopes and an identity (U/src/node-host/runner.ts:201–244). The shared client stores `hello.auth.deviceToken` and clears one-shot bootstrap options (U/packages/gateway-client/src/client.ts:951–970), backed by real persistent host dependencies (U/src/gateway/client.ts:70–118). Credential selection and retry logic are explicit in U/packages/gateway-client/src/connect-auth.ts:39–94, :111–135. This proves future source support, not 8.1 packaged-client behavior or a completed Tauri implementation.

Current Lightbulb preseed/live approval must be exercised as its own migration case. It protects same-key/member ownership and preserves prior node tokens (L/apps/backend/core/services/desktop_pair.py:481–545); device and command-surface live approvals go through backend operator RPCs, with commands constrained to the stored grant (L/apps/backend/core/services/desktop_pair_live.py:150–240, :340–370). Thus changing backend operator admission can also break desktop onboarding even if the node's credential itself is valid. Native token verification also checks issuer generation for tagged credentials and rejects certain issuerless browser tokens (U/src/infra/device-pairing-tokens.ts:186–197); do not assume all existing machine/browser grants share the same migration semantics.

## Smallest next prototype — proposed only

One isolated frozen-9.3 gateway, synthetic disposable pairing state, a proxy peer and a separately classified machine peer; no public admin ingress or real credentials. Run sequentially with roles absent and with the intended human roles configured. Preserve the current gateway-client mode and Control UI-disabled setting. Use one human principal, one backend operator device, one Paperclip agent device, one existing node and one fresh node. No room UI is needed.

1. Demonstrate headerless trusted-peer failure with a valid native device credential; demonstrate attributable native node reconnect on the selected edge-authorized machine path. Record the native auth method, device/role/scope and redacted ingress classification, not just a green socket.
2. Replay Lightbulb preseeded backend/Paperclip token bytes as signed device candidates with shared gateway token configuration removed. Compare roles absent versus roles configured; expect the verified-user gate in the latter. Then test a distinct native proxy service principal with exact required RPC permissions and stable nonhuman identity. Only if this cannot meet the trust contract should a new bridge/fork service-auth option be designed.
3. Enroll a new canonical node-host via the native **node-only** bootstrap profile, verify issuance/consumption and command-surface approval, then restart with the native paired token alone. Separately replay current Tauri and packaged CLI behavior, and specify the minimal client credential handoff/cache change needed; do not declare native CLI success to be Tauri success.
4. Exercise backend health/one-shot maintenance, live device/surface approval, a Paperclip dispatch/result, node invocation and forced disconnect/removal while the human session remains least-privileged. Retain backend tenant, membership, entitlement, device ownership and method authorization throughout.

Required negative cases before rooms:

- Wrong/revoked/missing token; foreign device ID/key; stale signature/nonce; changed role, scope or node commands; paired-state absent or imported incorrectly; stale tagged token issuer generation.
- Bootstrap wrong/expired/consumed token, replay with another key, node token used as operator, broad mobile/operator setup substituted for node-only, bootstrap-only reconnect after successful enrollment; pending approval cannot become full command access.
- Human and machine headers forged at the public edge; trusted peer missing forwarding evidence; untrusted peer with forwarded headers; remote/forwarded password attempts; mixed configured shared token plus trusted-proxy; valid device credential cannot repair unattributable ingress.
- Device-only backend/Paperclip operator with configured roles; service principal attempting human attribution; human attempting service role/admin scopes; service device removed/unlinked but outer JWT still live; outer edge access revoked while native credential remains valid.
- Existing paired node versus fresh node, CLI versus Tauri, restart/cache loss versus token refresh, backend pairing dependency failure, node-surface upgrades, worker-route edge admission where that runtime is enabled. No public route exemption is authorized by this report.

The acceptance output is a redacted matrix of actual handshake/RPC results and revocation behavior. Until that exists, native coexistence is source-supported in the bounded cases above, not proven operationally, and neither a custom bridge nor a production trusted-proxy switch is approved.
