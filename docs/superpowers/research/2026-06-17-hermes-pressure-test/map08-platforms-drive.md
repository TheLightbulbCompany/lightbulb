# map08 — How external systems drive Hermes agent runs (the inbound integration matrix)

**Basis:** Hermes v0.14.0 @ `4c46c35e`, `/Users/prasiddhaparthsarthy/Desktop/hermes-agent`. Every claim cites `file:line` read this pass. Adversarial read against `docs/superpowers/specs/2026-06-16-hermes-runtime-option-design.md`.

## What's in `gateway/platforms/`

`ls gateway/platforms/` (read directly): two HTTP server adapters — `api_server.py` (OpenAI-compat, the `/v1/runs` family the spec fixates on) and `webhook.py` (generic HMAC webhook receiver) — plus ~22 chat-platform adapters (telegram, discord, slack, matrix, signal, whatsapp, feishu, wecom, dingtalk, mattermost, homeassistant, email, sms, bluebubbles, qqbot, weixin, yuanbao, msgraph_webhook, ...), the shared `base.py` (`BasePlatformAdapter`, `MessageEvent`, `SendResult`), and `ADDING_A_PLATFORM.md`. There is **no** `discord/slack/matrix` subpackage; each is a single file. The only subdir is `qqbot/`.

## The canonical "external system drives a run" pattern (one contract for ALL adapters)

Every adapter — chat platform OR HTTP server — drives a run through the **same four-step contract** in `base.py`, not through `/v1/runs`:
1. Inbound event arrives (TCP/WS/poll/HTTP) and is normalized into a `MessageEvent` (`base.py:918-973`) via `self.build_source(...)` → `SessionSource`.
2. Adapter calls `self.handle_message(event)` (referenced `ADDING_A_PLATFORM.md:107`; dispatch machinery in `base.py`, `_background_tasks` spawn at `webhook.py:572`).
3. The gateway's single `_message_handler` (`base.py:1282,1518-1525`, set by `GatewayRunner`) runs the agent for that session and returns a reply string (or `None` if already streamed — `base.py:1177-1180`).
4. The adapter's own `send(chat_id, content, ...)` (`base.py:1555-1575`, abstract) routes the reply **back to the originating chat_id**, with optional `_post_delivery_callbacks` (`base.py:1303-1308,2330-2408`) for after-delivery hooks.

So "response routing back to the originating platform" is **structural**: the inbound `chat_id`/`SessionSource` IS the return address, and each adapter implements `send()` against its own transport. This is fundamentally different from `/v1/runs`, which has no return address and no `send()`.

## Six findings

- **The spec missed the one adapter that IS a Paperclip-shaped ingress: `gateway/platforms/webhook.py`.** It is a generic aiohttp server (`POST /webhooks/{route_name}`, `webhook.py:185,326`) that: HMAC-validates (GitHub `X-Hub-Signature-256` / GitLab token / generic `X-Webhook-Signature`, `webhook.py:590-619`), rate-limits + dedups retries by delivery-id (`webhook.py:365-468`), renders the JSON payload into a prompt template with dot-path interpolation `{pull_request.title}` / `{__raw__}` (`webhook.py:625-663`), spawns a non-blocking agent run returning **202 Accepted** immediately (`webhook.py:571-584`), and — critically — **routes the response back** to the originating or ANY configured platform (`deliver: github_comment | telegram | discord | slack | ...`, `webhook.py:220-263,763-806`). This is a near-exact structural match for Paperclip's issue-assignment → run → comment-back loop. The spec's entire ingress design (workstream 7: a ~400-600 LoC npm `hermes_gateway` Paperclip adapter, design §4/§9) **never evaluated it.** Across the whole 11-agent research corpus `webhook.py` is named **once** (`research/.../03-chatgpt-oauth.md:103`) and only to dismiss it as "an inbound messaging-platform adapter, not a credential-rotation egress hook." That is a real scope gap, not a nuance.

- **`/v1/runs` is pull-only — there is NO inbound `callback_url` / response-routing field, confirming the spec's poll-fallback but understating the consequence.** `_handle_runs` reads exactly `input`, `instructions`, `previous_response_id`, `conversation_history`, `session_id`, `model` (`api_server.py:2885-2941`); a repo grep for `callback_url|webhook_url|notify_url|response_url|postback` in `api_server.py` returns **zero**. Responses escape only via destructive SSE (`GET /v1/runs/{id}/events`) or terminal poll (`GET /v1/runs/{id}`). So a Paperclip binding on `/v1/runs` must hold a live SSE socket per run or poll — there is no "Hermes POSTs the answer back to me" path. The webhook adapter is the ONLY built-in that does push-back delivery.

- **Response routing back to origin is per-`chat_id` delivery state, NOT a per-request reply URL.** For chat platforms the origin is implicit in the inbound `SessionSource.chat_id`, and `send()` targets it. For the webhook adapter, the route's `deliver`/`deliver_extra` config is stashed in `self._delivery_info[chat_id]` at receipt (`webhook.py:530-543`) and read (not popped) by every `send()` so interim status messages don't consume it (`webhook.py:220-264`). `_deliver_cross_platform` then dials the live adapter for the target platform via the shared `gateway_runner.adapters` map and falls back to the platform's home channel (`webhook.py:763-806`). Implication for Isol8: to make Hermes comment back into Paperclip you'd register Paperclip as a `deliver:` target (a plugin platform adapter, `webhook.py:248-258` checks `platform_registry.is_registered`) — meaning the binding is **bidirectional through the same registry**, not a one-off.

- **`deliver_only` gives a zero-LLM push-notification rail that maps cleanly to heartbeat / status pings.** A route with `deliver_only: true` (`webhook.py:174-181,476-526`) skips the agent entirely: the rendered template IS the delivered message, sub-second, no inference cost. This is exactly the shape of an external system pushing a heartbeat/status notice through to a user channel. The spec's heartbeat discussion (design §3, §8) treats Hermes as having "no webhook/event egress" — true for credential rotation, but the webhook adapter is a ready-made **inbound** push relay that the spec never connected to the heartbeat question.

- **There is NO native heartbeat that a Paperclip-style binder can subscribe to; "liveness" is poll-only and the spec's recovery model is right but the orphan behavior is worse than a binder expects.** The only liveness surfaces are `GET /health` / `GET /health/detailed` (`api_server.py:918-941`, reading `gateway/status.read_runtime_status`) and per-run terminal poll. There is no outbound heartbeat emit; `write_runtime_status` (`base.py:1439-1469`) writes a local status file, not a network event. Worse for an issue-driven binder: the `/v1/runs` SSE queue is **popped in `finally` on ANY client disconnect mid-run** (spec design §3, `api_server.py:3217-3218`), so a Paperclip relay that drops its SSE socket loses all intermediate deltas and can only recover the terminal answer by polling — the run keeps executing headless. A webhook-style push binding (agent finishes → server POSTs result to Paperclip) sidesteps this entirely, which is another argument the spec didn't make.

- **Adding Paperclip as a first-class driver is the documented "Plugin Path" (zero core changes), not necessarily an npm fork — contradicting the spec's framing of workstream 7 as bespoke.** `ADDING_A_PLATFORM.md:5-58` documents a plugin model: drop `plugin.yaml` + `adapter.py` under `~/.hermes/plugins/`, subclass `BasePlatformAdapter`, register via `ctx.register_platform()` in `register(ctx)`, "**zero changes to core Hermes code**," with the system auto-wiring config parsing, authorization, cron delivery, `send_message` routing, system-prompt hints, and status. A Paperclip ingress could be (a) a webhook route binding (no code) or (b) a plugin adapter (a Python file in the container, the same per-version discipline as OpenClaw) — **not** the spec's implied custom transport. The spec's 4-7 eng-week ingress estimate (design §10) should be pressure-tested against these two lighter paths before being accepted.
