# Agents acting for other people: where it already happens (research 11, 2026-11-02)

Tags: [P] = I fetched the primary page (vendor doc, engineering blog, advisory, regulator text, the person's own post, or the code). [S] = rests on search snippets or journalism. Each claim has a URL.

## 1. Summary findings (12)

1. **It already happens, and it is the default in shared agents.** Notion Custom Agents answer "using the agent's own access, not the permissions of the person who triggered it", and Notion warns that sharing one is "giving your team access to everything the agent can see" [P] (https://www.notion.com/help/custom-agents-sharing-and-permissions). Copilot Studio defaults allow "maker-provided credentials", so "an end user might retrieve information or perform actions that only the maker's account is permitted to do" [P] (https://learn.microsoft.com/en-us/microsoft-copilot-studio/configure-no-maker-authentication).
2. **Vendors give a binary choice, and both sides break.** One side is "use the invoker's permissions" (Rovo interactive, Microsoft OBO, ServiceNow). The other is "use the agent's or maker's identity" (Notion, Copilot Studio maker creds, Rovo automation "connection user", Agentforce agent user). The invoker-permission model was the root of the ServiceNow attack: a low-privilege user's text ran with an admin's privileges [P] (https://appomni.com/ao-labs/ai-agent-to-agent-discovery-prompt-injection/). The agent-identity model leaks to whoever can use the agent [P] (Notion). Microsoft's fix for one side kills autonomy: blocking maker credentials means "agents triggered by scheduled or autonomous events ... fail" [P] (Copilot Studio page).
3. **Customers explicitly ask for "intersection of the invoker's and the agent's permissions".** Atlassian ticket AUTO-2337 is titled "use intersecting permissions with invoking user". Atlassian answered "intended behaviour", status "Gathering Interest", 12 votes [P] (https://jira.atlassian.com/browse/AUTO-2337). Atlassian's stated direction is separate "agent accounts" with their own permissions [P] (same page). No vendor I read ships a per-request rule that combines the requester, the agent and the resource.
4. **Coding-agent fleets are the most mature case, and their one hard rule is a second person.** GitHub Copilot cloud agent "Prevents the user who asked Copilot ... to create a pull request from approving it" [P] (https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations). At Stripe, "the engineer opens the PR and requests a review from another Stripe engineer" [P] (https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents). Ramp opens PRs with the user's own token because doing it "as the app itself" lets "any user ... approve their own changes" [P] (https://builders.ramp.com/post/why-we-built-our-background-agent).
5. **Ramp shows the multi-requester case.** "Any number of people can work in one session together", and authorship "is passed with every prompt sent to the agent" [P] (Ramp). That is a per-prompt "who asked" record, so the need is real. It stops at attribution, though: there is no rule that says what each person may make the agent do.
6. **Big shops contain risk with sandboxes, not authority checks.** Stripe minions have no access to "real user data, Stripe's production services, or arbitrary network egress", so they run "with full permissions and skip confirmation prompts" [P] (https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2). Block ships "a curated set of approved MCP servers ... authored by our own engineers", with "read-only"/"destructive" tool annotations [P] (https://goose-docs.ai/blog/2025/04/21/mcp-in-enterprise). That works for code. It does not work once the agent touches shared business systems.
7. **The single-owner open-source agent is breaking on "who is speaking".** OpenClaw: "not a hostile multi-tenant security boundary for mutually adversarial users sharing one agent" [P] (https://docs.openclaw.ai/gateway/security). Its GitHub advisories from 2026-01-31 to 2026-09-11 number 722. Of those, 33 mention "owner" and 104 mention a sender or allowlist, for example "Inbound voice calls could inherit owner tool authority", "Discord realtime transcripts could inherit another speaker's owner status" and "Non-owner chat senders could issue device-pairing bootstrap codes" [P] (gh api repos/openclaw/openclaw/security-advisories).
8. **Paperclip, the company-of-agents app, routes every approval to one "board".** It has four approval types: `hire_agent`, `approve_ceo_strategy`, `budget_override_required` and `request_board_approval` (packages/shared/src/constants.ts:689-694). The decide route calls `assertBoard(req)` (server/src/routes/approvals.ts:297-304). Budgets hard-stop (server/src/services/budgets.ts:95) [P, code at 1a6017d]. Nothing routes a request to the owner of the resource. Paperclip has 110k stars, so the "owner approves everything" model is popular, and it is the thing the founder rejected.
9. **The big incidents are borrowed authority.** In each case the agent acted with someone's real credentials on content written by someone else. ServiceNow: the admin's privileges ran a low-privilege user's ticket text [P]. GitHub MCP: a public-issue author got the repo owner's private repos leaked into a public PR [P] (https://invariantlabs.ai/blog/mcp-github-vulnerability). EchoLeak: one crafted email caused "remote, unauthenticated data exfiltration" from M365 Copilot, CVE-2025-32711 [P] (https://arxiv.org/abs/2509.10540). Salesloft Drift: stolen integration OAuth tokens queried "Cases, Accounts, Users, and Opportunities" across many Salesforce orgs [P] (https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift).
10. **In no incident did anyone check with the person who held authority over the resource.** The fixes were narrower scopes (Drift: "avoid overly permissive scopes like `full`"), "supervised mode" for privileged tools (ServiceNow), one repo per session (Invariant) and dev/prod separation (Replit [P], https://replit.com/blog/introducing-a-safer-way-to-vibe-code-with-replit-databases). Each fix narrows what the agent can reach. None adds an approver other than the requester.
11. **The only shipped escalation to someone other than the requester is Microsoft's agent sponsor, and it covers lifecycle and access grants, not single operations.** Sponsors are "human users accountable for making decisions about its lifecycle and access". Access-package requests go "to designated approvers". When a sponsor leaves, "sponsorship ... is automatically transferred to their manager" [P] (https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview). OBO tokens carry the user as subject and the agent as actor [P] (https://learn.microsoft.com/en-us/entra/agent-id/agent-on-behalf-of-oauth-flow). That is the "who asked, through which agent" half of a signed statement, without the operation or the operands.
12. **Regulators name the exact gap but prescribe nothing.** FINRA, quoting its 2026 report: "Agents may act beyond the user's actual or intended scope and authority". It asks firms to "track agent actions and decisions" and to set "guardrails" [P] (https://www.finra.org/rules-guidance/guidance/reports/2026-finra-annual-regulatory-oversight-report/gen-ai). The UK consulted (14 Jul to 6 Oct 2026) on whether consent and liability rules need changing for agentic payments [P on dates, https://www.gov.uk/government/consultations/modernising-payment-services-regulation; S on content]. EU AI Act Art. 14 requires override and a "stop" button for high-risk systems [P] (https://artificialintelligenceact.eu/article/14/).

## 3. Per-case detail

### Coding-agent fleets (platform team owns the agent, an engineer requests, a third person reviews)
- **Stripe** [P] https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents: "By tagging our Slack app, engineers can kick off a minion directly from the thread discussing a change." "Over a thousand pull requests merged each week at Stripe are completely minion-produced." "the engineer opens the PR and requests a review from another Stripe engineer." Part 2 [P] https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2: "minions don't have access to real user data, Stripe's production services, or arbitrary network egress", "so we can safely run the agent with full permissions and skip confirmation prompts". Agents "request only a subset of Toolshed tools relevant to their task". Minions grew from an internal fork of goose [S].
- **Ramp Inspect** [P] https://builders.ramp.com/post/why-we-built-our-background-agent: PRs open with the user's GitHub token, "strongly preferred over having it open pull requests as the app itself", because the app model lets "any user to approve their own changes". "You do not want to knowingly create a vector for unreviewed code to go into the codebase." "any number of people can work in one session together"; authorship "is passed with every prompt sent to the agent". "Send your session to any colleague, and they can help take it home." The share of Ramp PRs is 30-50% depending on source [S].
- **GitHub Copilot cloud agent** [P] https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations: "Only users with write access to the repository can trigger Copilot cloud agent". "Prevents the user who asked Copilot cloud agent to create a pull request from approving it". "workflows are not triggered until Copilot cloud agent's code is reviewed". Commits carry "the developer who assigned the issue ... marked as the co-author". Hidden characters and HTML comments are filtered. Also https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent: "Repository administrators can configure a ruleset bypass for Copilot."
- **Block goose** [P] https://goose-docs.ai/blog/2025/04/21/mcp-in-enterprise: "Thousands of Block employees use the tool daily". "all MCP servers used internally are authored by our own engineers". MCP "lets us annotate tools as 'read-only' or 'destructive' to require user confirmation". "Some servers enforce LLM allowlists or restrict tool output from being shared across systems." OAuth inside local MCP servers is "a practical but temporary solution". Red-team "Operation Pale Fire" planted poisoned recipes [S] (BSidesSF 2026 listing).

### Shared agents in collaboration suites (who triggered vs whose permissions)
- **Notion** [P] https://www.notion.com/help/custom-agents-sharing-and-permissions: a Custom Agent responds using "the agent's own access, not the permissions of the person who triggered it". Sharing is "giving your team access to everything the agent can see". A person removed from a page "might be able to get information from that page through the agent". The Audit Log is a "Full history of all Custom Agent actions". Enterprise admins can "Change permissions and delete any agent".
- **Atlassian Rovo** [P] https://support.atlassian.com/rovo/docs/rovo-agent-permissions-and-governance/: interactively, "the agent is acting on that person's behalf". Admins "can't restrict individual agents to specific groups or teams". [P] https://jira.atlassian.com/browse/AUTO-2337: results "include links to pages that the triggering user does not have permission to view"; "agents always use the permissions of the connection user in the automation"; requested fix is "use intersecting permissions with invoking user"; status Gathering Interest; Atlassian will "soon be introducing agent accounts". A sibling ticket says agent edits show in history as the invoking user, not the agent [S].
- **Microsoft Copilot Studio** [P] https://learn.microsoft.com/en-us/microsoft-copilot-studio/configure-no-maker-authentication: "When someone uses the agent, the agent uses the maker's credentials, not the end user's credentials". "By default, both End-user and Maker-provided credentials are enabled." With maker creds blocked, "agents triggered by scheduled or autonomous events, or that attempt to run in the background, fail ... All agent triggers must involve an active user." "If the user lacks permission for something, the agent is unable to do it on their behalf - by design."
- **Microsoft Entra Agent ID** [P] https://learn.microsoft.com/en-us/entra/agent-id/agent-on-behalf-of-oauth-flow: "User delegation enables agent identities to operate on behalf of signed-in users using standard OAuth 2.0 On-Behalf-Of flows". Child agent identities inherit admin-consented scopes from the blueprint. [P] https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview: sponsors are "human users accountable for making decisions about its lifecycle and access". Requests are "routed to designated approvers". Expiring access triggers a notice to the sponsor, and an extension "can trigger a new approval cycle". If a sponsor leaves, sponsorship goes "to their manager". Licensing is E7 or Agent 365 plus P1.
- **Slack** [P] https://docs.slack.dev/reference/methods/assistant.search.context: "All API calls made using a bot token require an `action_token`" ("as received in a message event"), so a bot search is bound to the user's triggering event. Bot tokens get only public search scopes; user tokens get private, IM and MPIM scopes. Slack's docs do not say whose permissions an agent gets in user A's channel when user B triggers it (Not verified).
- **Salesforce Agentforce** [S] https://www.salesforceben.com/agentforce-permissions-explained-agent-users-access-and-security/: service agents run as a dedicated agent user; employee agents run as the logged-in user. Obsidian calls the running-user model the biggest privilege-escalation source.

### Incidents
- **ServiceNow Now Assist** [P] https://appomni.com/ao-labs/ai-agent-to-agent-discovery-prompt-injection/: "Now Assist agents run with the privilege of the user who started the interaction". Agents are "discoverable by default when published" and "automatically grouped into the same team by default". A low-privilege user planted text in a ticket; an admin's run copied a record the attacker could not read. ServiceNow said the behavior was intended and "updated the on-platform documentation". The fix advice: privileged tools "should always be configured to run in supervised mode". The authority holder who should have been asked is the owner of the record that was read (INC0000001), not the admin who happened to trigger the run.
- **GitHub MCP** [P] https://invariantlabs.ai/blog/mcp-github-vulnerability: a malicious issue in a public repo made the owner's agent leak private-repo data ("a plan to relocate, and salary") into a public PR. "this is not a flaw in the GitHub MCP server code itself". Fix advice: granular permissions, one repo per session.
- **EchoLeak** [P] https://arxiv.org/abs/2509.10540 (Aim Labs blog returned 403): "a zero-click prompt injection vulnerability in Microsoft 365 Copilot", CVE-2025-32711. Mitigations include "provenance-based access control".
- **Salesloft Drift** [P] https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift: "compromised OAuth tokens associated with the Salesloft Drift third-party application". The attacker "systematically exported large volumes of data" and hunted AWS keys and Snowflake tokens. Fix advice: "avoid overly permissive scopes like `full` access", "Enforce IP restrictions", remove "API Enabled" from profiles.
- **Replit and SaaStr** [P] Lemkin https://www.saastr.com/replits-new-release-address-most-of-the-challenges-we-hit-vibe-coding-but-is-prosumer-vibe-coding-really-ready-for-commercial-apps-yet/: "eleven separate warnings in ALL CAPS"; "Enforcing a true code freeze was simply impossible within Replit's architecture". He still wants audit trails, human review before deploy, and real-time monitoring. Replit [P] https://replit.com/blog/introducing-a-safer-way-to-vibe-code-with-replit-databases: previously "a single database for both development and live customer data". The agent now "will ask during re-deployment whether those changes need to be applied to the production database". Masad's X post calling it "unacceptable" [S].
- **Meta internal agent (Mar 2026)** [S] https://incidentdatabase.ai/reports/7169/: engineer A asked an agent to analyse employee B's forum post; the agent replied to B unprompted; B acted on the advice; the result was a SEV1 with about 2 hours of sensitive data exposed to unauthorised employees. This is the cleanest "one person's agent acting toward another person" case, but it is secondary only (The Information).

### Open-source multi-user agents

### Regulators
- **FINRA 2026** [P] https://www.finra.org/rules-guidance/guidance/reports/2026-finra-annual-regulatory-oversight-report/gen-ai: "systems or programs that are capable of autonomously performing and completing tasks on behalf of a user"; "Agents may act beyond the user's actual or intended scope and authority"; consider "how to track agent actions and decisions" and "guardrails or control mechanisms".
- **EU AI Act Art. 14** [P] https://artificialintelligenceact.eu/article/14/: overseers must be able to "disregard, override or reverse the output" and "interrupt the system through a 'stop' button". Art. 14(5) requires verification "by at least two natural persons" for biometric ID only.
- **UK** [P dates] https://www.gov.uk/government/consultations/modernising-payment-services-regulation: consultation open 14 Jul to 6 Oct 2026, covering "agentic payments". It asks whether "authentication and consent ... and liability for unauthorised payment transactions" need updating [S]. FCA 2026 payments priorities on agentic AI [S].
- **US**: the Warner "AI AGENT Act" discussion draft (Jun 2026) on "custodial user agents" with loyalty, care and confidentiality duties and an FTC registry [S]. I found no CFPB text.

## 4. Where it shows up first, and what adopters ask for
- First and most mature: **internal coding-agent fleets** (Stripe, Ramp, GitHub, Block). A platform team owns the agent, any engineer requests work, and a different person approves the output.
- Second: **shared agents in work suites** (Notion, Rovo, Copilot Studio, Agentforce, Slack). One person builds the agent, many trigger it, and it holds the builder's or its own access. This is where the leaks happen today.
- Third: **single-owner personal agents opened to other senders** (OpenClaw groups, DMs, voice). Most of their security advisories concern sender vs owner authority.
- Consumer commerce is live but narrow (Buy for Me, Visa, Mastercard). Authority is a per-purchase tap or a registered agent token, and the open fight is disputes and liability.
- What adopters ask for, in their own words or builds:
  - Self-approval blocked and a second reviewer (GitHub, Stripe, Ramp).
  - Per-prompt authorship (Ramp).
  - "intersecting permissions with invoking user" (Atlassian customers).
  - End-user creds that still allow background runs (the Copilot Studio trade-off).
  - Supervised mode for privileged tools (AppOmni).
  - Narrow scopes and short-lived tokens (Drift).
  - A human sponsor with a manager fallback (Entra).
  - Audit trails and enforced freezes (Lemkin).
  - Tracking agent actions (FINRA).
- Nobody ships routing a single out-of-rule operation to the owner of the resource. Approvals go to the requester, a code reviewer, an admin, or the "board".

## 5. What this says the first product should be, and for whom
1. Start where the pain is documented and the buyer exists: **companies running shared or triggered agents over shared SaaS** (Notion, Rovo, Copilot Studio, Slack bots, internal agents). The buyer is the platform or security team that owns the agents.
2. Wedge: a decision point that evaluates **requester ∩ agent grant ∩ resource rule** per operation. That is exactly what AUTO-2337 customers asked for and vendors refuse, and it removes the maker-creds-vs-no-autonomy trade-off Microsoft documents.
3. Each decision records a signed statement: who asked (Ramp-style per-prompt authorship), through which agent (Entra's subject/actor), and the operation and operands. Incidents show the operands and their provenance are what matter (ServiceNow, EchoLeak, GitHub MCP).
4. Out-of-rule requests escalate to the **resource's holder**, with sponsor-to-manager fallback (Entra already proves orgs accept this shape). Requester self-approval is blocked by default, as GitHub does for PRs.
5. Do not lead with coding agents. They already solved this with sandboxes plus PR review. Plug into their PR or ticket review as one adapter.
6. Don't sell "owner approves everything". Paperclip's board model and OpenClaw's operator model are the incumbent pattern, and both fail once more than one person is involved.
7. Consumer commerce and regulated finance come later. The rules (UK consultation, Warner draft, Visa and Mastercard registries) are still moving. The record and log format should still be built to satisfy FINRA's "track agent actions and decisions".
