## 1. Architecture from the repo

**Layout.** npm workspaces `backend`, `frontend`, `packages/*` (`packages/dashboard`, `packages/shared-schemas`, `packages/ui`), built with `turbo`. Other top-level dirs: `functions/` (Deno runtime: `server.ts`, `worker-template.js`, `deno.json`), `deploy/` (`setup.sh`, `backup.sh`, `docker-compose/docker-compose.yml`, `docker-init/db/*.sql`), `docker/`, `openapi/` (17 YAML specs: ai, auth, dashboard, deployments, email, functions, health, logs, metadata, payments, realtime, records, schedules, secrets, storage, tables, usage), `docs/`, `examples/`, plus agent dirs `.agents/`, `.claude/`, `.claude-plugin/`, `.codex/` [P https://api.github.com/repos/insforge/insforge/contents/].

**Backend** is one Express 4 app (`backend/src/server.ts`), `pg` + `node-pg-migrate` (system migrations in schema `system`, table `migrations`), `jose` + `jsonwebtoken`, `openai`, `stripe`, `razorpay`, `socket.io`, six `@aws-sdk/*` packages, `nodemailer`, `libpg-query`, `winston`. No Supabase, Drizzle, Kysely, Hono or MCP packages [P backend/package.json]. Route groups under `/api`: advisor, ai, analytics, auth, compute, dashboard, database, deployments, docs, email, functions, github, logs, memory, metadata, payments, realtime, s3-gateway, schedules, secrets, storage, usage, webhooks, webscraper [P backend/src/api/routes]. Also mounted: `/storage/v1/s3` (S3 protocol gateway), `/functions/:slug` (proxy to Deno Subhosting if configured, else the local Deno container), `/.well-known/jwks.json`, `/api/health`, and the dashboard SPA at `/dashboard*` [P server.ts].

**docker-compose.yml (dev)** — four services [P]:
| service | image | host port |
|---|---|---|
| `postgres` | `ghcr.io/insforge/postgres:v15.13.4` (own image; pg_cron db + pgvector per release notes) | `${POSTGRES_PORT:-5432}` |
| `postgrest` | `postgrest/postgrest:v12.2.12`, `PGRST_DB_SCHEMA=public`, `PGRST_DB_ANON_ROLE=anon`, `PGRST_JWT_SECRET=$JWT_SECRET` | `${POSTGREST_PORT:-5430}`→3000 |
| `insforge` | built from `Dockerfile` target `dev` | `${APP_PORT:-7130}`, `${AUTH_PORT:-7131}`, `${UI_PORT:-7132}` (Vite dev) |
| `deno` | `denoland/deno:alpine-2.0.6`, runs `functions/server.ts --watch` | `${DENO_PORT:-7133}` |

**Prod compose** (`deploy/docker-compose/docker-compose.yml`, what `setup.sh` installs) is the same four services with `ghcr.io/insforge/insforge-oss:latest` (unpinned), postgres/postgrest/deno bound to `127.0.0.1`, and 7130 on all interfaces [P]. There is **no separate auth service**: `server.ts` starts a single `app.listen(PORT)`; auth is a router at `/api/auth`. Port 7131 is published but what binds it is not visible in `server.ts` [U]. No dedicated realtime service: `SocketManager` (Socket.IO) attaches to the same HTTP server and `RealtimeManager` listens on `pg_notify` [P server.ts]. Dashboard events moved from Socket.IO to SSE in v2.3.0 [P releases].

**Borrowed from Supabase.** PostgREST, the `anon`/`authenticated` roles with `PGRST_DB_ANON_ROLE=anon`, `auth.uid()` in policies, `auth.users`, `storage.objects`, and an SDK shaped like supabase-js (`createClient({ baseUrl, anonKey })`, `.from().select()`, `{ data, error }`) [P db-init.sql; skill SKILL.md; auth docs]. Supabase's `service_role` is replaced by `project_admin` [P db-init.sql]. Everything else (auth, storage, functions host, AI gateway, deployments) is InsForge's own Express code.

**Multi-project.** Self-host: one full stack per project — "give each project its own directory and set a unique `COMPOSE_PROJECT_NAME`", with `POSTGRES_PORT`, `POSTGREST_PORT`, `APP_PORT`, `AUTH_PORT`, `DENO_PORT` per project [P README]. The CLI's `local start` does the same per directory, shifting the port block by ten when 7130/7131/7133/5432/5430 are taken [P skill references/local.md]. Cloud: the OSS container is the per-project data plane (`PROJECT_ID`, `DEPLOYMENT_ID`, `APP_KEY`, `CLOUD_API_HOST=https://api.insforge.dev` in `.env.example`); branches "run on their own EC2 instance", and `projects upgrade-instance nano|micro|small|medium|large|xl` sizes a project [P branching docs; CLI skill]. The control plane (orgs, projects, billing, branching) is **not in the OSS repo** [S: inferred from env vars and skill command list].

**"Project" data model.** In the OSS code a project *is* the instance: one Postgres (`public` for user tables, `auth`, `storage`, `functions`, `system`, `payments` schemas), one `ik_` admin key, one `anon_` key, one JWT secret. The cloud `projects` object (id, name, domain, instance size, org, version) lives only behind api.insforge.dev [S].

**Secrets (`deploy/setup.sh`).** Sparse-clones the repo, copies `.env.example` → `.env` (mode 600) and writes, via `openssl rand -hex N`: `JWT_SECRET` (64 hex), `ENCRYPTION_KEY` (64 hex), `ROOT_ADMIN_PASSWORD` (24 hex), `POSTGRES_PASSWORD` (32 hex), `ACCESS_API_KEY` = `ik_` + 40 hex, `ACCESS_ANON_KEY` = `anon_` + 40 hex; sets `COMPOSE_FILE=deploy/docker-compose/docker-compose.yml`; starts nothing; you must set `API_BASE_URL`/`VITE_API_BASE_URL` yourself [P setup.sh]. Keys are opaque random strings, not signed JWTs; if left empty the backend generates them on first boot [P .env.example]. Open issue #2140 / PR #2172: keys were logged in plaintext at startup [P issues].

## 2. What an agent does, end to end

**Two agent interfaces.** README: "MCP Server (self-hosted and cloud)" and "CLI + Skills (cloud only)" [P README]. In practice the CLI also talks to OSS backends (see §4).

**MCP server** — `@insforge/mcp` (repo https://github.com/insforge/insforge-mcp, 38 stars). Self-host: `npx -y @insforge/mcp@latest` with env `API_KEY` (the `ik_` key) and `API_BASE_URL` (default `http://localhost:7130`); installer `npx @insforge/install --client <claude-code|cursor|windsurf|cline|roo|trae> --env API_KEY=… --env API_BASE_URL=…` [P insforge-mcp README]. Cloud: remote `https://mcp.insforge.dev/mcp` via `npx add-mcp …`, browser login + org/project grant [P docs/mcp-setup.md]. Tools registered in `src/shared/tools/*.ts` [P]:
- `fetch-docs` (GET `/api/docs/{type}`), `fetch-sdk-docs` (feature × language; backend ≥1.5.1), `get-anon-key` ("Generate an anonymous JWT token that never expires", POST `/api/auth/tokens/anon`)
- `get-backend-metadata` (GET `/api/metadata?mcp=true`), `get-table-schema` (schema incl. RLS/indexes), `run-raw-sql` (POST `/api/database/advance/rawsql`, admin), `bulk-upsert` (CSV/JSON file; stdio-only), `download-template` ("MANDATORY FIRST STEP", `npx create-insforge-app`, `react`|`nextjs`)
- `create-bucket`, `list-buckets`, `delete-bucket`
- `create-function`, `get-function`, `update-function`, `delete-function` (inputs `slug`, `name`, `description`, `status`, `code` string or `codeFile`)
- `get-container-logs` (sources `insforge.logs`, `postgREST.logs`, `postgres.logs`, `function.logs`), `create-deployment` (backend ≥1.4.7; uploads a directory via `/api/deployments/direct` + per-file PUT), `start-deployment`
Docs also name `get-function-logs` [P functions overview] but it is not in the MCP source [U]. Raw SQL blocks system tables and `auth.users` [P mcp-setup docs].

**CLI** — `npx -y @insforge/cli` (repo https://github.com/InsForge/CLI, 22 stars, 81 open issues; npm 403 to fetch). Command groups from the `insforge-cli` skill [P https://raw.githubusercontent.com/insforge/insforge-skills/main/skills/insforge-cli/SKILL.md]: `login|logout|whoami|current|create|link|list|metadata|local`; `projects get|update|restore|update-version|upgrade-instance|delete|transfer`; `orgs …`; `billing status|credits|history|cycles|upgrade|manage`, `usage`; `backups list|latest|create|rename|delete|restore`; `db migrations new|up`, `db query [--unrestricted]`, `db rpc`, `config export|plan|apply` (`insforge.toml`); `storage buckets|create-bucket|delete-bucket|list-objects|upload|download`, `storage s3-keys …`; `functions list|code|deploy|invoke|delete`; `ai setup|overview`; `memory list|recall|remember`; `payments stripe|razorpay …`; `deployments deploy <dir>|list|status|cancel|env list|env set`, `domains`; `compute deploy …`; `secrets list|get|add|update|delete|rotate`; `schedules …`; `branch create|list|switch|merge|reset|delete`; `diagnose [advisor|db|metrics|logs] [--ai]`, `logs <source>`; `advisor scan|suppress…`; `docs`, `feedback`; `posthog setup` (cloud only), `webscraper apify connect`. Global `--json`, `-y`; exit codes 0/1/2 (not authenticated)/3 (not linked)/4/5.

**Agent auth.** Cloud: `login` opens a browser; headless `login --user-api-key uak_…` (key from Profile → API Keys); sandboxes `login --device` (RFC 8628) → `INSFORGE_ACCESS_TOKEN`; "autonomous registration (preview)" via a WorkOS ID-JAG posted to `/agent/auth` [P https://agents.insforge.dev/auth.md]. Then `create` or `link --project-id <id>`, which writes `.insforge/project.json` (`oss_host` field) [P skill]. Self-host: `link --api-base-url <url> --api-key <ik_ key>` "without platform login" [P skill]; MCP uses the `ik_` key directly. App anon key: `secrets get ANON_KEY` → `NEXT_PUBLIC_INSFORGE_URL` / `_ANON_KEY` etc. [P skill].

**Skills** (repo https://github.com/InsForge/insforge-skills, 46 stars). Install: `/plugin marketplace add InsForge/InsForge` + `/plugin install insforge` (Claude Code), `npx -y skills add insforge/insforge-skills`, `codex plugin marketplace add InsForge/insforge-skills` [P CLAUDE_PLUGIN.md; skills README]. Four skills [P]: `insforge` (app code with `@insforge/sdk`; rules: anon-key client vs `createAdminClient({ apiKey })` server-only, inserts take arrays, storage governed by RLS on `storage.objects`, branch before risky schema/RLS/OAuth changes, Tailwind 3.4, `vercel.json` for SPA routing, run local build before deploy); `insforge-cli` (rules: always `npx -y`, treat API keys as full-access admin, prefer CLI over raw HTTP, `--json`, check project memory, report platform bugs with `feedback`; cloud default, Docker only if user asks); `insforge-debug` (diagnostics only, no fixes); `insforge-integrations` (Auth0, Clerk, Kinde, Stytch, WorkOS, Better Auth, OKX x402).

**Migrations.** Plain SQL in `migrations/<YYYYMMDDHHmmss>_<name>.sql`; `db migrations new|up --all|up <v>|up --to <v>|list|fetch`; recorded in `system.custom_migrations`; each file in a transaction, `search_path=public`, `BEGIN/COMMIT` rejected, 30 s `statement_timeout`; forward-only, no `down` [P docs/core-concepts/database/migrations.md]. MCP path is `run-raw-sql`.

**Edge functions.** Code is stored in Postgres (`functions.definitions`: `slug`, `code`, `status`), not on disk; `functions/server.ts` serves `/<slug>` (single segment, no subpaths), spawns a Deno `Worker` from `worker-template.js` per request with env/read/write/run/FFI off and net on, passes secrets from `system.secrets` (AES-GCM, key = SHA-256 of `ENCRYPTION_KEY`) by message, `WORKER_TIMEOUT_MS=60000` → 504 [P functions/server.ts]. Public URL on cloud `https://<project>.insforge.dev/functions/<name>`; triggers: HTTP, cron (`schedules`, pg_cron syntax), DB `INSERT/UPDATE/DELETE` with a service-role JWT; imports via `jsr:`/`esm.sh`/`npm:` [P functions overview]. Exact handler signature inside `worker-template.js` not read [U]. Cloud runs on Deno Subhosting v2 (`DENO_DEPLOY_TOKEN`, `DENO_DEPLOY_ORG_ID`; v2.2.2) [P .env.example; releases]; pre-deploy `deno check` since v2.2.4 [P].

**Storage.** Buckets public/private, presigned direct uploads, RLS on `storage.objects`, S3-compatible gateway at `/storage/v1/s3` with per-project `s3-keys`; backends: local FS (default), `docker-compose.minio.yml` / `docker-compose.rustfs.yml` overlays, or BYO S3 via `S3_BUCKET`, `S3_ENDPOINT_URL`, `S3_USE_PRESIGNED_URLS=false` proxy mode; `MAX_FILE_SIZE` default 50 MB [P README; .env.example; storage overview].

**Model gateway.** OpenAI-compatible: `/v1/chat/completions` (SSE), `/v1/embeddings`, `/v1/models` at `https://<project>.insforge.dev/v1` on cloud; routes through OpenRouter (OpenAI, Anthropic, Google, Mistral, Llama…); per-project rate limit and spend cap → 429; per-request model/token/cost logging; cloud "billed by usage", "reconciles to OpenRouter's invoice" [P docs/core-concepts/ai/overview.md; pricing]. OSS mounts it at `/api/ai` and needs your own `OPENROUTER_API_KEY` (or `ai setup`), copied into the encrypted secret store on first boot [P server.ts; .env.example].

**Site deployment.** `deployments deploy ./frontend` uploads the source tree (skips `node_modules`, `.git`, build output, `.env`) → InsForge creates a **Vercel production deployment**; Vercel detects the framework (`package.json`, `vercel.json`); static on Vercel CDN, server code in `iad1` unless `vercel.json` `regions` [P docs/core-concepts/sites/overview.md]. URL `https://<appkey>.insforge.site`, optional slug `https://<slug>.insforge.site` (3–63 chars), custom domains via `POST /api/deployments/domains` (CNAME/TXT/A returned) [P openapi/deployments.yaml]. API: `POST /direct` → `PUT /{id}/files/{fileId}/content` → `POST /{id}/start` → `/sync`, `/cancel`; statuses `WAITING|UPLOADING|QUEUED|BUILDING|READY|ERROR|CANCELED`; env vars are set for production/preview/development, but **no preview target, no rollback/promote/redeploy endpoint** [P deployments.yaml]. Self-host needs your own `VERCEL_TOKEN`, `VERCEL_TEAM_ID`, `VERCEL_PROJECT_ID` ("Required for self-hosted site deployments and custom domains") [P .env.example]. Compute (long-running containers): Fly.io on cloud or with `FLY_API_TOKEN`/`FLY_ORG`; Docker provider on self-host via the Docker socket (root-equivalent), ingress `none|port|host`, no TLS termination, one instance per service, no persistent volumes [P docs/core-concepts/compute/overview.md].

## 3. App-user auth and permissions

**Providers:** email+password (confirmation, reset, throttling), magic link + 6-digit OTP, OAuth Google/GitHub/Apple/Microsoft/GitLab/Discord/LinkedIn/X (`.env.example` has `GOOGLE_`, `GITHUB_`, `DISCORD_`, `MICROSOFT_`, `LINKEDIN_`, `X_`, `APPLE_` `_CLIENT_ID/_SECRET`, redirect `http://localhost:7130/auth/<provider>/callback`), custom OIDC by URL (Keycloak, Okta, Auth0), third-party JWT integrations (Clerk, Auth0, WorkOS, Kinde, Stytch, Better Auth), and an OAuth-server mode where InsForge is the IdP (`/api/oauth/v1/authorize`, `/token`, PKCE; client registration "not self-serve — contact InsForge") [P auth overview; .env.example; oauth-server.md]. Self-host must configure custom SMTP or no verification/reset mails are sent [P auth overview]. Users live in `auth.users`, `auth.user_providers`; JWTs are RS256 with JWKS (HS256 fallback) since v2.2.5 [P releases].

**Roles and policies.** `db-init.sql` creates `anon`, `authenticated`, `project_admin` (NOLOGIN); grants `SELECT/INSERT/UPDATE/DELETE` on all current and future `public` tables to all three; two event triggers add `project_admin_policy` (`USING (true) WITH CHECK (true)`) when RLS is enabled on a table; **no policies are generated for `anon` or `authenticated`**, and RLS is not enabled automatically [P deploy/docker-init/db/db-init.sql]. Consequence: a table created without `ENABLE ROW LEVEL SECURITY` is fully writable with the anon key — open issue #2153 "SQL Editor tables get no RLS: anon key can insert/delete every row (self-host 2.3.4)" [P]. Guidance lives in the skill reference (`database/access-control.md`: RLS required on "tables with user data", owner pattern `user_id = (SELECT auth.uid())`, separate per-op policies, `SECURITY DEFINER` helpers with pinned `search_path`, index policy columns) — a manual checklist, no linter [P]. The **advisor** (`diagnose advisor`, `advisor scan`) flags findings such as a permissive policy exposing a table to anon, with SQL fixes [P docs/agent-native/diagnostics.md]. `insforge.toml` config-as-code covers auth settings, password rules, SMTP, storage size, retention, deployment subdomain — not OAuth credentials, buckets, functions, secrets or RLS [P config-as-code.md].

**Agent vs end user: one middleware, different credentials.** `backend/src/api/middlewares/auth.ts`: `verifyUser` dispatches on the Bearer token — `ik_…` → `verifyApiKey` (admin, no `req.user`), `anon_…` → `verifyAnonKey` (role `anon`), else JWT → `verifyToken` (role from claim); `verifyAdmin` requires `ik_` key, a `project_admin` JWT (dashboard login via `ROOT_ADMIN_USERNAME/PASSWORD`) or a cloud `project_authorization` token [P]. So the agent (admin key) and the app's users (JWTs from `/api/auth`) share one auth stack and one header, separated by role; the cloud `uak_` user key and device-flow tokens authenticate the agent to the *control plane*, not to the project's PostgREST.

## 4. Cloud vs self-host

**Pricing** [P https://insforge.dev/pricing]: Free $0 — 50k MAU, 500 MB DB, 5 GB bandwidth, 1 GB storage, 100k function calls, 600 build minutes, 120 h compute, paused after 1 week inactive, 1 manual backup slot. Pro $20/mo yearly ($25 monthly) — 100k MAU then $0.00325/MAU, 8 GB DB then $0.125/GB, 250 GB bandwidth then $0.09/GB, 100 GB storage then $0.021/GB, 100k calls then $0.01/1k, unlimited build time, compute and AI gateway by usage, $10 compute credit, daily backups with 7-day retention, 5 manual slots. Enterprise custom: SOC2, HIPAA add-on, SSO, unlimited projects. Project count per plan not stated [U]. Branch limits: 3 parent projects/org, 2 active branches/parent [P branching.md].

**Cloud-only or cloud-dependent:** project/org/billing/usage commands (`create`, `list`, `orgs`, `billing`, `usage`, `whoami` "still reach InsForge Cloud" even when linked locally) [P local.md]; the remote MCP; branching (control-plane EC2 clones; docs say "Available on InsForge OSS 2.1.0+" but creation needs the platform) [P/S]; managed email sender; Deno Subhosting; `posthog setup`; managed compute. Site deploy and custom domains work self-hosted only with your own Vercel token [P .env.example]. README's "CLI + Skills (cloud only)" is contradicted by the skill docs (`link --api-base-url --api-key`, `local start`, `config apply` against OSS) — treat the CLI as usable against OSS for db/functions/storage/secrets/config/backups, cloud for the rest [P README vs skill].

**One-click hosts:** Railway, Zeabur, Sealos, RepoCloud, ZopDay buttons in README; guides for AWS EC2, GCP, Azure, Hetzner, Coolify, Dokploy, Containarium, plus a VPS security guide [P README; llms.txt].

**Backups:** self-host has scheduled backups in Database Settings (6 h–weekly or cron, stored on local disk/S3, missed runs catch up on restart; v2.3.0), manual backup/restore (restore replaces the DB, takes the project offline, cannot be undone), `backups …` CLI works self-hosted; `deploy/backup.sh` is a `pg_dump` + `.env` copy with `RETENTION_DAYS=14`, no scheduler, no restore; storage files are never included [P backups.md; backup.sh; changelog 2026-08-07].

**Branching** ("backend branching", Product Hunt 2026-06-03, #2 of the day): a branch is a child project on its own EC2 instance restored from the parent — Postgres (full or schema-only), auth config, storage, functions, email templates, realtime channels, schedules; shares the parent JWT secret, own API key; `branch merge --dry-run --save-sql` does a three-way schema diff, `branch reset` returns to the creation snapshot; compute and site deployments do not branch; data rows are not merged [P branching.md].

**Observability:** `logs <source>` (`insforge.logs`, `postgREST.logs`, `postgres.logs`, `function.logs`, `function-deploy.logs`), `diagnose` (advisor + db health + CPU/mem/disk + error logs, `--ai "<question>"`), per-invocation function logs, per-container compute logs, MCP `get-container-logs`; cloud ships logs to CloudWatch, OSS writes Winston files to `LOGS_DIR`; anonymous self-host telemetry is on unless `INSFORGE_TELEMETRY_DISABLED=1` [P diagnostics.md; .env.example; backend deps].
