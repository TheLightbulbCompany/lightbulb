## 1. Correction to the earlier note

The earlier note called the surviving idea "narrower than stated". That was the wrong word. The evidence narrowed one claim, "build the business its own version of the SaaS it pays for", not the thesis the founder actually holds. The thesis as restated here, small software built inside the company for a job, one-off or recurring, is the version the evidence supports, and it is the version YC has written a request for.

## 3. Findings

1. **The thesis holds, and the founder's split is the right one.** Recurring internal tools are a served, crowded lane (Lovable, Power Platform, Retool, Softr, nine YC tools). One-off internal software is unserved: Lovable defines it out of scope, charges in a way that punishes it, and is building toward governance; the chat tools return a document, not a tool; the people who build one-offs on Replit let most of them die, which is the point.
2. **"Nobody uses Lovable for that" is half true, and the half that matters is true.** Ops people do build durable trackers on Lovable and then leave because of upkeep and credits. Nobody builds a use-once tool on it, and its 2026 roadmap says it does not want them.
3. **The breakages are permissions, data, handoff and memory, not generation.** Every source puts data access and access control first, who fixes it second, who remembers it exists third. Koomen's request for startups is a list of exactly those: deployment, sharing, authentication, permissions "handled for you".
4. **The unserved lane maps onto what a messaging workspace already is.** A tool that lives in the room where it was asked for inherits the room's membership as its permission, the workspace's connections as its data, the thread as its discoverability, and the agent that built it as its maintainer. When the job is done it is a message in history, searchable later, costing nothing to keep or forget. That is "shared like a Google Doc" without a new URL.
5. **This fits the current wedge better than the contractor idea did.** The people Retool and Rokt describe, technical staff building tools outside IT, are the 3-to-15 teams already running Claude Code and Codex. The non-technical cofounder who needs the tool is the second person the plan calls the activation event. The tool is the handoff Lightbulb already sells: built on the network, kept in the workspace. The SMB fallback (Anna's shape) is the same product with the agent doing the building.
6. **The nearest neighbours are small and new, and one of them is a workspace.** Plyxl (W27, four people) sells "the workspace that does the work… custom automations, agents, and apps for your business" and demos on an HVAC firm. Floot (S25) is the hosting layer "inside Claude and ChatGPT". Neither has a network of the team's own coding agents, rooms with people and agents, approval cards, or a record of who asked and who said yes.
7. **The limits that stay.** The best model passes 62% of end-to-end app workflows unattended; a one-off tool can tolerate that (it is checked once and used once), a recurring one cannot. The sandbox in the room is read-only on live data; a recurring tool with live data needs a host that knows the workspace's identity, which Lightbulb does not have yet. And the demand numbers are vendor samples; nobody has measured how often a person wants an interactive one-off tool rather than a one-off table.

## 4. What this means for Lightbulb

- Keep the contractor "replace Jobber" version dead. Keep the "small tool beside the suite" pilot from the earlier note as the SMB instance of this thesis.
- Name the product by its lifecycle, not its size: a tool is asked for in a room, built by an agent (a workspace agent, or a teammate's Claude Code on the network), appears in the room, is used, and either dies in history or is promoted to recurring. Promotion is the explicit step: a routine, a deploy to the owner's Vercel, or a Lightbulb-hosted tool bound to the room's membership. Lovable's model charges to keep things alive; this one costs nothing to let things die.
- The three breakages become the three product rules: the room is the permission, the workspace connections are the data, the agent that built it answers for it in the same room.
- Do not put this on the homepage. It is a reason the workspace exists, demonstrated in the room, and a Show HN of its own later ("asked my agent for a tool in chat; my cofounder used it; nobody deployed anything") once it can be watched working.

## 5. What to test, cheaply

1. **Count what already happens.** Ask Gauge for the last 30 days of agent messages with an HTML, CSV or XLSX attachment in external workspaces, and how many were opened by a second person. That is the one-off case in the wild, if any.
2. **Make the one-off path deliberate.** The agents' instructions say: when a person asks for a calculator, a tracker, a form, a comparison or a dashboard, answer with a single-file tool attached to the room, data baked in from the connections, with one line saying what it reads and when it was read. Measure: tools attached per week, opened by someone other than the asker, re-asked for a week later (the signal for "promote").
3. **One recurring promotion by hand.** For the first tool that gets re-asked, deploy it to the owner's Vercel through the credential skill the agents already have, with the agent as its owner on the task board. Log the upkeep: changes asked, changes shipped by chat, incidents.
4. **Decide the host question with that log.** If promoted tools accumulate, Koomen's "shared, secured URL in one step" bound to the workspace's identity is the build; the Stripe Projects rail provisions the database and host, and Lightbulb's own identity is the auth. If they do not, the room is enough and nothing is built.

## 6. Open questions

1. How often does a person want an interactive tool rather than a table or a document? Programming is 4.2% of ChatGPT messages; Cowork ships documents. The in-product count (test 1) answers this for Lightbulb's users.
2. Does the room sandbox need live data for the one-off case, or is a timestamped snapshot the honest default? (A snapshot is also the safer one: nothing in the room holds a credential.)
3. Who owns a promoted tool when the person who asked for it leaves? The agent, by rule, but the approval chain for changes needs a named human.
4. Is the network path real: can a teammate's Claude Code build the tool and hand it to the workspace room today, or only a workspace agent? The 30-minute turn budget on the workspace runtime argues for the network path on anything larger than a single file.
